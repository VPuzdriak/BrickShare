# Write a lesson script

Lesson id: `$ARGUMENTS`

You write the script for this one lesson. The author reads the script and types the code into the repository by hand.

## Hard rules

- Write exactly one file: `docs/lessons/<id>-<slug>.md`. Example: `docs/lessons/2.10-inventory-code.md`. The slug is a short kebab-case form of the lesson title.
- Do not create, edit, or delete any other file. Do not touch source code, `docs/Progress.md`, `docs/CoursePlan.md`, or other docs. All code goes into the Markdown file only.
- Do not build, run, or format code.
- A file that the dotnet CLI can generate is created by the CLI in the script, never typed by hand. Use `dotnet new`, `dotnet sln`, `dotnet add package`, `dotnet ef migrations add`, or `dotnet user-jwts`. The rule is in "Generated files" below.
- If the lesson id is missing or is not in `docs/CoursePlan.md`, stop and say so. Do not guess.
- If the file already exists, read it and rewrite it in full.

## Step 1. Gather context

Read these before you write anything:

1. `CLAUDE.md`: code conventions, DDD and TDD rules, architecture rules. The script code must follow all of them.
2. `docs/CoursePlan.md`: find the lesson row. Note its title, its features (F01 = `docs/features/01-*.md`, and so on), and the lessons before and after it.
3. Each feature file the lesson links to in `docs/features/`. Business rules come from here only.
4. The matching sections of `docs/Architecture.md` (the service section, plus 7.1 and 7.2 for DDD and TDD).
5. Earlier lesson scripts in `docs/lessons/`, at least the previous one. Reuse their names, folders, and types.
6. The current source tree (`git ls-files`, then read the files the lesson changes). The author may have changed the code. The code in the repository wins over earlier scripts.

Scope: cover only what the lesson title promises. Do not build things that belong to later lessons. If a later lesson needs a hook, leave it out and let that lesson add it.

## Step 2. Write the script

Use this structure:

````markdown
# Lesson <id>. <Title>

Features: [F01](../features/01-catalog-management.md) (omit the line if the lesson has none)
Previous: [<id>](<file>.md) · Next: <id> <title>

## Summary

Two to four sentences: what we build and what works at the end.

## The problem

What is wrong or missing before this lesson, and why it matters for BrickShare.
Quote or link the business rules from docs/features/ that drive the lesson.
Name the concept or pattern we introduce and why it fits here.

## Step 1. <Short imperative title>

One or two sentences: why this step.

`path/to/File.cs`

```csharp
// code
```

Run: `dotnet test ...` → expected result (red, with the reason, or green).

## Step 2. ...

## Result

What now works. The test command and the expected green output.
A short list of files added or changed.
````

### Step rules

- Follow TDD: a failing test first, then the simplest code that passes, then a refactor step if one is needed. Say "red" or "green" after each test run, and why.
- Test names describe behavior (`Pickup_fails_when_deposit_is_not_secured`). Use xUnit v3 and AwesomeAssertions. Never FluentAssertions.
- One step changes one thing. Keep steps small enough to type in a few minutes.
- Every code block starts with its repository-relative file path on the line above.
- New file generated by the CLI: the command only, as in "Generated files". New file written by hand: show the full content. Changed file: show the full changed member or block, with enough context lines to find it, and say what replaces what.
- Code must compile against the current tree and match the project conventions: Minimal APIs, vertical slices, central package management (versions only in `Directory.Packages.props`), `TimeProvider`, `long` money in minor units, RFC 9457 `ProblemDetails`, and authorization on every endpoint group.
- Include shell commands the author must run (`dotnet new`, `dotnet add package`, `dotnet ef migrations add`, `dotnet user-jwts`) as `powershell` blocks.

### Generated files

When a step creates a file the dotnet CLI can generate, the step uses the CLI. Known commands (verified with the SDK 10.0.100 templates):

| File | Command | Note |
|------|---------|------|
| `global.json` (new) | `dotnet new globaljson --sdk-version <version>` | Does not edit an existing file. Edit by hand. |
| `.editorconfig` (new) | `dotnet new editorconfig` | Appending a section to an existing file is a hand edit. |
| `.gitignore` (new) | `dotnet new gitignore` | |
| Solution file | `dotnet new sln` | SDK 10.0.100 writes `.sln`, not `.slnx` (see lesson 1.1). |
| Class library | `dotnet new classlib -n <Name> -o <folder>` | Writes `TargetFramework` net11.0 and `Class1.cs`. See the template checks below. |
| xUnit test project | `dotnet new xunit -n <Name> -o <folder>` | Writes xUnit v2 with the VSTest packages (`Microsoft.NET.Test.Sdk`, `xunit`, `xunit.runner.visualstudio`, `coverlet.collector`), a `net11.0` target, a `Using Include="Xunit"` item, and a sample `UnitTest1.cs`. The SDK 10.0.100 has no `--xunit-version` option. Adjust by hand. See the template checks below. |
| C# class, interface, record | `dotnet new class -n <Name> -o <folder>` (and `interface`, `record`) | |
| Package reference | `dotnet add <project> package <id>` | No version: central package management. |
| Remove package | `dotnet remove <project> package <id>` | Removes a package the template added. |

The table shows the SDK's own short names. Do not invent a short name. The SDK has `xunit`, not `xunit3`. The xUnit v3 packages are added with `dotnet add ... package xunit.v3`.

For the xUnit test project, the step runs the command, then removes the VSTest and coverlet packages, adds `xunit.v3` and `AwesomeAssertions`, deletes `UnitTest1.cs`, and shows the full project file as it should read. The full file is shown because the hand edits change several lines, as lesson 1.6 does.

Rules for a generated file:

- The step shows the command in a `powershell` block, with a `Run from ...` line. Do not show the template output in full. The author sees the file on disk.
- After the command, show only the hand edits, as before and after.
- If the template output conflicts with [CLAUDE.md](../../../CLAUDE.md) or the repository's `Directory.Build.props`, `Directory.Packages.props`, or `global.json`, still run the template, then adjust the conflicting lines by hand. Show each adjustment as before and after, and say why in one sentence in the step. Examples of a conflict: a `Version` on a `PackageReference`, a `TargetFramework` that differs from `Directory.Build.props`, or a second `global.json` inside a project folder.
- A file that the CLI does not generate, such as `docs/Progress.md`, Markdown, or a test body, is written by hand.
- Do not add explanations as code comments. Explain in the prose around the block.
- Source samples never mention the course. No "course", "lesson", "tutorial", or "student" in code, comments, exception messages, test names, or identifiers. Prose around the block may mention the course.
- Plain technical English: short sentences, active voice, one term per concept.

## Step 3. Check and report

Before you finish, reread the script and check:

- Every business rule in the code traces to a feature doc.
- No step uses a type or file that an earlier step or the current tree does not define.
- Every file the lesson creates by hand is one the CLI cannot generate. Every file the CLI generates and then adjusts by hand has its adjustments shown and explained in the step.
- Nothing from a later lesson slipped in.

Then reply with the file path and a two-line summary. Mention any open question or doc gap you found, but do not fix docs yourself.

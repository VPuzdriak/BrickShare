# Lesson 1.11. GitHub repository setup: pull requests only, squash merges, branch protection

Previous: [1.10](1.10-ci-workflow.md) · Next: 2.1 Catalog Domain and Api projects, architecture tests, first Minimal API endpoint, OpenAPI and Scalar

## Summary

We configure the GitHub repository in the GitHub web interface. Only squash merges are allowed. Nobody can push to `main` directly, and no pull request merges until the `ci` check is green. We prove the rules by trying to break them: a direct push to `main` is rejected. At the end, we merge this lesson's own pull request through the same gate that protects `main` for the rest of the course.

## The problem

Lesson 1.10 added the `ci` check, but nothing requires it. Until now, a commit can still go straight to `main`, and a pull request can merge while `ci` is red or still running. The check only reports. It does not block.

[Architecture.md section 10.1](../Architecture.md#101-github-setup) sets the rule for `main`: a pull request is required, CI must pass, and only squash merges are allowed. There is no required review, because the course is solo work. The course plan row for this lesson says the same.

The concepts:

- **Merge settings.** The repository decides which merge methods a pull request may use. We keep squash and turn off merge commits and rebase merges. Squash gives one commit per pull request on `main`, so the history reads as one line per lesson.
- **Ruleset.** A ruleset applies rules to a branch. GitHub offers rulesets and the older classic branch protection. We use a ruleset, because it is the current form and it shows every rule on one page.
- **Required status check.** The ruleset names the check `ci`. GitHub blocks the merge until that check passes. The name comes from the job id in `.github/workflows/ci.yml` (lesson 1.10).
- **No bypass.** The ruleset has an empty bypass list. The repository owner also goes through a pull request.

## Step 1. Check the starting state

This step changes nothing. It confirms the repository state that the lesson depends on.

Run from the repository root:

```powershell
git status
git branch --show-current
```

Expected: `git status` reports a clean tree. `git branch --show-current` prints `main` or `lesson-1.10`.

In the browser, open the repository on GitHub, then open the pull request for lesson 1.10. Its Checks section shows the `ci` check as passed. If that pull request is not open yet, finish lesson 1.10 first.

Rulesets need a public repository or a paid GitHub plan for a private one. Open **Settings**. If the **Rules** item is missing from the left menu, the plan does not allow rulesets. Make the repository public or change the plan before you go on.

## Step 2. Red: check the merge settings

We look at the merge settings first. A new repository allows all three merge methods, so the check fails until we change them.

In the browser, open **Settings**, then **General**. Scroll to the **Pull Requests** section.

Expected: red. **Allow merge commits**, **Allow squash merging**, and **Allow rebase merging** are all checked. The target is: only **Allow squash merging** is checked.

## Step 3. Green: allow squash merges only

We turn off the two methods we do not want. Squash merging stays on.

In **Settings**, then **General**, **Pull Requests** section:

1. Uncheck **Allow merge commits**.
2. Uncheck **Allow rebase merging**.
3. Keep **Allow squash merging** checked. Leave its default commit message as it is.

GitHub saves each change when you click the box.

Expected: green. Reload the page. Only **Allow squash merging** is checked.

## Step 4. Red: check the rulesets

We look at the rulesets. A new repository has none, so `main` has no rule yet.

In **Settings**, open **Rules**, then **Rulesets**.

Expected: red. The list is empty, or it shows no ruleset for `main`.

## Step 5. Green: create the ruleset for main

We create a branch ruleset for `main`.

In **Settings**, open **Rules**, then **Rulesets**. Click **New ruleset**, then **New branch ruleset**. Set the fields as follows:

1. **Ruleset Name:** `Protect main`.
2. **Enforcement status:** **Active**.
3. **Bypass list:** leave it empty. The owner has no bypass, so the owner also goes through a pull request.
4. **Target branches:** click **Add target**, then **Include default branch**. The default branch is `main`.
5. **Branch rules**, turn on these rules:
   - **Restrict deletions.** Nobody can delete `main`.
   - **Block force pushes.** Nobody can rewrite the history of `main`.
   - **Require a pull request before merging.** Set **Required approvals** to `0`. Under **Allowed merge methods**, keep only **Squash**. This rule has no review requirement, because the course is solo work.
   - **Require status checks to pass.** Turn on **Require branches to be up to date before merging**. Click **Add checks**, search for `ci`, and select it. The search only finds a check that has run at least once on the repository. The lesson 1.10 pull request ran it, so `ci` appears.

Click **Create**.

Expected: green. The ruleset list now shows `Protect main` with status **Active**. Open the ruleset and check that the four rules are on and that `ci` is listed under the status checks.

## Step 6. Red: try to push straight to main

A rule that is not tested is not a rule. We create a local commit on a probe branch and push it to `main`. The push must fail.

Run from the repository root:

```powershell
git switch -c probe-direct-push main
git commit --allow-empty -m "Probe direct push"
git push origin probe-direct-push:main
git switch main
git branch -D probe-direct-push
```

Expected: red for the push. The `git push` line prints `! [remote rejected]` with a message from GitHub that the ruleset blocks the change. The remote `main` does not move. The last two commands switch back and delete the probe branch. The probe commit exists only on this computer, and it is gone after the delete.

Check that `main` on GitHub did not change:

```powershell
git fetch origin
git rev-parse main origin/main
```

Expected: both lines print the same commit hash.

## Step 7. Merge the lesson 1.10 pull request with squash

The `ci` check must now pass before a merge. We merge the pull request for lesson 1.10 through the new gate. Its branch holds one commit with the broken format and one revert. The squash merge puts one commit on `main`.

In the browser, open the pull request for `lesson-1.10`. In the Checks section, wait until `ci` shows a green check. If the box says the branch is out of date, click **Update branch**, wait for `ci` again, and continue. That is the strict rule at work.

When `ci` is green, click the merge button and choose **Squash and merge**. Confirm the merge. Then click **Delete branch**.

Run from the repository root:

```powershell
git switch main
git pull --ff-only
git branch -D lesson-1.10
```

Expected: the merge finishes in GitHub. `git pull --ff-only` moves local `main` to the new squash commit. The last command removes the local `lesson-1.10` branch. Git refuses the delete if the branch has commits that `main` lacks. That is not expected here, because the squash merge holds them.

## Step 8. Start lesson 1.11 on its own branch

We create the branch for this lesson from the updated `main`. We mark the lesson as started in the progress file, as lesson 1.10 did.

Run from the repository root:

```powershell
git switch -c lesson-1.11
```

In `docs/Progress.md`, change `- [ ] 1.11 GitHub repository setup: ...` to `- [~] 1.11 GitHub repository setup: ...`. Set "Current lesson" to 1.11, and add a row to the log with today's date. The log row names the lesson and says that it started.

Commit and push the branch:

```powershell
git add docs/Progress.md
git commit -m "Start lesson 1.11: repository settings and branch protection"
git push -u origin lesson-1.11
```

In the browser, GitHub shows a banner for the new branch. Click **Compare & pull request**. Set the title to `Repository settings: squash merges and branch protection`, and the description to `Squash merges only, and a ruleset on main that requires a pull request and the ci check.` Click **Create pull request**.

Expected: the push succeeds, because the ruleset blocks only `main`. The pull request opens, and its Checks section starts the `ci` check.

## Step 9. Green: wait for ci, then finish the lesson

We mark the lesson done in the progress file. Then we push, wait for `ci` to pass again, and merge the pull request with squash.

In the browser, on the lesson 1.11 pull request, wait until the `ci` check is green.

In `docs/Progress.md`, change `- [~] 1.11 ...` to `- [x] 1.11 ...`. Set "Current lesson" to 2.1, and add a log row that names the ruleset and the merge settings. Then run:

```powershell
git add docs/Progress.md
git commit -m "Finish lesson 1.11"
git push
```

In the browser, wait until `ci` is green on the new commit.

Merge the pull request: click the merge button, choose **Squash and merge**, confirm, then click **Delete branch**. Then run:

```powershell
git switch main
git pull --ff-only
git branch -D lesson-1.11
```

Expected: `main` now holds one squash commit for this lesson, and the local `lesson-1.11` branch is gone.

## Result

`main` accepts changes only through a pull request. The pull request merges only with a squash commit, and only when the `ci` check passes. The owner has no bypass. The direct push in step 6 was rejected, and the rules were checked on the real repository.

Settings and rules, set in the GitHub web interface, not in files:

- **Settings, General, Pull Requests:** squash merging only.
- **Settings, Rules, Rulesets:** `Protect main`, active, no bypass. It requires a pull request (no approvals, squash only), requires the `ci` check, requires the branch to be up to date, blocks force pushes, and restricts deletions.

Files added or changed in the repository:

- `docs/Progress.md` (lesson 1.11 marked `[x]`, with dated log rows)

# Lesson 1.3. Central package management: Directory.Packages.props

Previous: [1.2](1.2-central-build-settings.md) · Next: 1.4 Code style: `.editorconfig`, SonarAnalyzer, `dotnet format`

## Summary

We add one `Directory.Packages.props` file at the repository root. It turns on central package management, so every NuGet version lives in that one file and no project file carries a `Version`. We prove the rule with a probe project that is deleted again at the end. The first real package entries arrive in lesson 1.4 (SonarAnalyzer) and lesson 1.5 (xUnit v3 and AwesomeAssertions).

## The problem

Right now, the repository has shared build settings from lesson 1.2, but no rule for package versions. Without central package management:

- Each project file sets its own `Version` for each package. The Catalog, Reservation, and Customer services can then run different versions of the same library.
- A version bump needs edits in many `.csproj` files. Some projects get the update and others do not.
- Test projects can drift from the production projects. A test then passes against a library version that the service does not ship.

For BrickShare, [CLAUDE.md](../../CLAUDE.md) requires versions only in `Directory.Packages.props`. Never put `Version` on a `PackageReference`. [Architecture.md section 7.4](../Architecture.md#74-directorypackagesprops) shows the design. This lesson has no business rule from `docs/features/`.

The concept is NuGet central package management. A `Directory.Packages.props` file declares each version once as a `PackageVersion` item. Each project then declares only the package name in a `PackageReference`. With `CentralPackageTransitivePinningEnabled` set, the central version also applies to transitive packages, so the whole solution uses one version of each library.

## Step 1. Check the starting state

This step changes no files. It confirms that the repository is clean, the branch is `lesson-1.3`, and the SDK from lesson 1.1 is active.

Run from the repository root:

```powershell
git status
dotnet --version
```

Expected: `git status` reports a clean tree on branch `lesson-1.3`. `dotnet --version` prints a `10.0.x` version.

## Step 2. Create a probe project with a version in the project file

There are no projects with packages yet, so we use a small probe project. The probe lives in a `probe/` folder at the repository root. We delete it in step 5, before the commit.

The probe references AwesomeAssertions and puts the version in the project file. This is the pattern that the rule forbids.

`probe/PackageProbe/PackageProbe.csproj`

```xml
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>Library</OutputType>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="AwesomeAssertions" Version="9.6.0" />
  </ItemGroup>

</Project>
```

Run from the repository root:

```powershell
dotnet build probe/PackageProbe
```

Expected: green. The build restores AwesomeAssertions and reports `Build succeeded`. Nothing stops a version in a project file yet. That is the gap this lesson closes.

## Step 3. Turn on central package management and see the rule fail

We create `Directory.Packages.props` at the repository root with the .NET CLI. MSBuild finds it for every project below the root. The `packagesprops` template already turns on central version management. We add transitive pinning, so one version applies to the whole dependency graph.

Run from the repository root:

```powershell
dotnet new packagesprops
```

Expected: the CLI prints `The template "MSBuild Directory.Packages.props file" was created successfully.` and creates `Directory.Packages.props`. The file has `ManagePackageVersionsCentrally` set to `true` and an empty `ItemGroup`.

Add the transitive pinning setting to the `PropertyGroup`. The template's comment line can stay. The file then reads:

`Directory.Packages.props`

```xml
<Project>

  <PropertyGroup>
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
    <CentralPackageTransitivePinningEnabled>true</CentralPackageTransitivePinningEnabled>
  </PropertyGroup>

</Project>
```

What the settings do:

- `ManagePackageVersionsCentrally` set to `true` tells NuGet that versions come from this file. From now on, a `PackageReference` in a project must not carry a `Version`. NuGet reads the `PackageVersion` items below instead.
- `CentralPackageTransitivePinningEnabled` set to `true` applies the same central versions to transitive packages. A library that pulls in another library gets the version from this file too. Without it, a transitive package can resolve to a different version in each project.
- `PackageVersion` items, added in step 4, hold the version of each package. The `Include` attribute names the package, and the `Version` attribute sets its version.

For the full reference, see [Central Package Management](https://learn.microsoft.com/nuget/consume-packages/central-package-management).

The probe file does not change in this step. It still has `Version="4.2.1"` on its `PackageReference`.

Run from the repository root:

```powershell
dotnet build probe/PackageProbe
```

Expected: red. The restore fails with `error NU1008`. NuGet reports that projects that use central package version management must not define the version on `PackageReference` items. The rule works. The version must move to the central file.

## Step 4. Move the version to Directory.Packages.props

We move the version into one `PackageVersion` entry in the central file. The probe then declares only the package name.

`Directory.Packages.props`

```xml
<Project>

  <PropertyGroup>
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
    <CentralPackageTransitivePinningEnabled>true</CentralPackageTransitivePinningEnabled>
  </PropertyGroup>

  <ItemGroup>
    <PackageVersion Include="AwesomeAssertions" Version="9.0.0" />
  </ItemGroup>

</Project>
```

`probe/PackageProbe/PackageProbe.csproj`

```xml
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>Library</OutputType>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="AwesomeAssertions" />
  </ItemGroup>

</Project>
```

Run from the repository root:

```powershell
dotnet build probe/PackageProbe
```

Expected: green. The build restores AwesomeAssertions with the version from `Directory.Packages.props`. The probe file has no version, so the build now follows the rule.

## Step 5. Delete the probe and remove its package entry

The probe was only a check. It must not reach the repository. The AwesomeAssertions entry was needed only for the probe. Lesson 1.5 adds the test packages with their real use. We remove the `PackageVersion` entry and the `ItemGroup` that holds it, so the central file holds only the settings.

Run from the repository root:

```powershell
Remove-Item -Recurse -Force probe
```

`Directory.Packages.props`

```xml
<Project>

  <PropertyGroup>
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
    <CentralPackageTransitivePinningEnabled>true</CentralPackageTransitivePinningEnabled>
  </PropertyGroup>

</Project>
```

Run from the repository root:

```powershell
git status --short
```

Expected: `git status --short` lists one new file, `Directory.Packages.props`. It shows no `probe/` folder. The `bin/` and `obj/` folders that the probe created are already ignored by `.gitignore` from lesson 1.1, and they are gone with the probe.

## Step 6. Commit the central file

Commit the file on the `lesson-1.3` branch. Commit only this file.

Run:

```powershell
git add Directory.Packages.props
git commit -m "Add central package management"
```

Expected: Git reports one commit with one new file. `git status` then shows a clean tree.

## Result

What works now:

- `Directory.Packages.props` at the repository root turns on central package management for every project under the root.
- A `PackageReference` with a `Version` fails the restore with `NU1008`. Step 3 showed the failure, and step 4 showed the fix.
- The probe is removed. The solution still has no projects, and no packages are declared yet.

There are no tests yet. The first red-green cycle with a unit test starts in lesson 1.5. The first real `PackageVersion` entries arrive in lesson 1.4 (SonarAnalyzer) and lesson 1.5 (xUnit v3 and AwesomeAssertions).

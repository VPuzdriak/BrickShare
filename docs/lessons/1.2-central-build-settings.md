# Lesson 1.2. Central build settings: Directory.Build.props, nullable, warnings as errors

Previous: [1.1](1.1-repository-and-solution.md) · Next: 1.3 Central package management: `Directory.Packages.props`

## Summary

We add one `Directory.Build.props` file at the repository root. It sets the target framework to `net10.0`, turns on nullable reference types, and makes every warning a build error. Every project that the course adds later gets these settings without repeating them. At the end, a probe project shows that the file applies, and the probe is deleted again. The settings take effect when the first real projects arrive in lessons 1.5 and 2.1.

## The problem

Right now, the repository has a solution file and a `global.json`, but no build rules. Without shared build settings:

- Each project sets its own target framework, nullable mode, and warning level. Projects drift apart over time.
- Nullable warnings are only warnings. A null reference bug compiles and runs until it fails in production. Students learn to ignore the yellow text.
- A build with warnings passes. CI then accepts code that the author never reviewed.

For BrickShare, the rules in [CLAUDE.md](../../CLAUDE.md) say that shared build settings live in `Directory.Build.props`: net10.0, nullable, and warnings as errors. [Architecture.md section 7.3](../Architecture.md#73-directorybuildprops) gives the full file. This lesson has no business rule from `docs/features/`.

The concept is MSBuild's `Directory.Build.props` file. MSBuild reads the file automatically for every project in the folder tree below it. A project does not need to import it. We put the file at the root, so every project in `src/` and `tests/` gets the same settings.

The Architecture file lists more settings in 7.3, such as `ImplicitUsings`, `AnalysisLevel`, and `EnforceCodeStyleInBuild`. We add only the settings that the title promises. The analyzer and style settings arrive with SonarAnalyzer and `.editorconfig` in lesson 1.4.

## Step 1. Check the starting state

This step changes no files. It confirms that the repository is clean and that the SDK from lesson 1.1 is active.

Run from the repository root:

```powershell
git status
dotnet --version
```

Expected: `git status` reports a clean tree on the branch for this lesson, for example `lesson-1.2`. `dotnet --version` prints a `10.0.x` version.

## Step 2. Create a probe project and see it fail

There are no test projects until lesson 1.5, and no business rule to test. We use a small probe project to check the build settings. The probe lives in a `probe/` folder at the repository root. We delete it in step 6, before the commit.

The probe project file sets no target framework on purpose. Without `Directory.Build.props`, the SDK has nothing to use.

`probe/BuildProbe/BuildProbe.csproj`

```xml
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>Library</OutputType>
  </PropertyGroup>

</Project>
```

Run from the repository root:

```powershell
dotnet build probe/BuildProbe
```

Expected: red. The build fails with `error NETSDK1013: The TargetFramework value '' was not recognized.` The SDK reports the empty target framework because the project sets none. This failure is the reason for the shared settings file.

## Step 3. Add Directory.Build.props with the target framework and nullable

We create the shared file with the .NET CLI. The `buildprops` template writes an empty `Directory.Build.props` at the repository root. MSBuild finds it because it sits above the probe folder. Then we add the settings. The file sets `net10.0` for every project and turns on nullable reference types. We do not turn on warnings as errors yet. Step 4 adds that rule, so each rule can be seen on its own.

Run from the repository root:

```powershell
dotnet new buildprops
```

Expected: the CLI prints `The template "MSBuild Directory.Build.props file" was created successfully.` and creates `Directory.Build.props` with an empty `PropertyGroup`.

Put the two settings in the `PropertyGroup`. The template's comment line can stay. The file then reads:

`Directory.Build.props`

```xml
<Project>

  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <Nullable>enable</Nullable>
  </PropertyGroup>

</Project>
```

The probe now needs code that breaks the nullable rule. Add this class to the probe. It dereferences a `string?` without a null check.

`probe/BuildProbe/Probe.cs`

```csharp
namespace BuildProbe;

public static class Probe
{
    public static int Length(string? text) => text.Length;
}
```

Run from the repository root:

```powershell
dotnet build probe/BuildProbe
```

Expected: the build succeeds and prints a warning `CS8602: Dereference of a possibly null reference.` The warning is still a warning, so this result is red for the rule we want. Without step 3, the same code would build without any warning.

## Step 4. Treat warnings as errors

We add the rule that turns every warning into a build error. This is the line that makes the nullable warning fail the build. The full file is shown, with one new line in the `PropertyGroup`.

`Directory.Build.props`

```xml
<Project>

  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <Nullable>enable</Nullable>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
  </PropertyGroup>

</Project>
```

Run from the repository root:

```powershell
dotnet build probe/BuildProbe
```

Expected: red. The build fails with `error CS8602: Dereference of a possibly null reference.` The rule works. The probe still contains the bad code, so the build must fail.

## Step 5. Fix the probe and get a green build

We fix the code and do not suppress the warning. The shared rule forbids `#pragma` or `[SuppressMessage]` without a justification comment. The fix is a null check in the code itself. The expression uses `?.` and `??` to return 0 for a null input.

`probe/BuildProbe/Probe.cs`

```csharp
namespace BuildProbe;

public static class Probe
{
    public static int Length(string? text) => text?.Length ?? 0;
}
```

Run from the repository root:

```powershell
dotnet build probe/BuildProbe
```

Expected: green. The build reports `Build succeeded` with no warnings and no errors.

## Step 6. Delete the probe and commit the settings

The probe was only a check. It must not reach the repository. The `bin/` and `obj/` folders that the probe created are already ignored by `.gitignore` from lesson 1.1.

Run from the repository root:

```powershell
Remove-Item -Recurse -Force probe
git status --short
```

Expected: `git status --short` lists one new file, `Directory.Build.props`. It shows no `probe/` folder.

Commit the file:

```powershell
git add Directory.Build.props
git commit -m "Add shared build settings"
```

Expected: Git reports one commit with one new file. `git status` then shows a clean tree.

## Result

What works now:

- `Directory.Build.props` at the repository root sets `net10.0`, nullable reference types, and warnings as errors for every project under the root.
- A nullable warning fails the build. Step 4 showed the failure, and step 5 showed the fix.
- The probe is removed. The solution still has no projects.

There are no tests yet. The first red-green cycle with a unit test starts in lesson 1.5. The settings apply to the test projects from that lesson on.

# Lesson 2.6c. Update a set: `Update`, `PUT /catalog/sets/{id}`, `404` as `ProblemDetails`

Features: [F01](../features/01-catalog-management.md)
Previous: [2.6b](2.6b-validation-with-fluentvalidation.md) · Next: [2.6d](2.6d-deactivate-a-set.md) Deactivate a set: `Deactivate`, `DELETE /catalog/sets/{id}`, shared `ProblemDetails`

## Summary

We add `LegoSet.Update`, the endpoint `PUT /catalog/sets/{id}`, and a `404` `ProblemDetails` for a set that does not exist. The update reuses the validation filter from lesson 2.6b. At the end an admin can change a set and the stored row shows the change, an employee gets `403`, and an invalid request gets `400`. The test support class `SetTestData` seeds the sets that the tests need.

## The problem

A set is created in lesson 2.6a, but nothing changes it later. The endpoint table in [Architecture.md section 3.2](../Architecture.md#32-catalog-service) lists `PUT /catalog/sets/{id}` with the policy `AdminOnly` and the purpose "Update set". The [catalog management](../features/01-catalog-management.md#sets) rules still apply to a changed set:

- "Catalog gives every set and instance its own id. APIs, events, and other services use only these ids." So the route takes the Catalog id, not the number on the box and not the Rebrickable reference.
- "The LEGO set number is digits only." The same rule applies on update.
- "Minimum rental days ... is any whole number greater than 0."

The rules for a set do not change on update, so the request goes through the same validator as create. Lesson 2.6b wrote that validator once.

The rule that matters is who changes a set. Only the aggregate changes its own state. The endpoint loads the set, calls `Update`, and saves. It does not assign the properties itself. A new set gets its fields in the constructor. An existing set gets them through `Update`. The two methods are separate, even though they assign the same fields.

The concepts we introduce:

- **Aggregate method.** `Update` is a public method. The properties keep private setters, so the handler cannot change a set without going through the aggregate.
- **Typed results.** The handler returns `Results<Ok<SetResponse>, ProblemHttpResult>`. The compiler then lists both outcomes, `200` and `404`.
- **Missing set.** An unknown id returns `404` as `ProblemDetails`, not as an empty body. The client gets the same error format as for validation.

`Update` does not change the active flag. Deactivating a set is lesson 2.6d.

## Step 6. Green: the update slice and the route

The update slice loads the set, applies the request, and saves. A missing set returns `ProblemDetails` with status `404`. The return type lists the two outcomes, so the compiler checks both.

`src/Services/Catalog/BrickShare.Catalog.Api/Features/Sets/Update/UpdateSet.cs` (new file)

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

using BrickShare.Catalog.Api.Infrastructure.Persistence;
using BrickShare.Catalog.Api.Infrastructure.Validation;

using Microsoft.AspNetCore.Builder;
using Microsoft.AspNetCore.Http;
using Microsoft.AspNetCore.Http.HttpResults;
using Microsoft.AspNetCore.Routing;

namespace BrickShare.Catalog.Api.Features.Sets.Update;

public static class UpdateSet
{
    public static void MapUpdateSet(this RouteGroupBuilder sets) =>
        sets.MapPut("/{id:guid}", Handle).AddEndpointFilter<ValidationFilter<SetRequest>>();

    private static async Task<Results<Ok<SetResponse>, ProblemHttpResult>> Handle(
        Guid id, SetRequest request, CatalogDbContext dbContext, CancellationToken cancellationToken)
    {
        var legoSet = await dbContext.LegoSets.FindAsync([id], cancellationToken);

        if (legoSet is null)
        {
            return TypedResults.Problem(
                title: "Set not found",
                detail: $"No set with id {id} exists.",
                statusCode: StatusCodes.Status404NotFound);
        }

        request.ApplyTo(legoSet);
        await dbContext.SaveChangesAsync(cancellationToken);

        return TypedResults.Ok(SetResponse.From(legoSet));
    }
}
```

The group maps the update route next to the create route. The `RequireAuthorization` call on the group already applies `AdminOnly` to the new route, so the route needs no policy of its own.

The request goes through the same validation filter as create, so the same rules apply, and an invalid request gets `400` as `ProblemDetails`. A set that does not exist returns `404` as `ProblemDetails`. The aggregate changes its own state through `Update`, and the active flag is not touched.

# Lesson 2.6b. Validation with FluentValidation and `ProblemDetails` for create

Features: [F01](../features/01-catalog-management.md)
Previous: [2.6a](2.6a-create-a-set.md) · Next: [2.6c](2.6c-update-a-set.md) Update a set: `Update`, `PUT /catalog/sets/{id}`, `404` as `ProblemDetails`

## Summary

We check the create request with a FluentValidation validator. An endpoint filter runs it before the handler, so a bad request gets `400` with `ProblemDetails`, and the `errors` object names the field. An empty name and a set number with a suffix are rejected before the aggregate is built. Unhandled exceptions also get a `ProblemDetails` body, but no test in this lesson reaches that path. At the end the create tests are green.

## The problem

Lesson 2.6a accepts any request. Two cases are wrong:

- An empty name is stored. [Catalog management](../features/01-catalog-management.md#sets) says a set has a name, so the endpoint must refuse a missing one.
- A set number with a suffix such as `10294-1` reaches `LegoSetNumber`, which throws `ArgumentException`. The request fails on the server instead of returning a client error. The feature doc says: "The LEGO set number is digits only. `10294-1` is not a LEGO set number: the `-1` suffix is part of the Rebrickable reference."

The fix is a check at the edge, before the handler runs. The rules are written once in a validator class. A filter runs the validator for the create endpoint. The decisions summary in [Architecture.md](../Architecture.md) asks for request validation at the endpoint, and RFC 9457 `ProblemDetails` for every error. This lesson follows both.

The concepts we introduce:

- **FluentValidation.** A class that inherits `AbstractValidator<T>` states the rules with `RuleFor`. The validator runs on a request object and returns the failures. The request needs no attributes, so it stays a plain record.
- **Endpoint filter.** An `IEndpointFilter` runs after the framework binds the body and before the handler. The generic `ValidationFilter<T>` resolves `IValidator<T>` from the container. The create route adds it with one call to `AddEndpointFilter`.
- **`ProblemDetails`.** The response has the content type `application/problem+json`. `AddProblemDetails` and `UseExceptionHandler` make an unhandled exception return the same format.

`src/Services/Catalog/BrickShare.Catalog.Api/Features/Sets/SetRequestValidator.cs` (new file)

```csharp
using FluentValidation;

namespace BrickShare.Catalog.Api.Features.Sets;

public sealed class SetRequestValidator : AbstractValidator<SetRequest>
{
    public SetRequestValidator()
    {
        RuleFor(request => request.LegoSetNumber)
            .NotEmpty()
            .Matches(@"\A[0-9]+\z");

        RuleFor(request => request.Name)
            .NotEmpty();

        RuleFor(request => request.MinRentalDays)
            .GreaterThanOrEqualTo(1);

        RuleFor(request => request.DailyPrice)
            .GreaterThanOrEqualTo(0);

        RuleFor(request => request.Deposit)
            .GreaterThanOrEqualTo(0);

        RuleFor(request => request.ReplacementValue)
            .GreaterThanOrEqualTo(0);

        RuleFor(request => request.LateFeePerDay)
            .GreaterThanOrEqualTo(0);
    }
}
```

The pattern uses `\A` and `\z`, not `^` and `$`. In .NET, `$` also matches before a final newline. The value `"10294\n"` would pass a `$` pattern, and then the value object would throw.

## Step 4. Green: the filter runs the validator

The filter runs after the framework binds the body and before the handler. It asks the container for the `IValidator<T>` of the request type and runs it. When a rule fails, it returns `TypedResults.ValidationProblem`. That is `400` with a `ProblemDetails` body and an `errors` object. The keys use the camel-case names that the client sends. The filter has no constructor parameters, so the container creates it.

`src/Services/Catalog/BrickShare.Catalog.Api/Infrastructure/Validation/ValidationFilter.cs` (new file)

```csharp
using System.Linq;
using System.Text.Json;
using System.Threading.Tasks;

using FluentValidation;

using Microsoft.AspNetCore.Http;
using Microsoft.Extensions.DependencyInjection;

namespace BrickShare.Catalog.Api.Infrastructure.Validation;

public sealed class ValidationFilter<T> : IEndpointFilter
{
    public async ValueTask<object?> InvokeAsync(EndpointFilterInvocationContext context, EndpointFilterDelegate next)
    {
        var request = context.Arguments.OfType<T>().FirstOrDefault();

        if (request is null)
        {
            return await next(context);
        }

        var validator = context.HttpContext.RequestServices.GetRequiredService<IValidator<T>>();
        var result = await validator.ValidateAsync(request, context.HttpContext.RequestAborted);

        if (result.IsValid)
        {
            return await next(context);
        }

        var errors = result.Errors
            .GroupBy(
                failure => JsonNamingPolicy.CamelCase.ConvertName(failure.PropertyName ?? string.Empty),
                failure => failure.ErrorMessage)
            .ToDictionary(group => group.Key, group => group.ToArray());

        return TypedResults.ValidationProblem(errors);
    }
}
```

The create route gets the filter. The `Handle` method does not change.

## Step 5. Green: `ProblemDetails` for unhandled exceptions

Validation errors already use `ProblemDetails` after step 4. This step makes every other error use it too. `AddProblemDetails` registers the default writer, and `UseExceptionHandler` catches an unhandled exception and writes the response with it. Without these two calls, an unhandled exception returns a body that is not `ProblemDetails`.

No test in this lesson reaches this path. Validation stops every bad create before the handler runs, so the create path does not throw for bad input. The first endpoint that can throw on a valid request gets its test then.

# Lesson 2.8f. Adapter: Rebrickable failure raises `SetSpecificationUnavailableException`, test-first

Features: [F01](../features/01-catalog-management.md#lookup-in-rebrickable)
Previous: [2.8e](2.8e-specification-cache.md) · Next: [2.8g](2.8g-wire-adapter-and-api-key.md)

## Summary

When Rebrickable fails, the adapter throws `SetSpecificationUnavailableException`. The domain owns this exception, so the endpoint does not depend on HTTP types. At the end the adapter has four green tests.

## The problem

[Catalog management](../features/01-catalog-management.md#lookup-in-rebrickable) now says: "If Rebrickable is down, slow, or still failing after the retries, the lookup returns `503`." The endpoint must know that Rebrickable is unavailable, but it must not know about `HttpRequestException` or the resilience library. The port is the right place for that contract. The port throws a domain exception, and lesson 2.8j maps it to `503`.

This lesson catches `HttpRequestException`. Lesson 2.8g adds the resilience exceptions, once the package is installed.

## Step 3. Red: a failing Rebrickable raises the domain exception

The stub gets a switch that makes every request fail with `500`. The adapter currently lets the `HttpRequestException` escape, so the test fails.

`tests/Services/Catalog/BrickShare.Catalog.Api.Tests/RebrickableStub.cs` (add this field, this method, and the check at the start of `SendAsync`)

Add this field after `_responses`:

```csharp
    private bool _unavailable;
```

Add this method after `Respond`:

```csharp
    public RebrickableStub Unavailable()
    {
        _unavailable = true;
        return this;
    }
```

Add this check as the first line of `SendAsync`:

```csharp
        if (_unavailable)
        {
            return Task.FromResult(new HttpResponseMessage(HttpStatusCode.InternalServerError));
        }
```

`tests/Services/Catalog/BrickShare.Catalog.Api.Tests/RebrickableSetSpecificationProviderTests.cs` (add this test after `FindAsync_answers_a_repeated_lookup_from_the_cache`)

```csharp
    [Fact]
    public async Task FindAsync_raises_unavailable_when_rebrickable_fails()
    {
        var provider = CreateProvider(new RebrickableStub().Unavailable());

        Func<Task> act = () => provider.FindAsync(
            RebrickableSetNumber.Parse("10294").Value, TestContext.Current.CancellationToken);

        await act.Should().ThrowAsync<SetSpecificationUnavailableException>();
    }
```

## Step 4. Green: wrap the Rebrickable failure

The public `FindAsync` now catches `HttpRequestException` and throws the domain exception. The old method body moves to a private method with the same logic, so the cache and the mapping stay unchanged.

`src/Services/Catalog/BrickShare.Catalog.Api/Infrastructure/Rebrickable/RebrickableSetSpecificationProvider.cs` (rename the existing `FindAsync` method to `FindFromRebrickableAsync` and make it private, then add the new `FindAsync` above it)

Add this method above the renamed method:

```csharp
    public async Task<SetSpecification?> FindAsync(RebrickableSetNumber setNumber, CancellationToken cancellationToken)
    {
        try
        {
            return await FindFromRebrickableAsync(setNumber, cancellationToken);
        }
        catch (HttpRequestException exception)
        {
            throw new SetSpecificationUnavailableException("Rebrickable is unavailable.", exception);
        }
    }
```

Change the renamed method's signature to:

```csharp
    private async Task<SetSpecification?> FindFromRebrickableAsync(RebrickableSetNumber setNumber, CancellationToken cancellationToken)
```

Its body stays as it is.

Run from the repository root:

```powershell
dotnet test --project tests/Services/Catalog/BrickShare.Catalog.Api.Tests --filter-class "*RebrickableSetSpecificationProviderTests"
```

Expected: green. All four adapter tests pass: the mapping, the `null` for an unknown set, the cache, and the unavailable case.

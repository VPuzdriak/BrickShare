# Lesson 3.2. docker compose: PostgreSQL, Azurite, Catalog Service

Previous: [3.1](3.1-multi-stage-dockerfile.md) · Next: 3.3 Configuration through environment variables, `docker-compose.override.yml`, init scripts

## Summary

We add a `docker-compose.yml` at the repository root with three services: PostgreSQL, Azurite, and the Catalog Api image from lesson 3.1. One command starts all three. The Catalog container reaches PostgreSQL and Azurite by their service names, and its liveness check answers 200 on `http://localhost:8080/health/live`.

## The problem

Lesson 3.1 gives us a Catalog image, but the image needs two other things to run in the same environment: a PostgreSQL database and a Blob Storage endpoint. Without compose, each developer starts these by hand, with their own ports and their own commands. [Architecture 8](../Architecture.md#8-local-development) sets the rule:

> `docker compose up` starts all services and their dependencies.

The table in that section names the containers for this lesson:

- `postgres`, image `postgres:18`, for the `catalog` database.
- `azurite`, image `mcr.microsoft.com/azure-storage/azurite`, for Blob Storage.
- The Catalog Api, built from the Dockerfile of lesson 3.1.

Concepts this lesson introduces:

- **Service names are host names.** Compose puts all services on one network. Each service is reachable by its name. Inside the Catalog container, `localhost` means the Catalog container itself, so the connection string must say `Host=postgres`, not `Host=localhost`.
- **Start order is not readiness.** `depends_on` with a plain name waits only for the container to start. A PostgreSQL container starts before the server accepts connections. A health check and `depends_on` with `condition: service_healthy` wait for the server.
- **Named volumes.** A volume keeps the PostgreSQL and Azurite data when the containers stop. `docker compose down` removes the containers and keeps the volume. `docker compose down -v` removes the volume too.
- **Port binding.** `127.0.0.1:5432:5432` publishes the port to this machine only. Other machines on the network cannot reach the database.

Two decisions in this lesson follow from [CLAUDE.md](../../CLAUDE.md):

- The PostgreSQL container uses `trust` authentication, so the repository holds no database password. The port binds to `127.0.0.1`, so only this machine reaches it. This is for local development only. Azure uses Entra authentication, set up in [lesson 13.4](../CoursePlan.md#13-azure-infrastructure-with-terraform).
- The Rebrickable key is a placeholder in this lesson. It is not a secret, and it satisfies the startup check in `Program.cs`. Set lookups need a real key. Lesson 3.3 moves the settings out of the compose file.

No feature doc sets a business rule for this lesson, so there is no unit test to write first. The checks are run steps, as in lesson 3.1. Each one ends with red or green.

The Api tests do not use compose. [Architecture 8](../Architecture.md#8-local-development) says the integration tests use Testcontainers. The tests still run at the end of this lesson to confirm nothing else broke.

## Step 3. Green: the PostgreSQL service

The first version of the file has one service. The database is named `catalog`, so `POSTGRES_DB` creates it on first start. The volume holds the data, so the database survives a `docker compose down`. The `postgres:18` image expects the volume at `/var/lib/postgresql`, not at `/var/lib/postgresql/data`. It stores the data in a `18/docker` subfolder of the volume.

`docker-compose.yml`

```yaml
services:
  postgres:
    image: postgres:18
    environment:
      POSTGRES_DB: catalog
      POSTGRES_HOST_AUTH_METHOD: trust
    ports:
      - "127.0.0.1:5432:5432"
    volumes:
      - postgres-data:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d catalog"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  postgres-data:
```

Run from the repository root:

```powershell
docker compose up -d postgres
docker compose exec postgres pg_isready -U postgres -d catalog
docker compose ps postgres
```

Expected: green. The `pg_isready` line ends with `accepting connections`. After a few seconds, the `docker compose ps` row shows `(healthy)` in the status column. If it shows `(health: starting)`, wait a few seconds and run the command again.

Failure guide: if the container exits with `in 18+, these Docker images are configured to store database data in a...`, the `postgres-data` volume holds data from PostgreSQL 17, which used the old mount point. Run `docker compose down -v` once to delete that volume, then run the step again. The database is empty after that.

Failure guide: if the `up` command fails with `port is already allocated` on 5432, another PostgreSQL runs on this machine. Stop it, or change the left side of the port mapping to a free port, for example `127.0.0.1:5433:5432`. The Catalog Api still uses port 5432 inside compose, so only your own tools on this machine see the change.

## Step 4. Green: the Azurite service

Add the `azurite` service after the `postgres` block and before the `volumes:` line. The command starts only the Blob service, which is the one the Catalog Api uses. The host address `0.0.0.0` lets the other containers reach it. The published port matches the local setting `http://127.0.0.1:10000/devstoreaccount1` in `appsettings.Development.json`. The `--location /data` option stores the blobs in `/data`, and the volume mounts that folder. The image's default command also sets `/data`, but this command replaces the default, so the option must be given here.

`docker-compose.yml`

Add this block after the `postgres` block. Nothing is replaced.

```yaml
  azurite:
    image: mcr.microsoft.com/azure-storage/azurite
    command: azurite-blob --blobHost 0.0.0.0 --location /data
    ports:
      - "127.0.0.1:10000:10000"
    volumes:
      - azurite-data:/data
```

Then add the `azurite-data` volume under the top-level `volumes:` key, below `postgres-data`:

```yaml
volumes:
  postgres-data:
  azurite-data:
```

Run from the repository root:

```powershell
docker compose up -d azurite
docker compose logs azurite
```

Expected: green. The log contains the line `Azurite Blob service successfully listens on http://0.0.0.0:10000`.

Azurite keeps its blobs in the `azurite-data` volume, so they survive `docker compose down`, as the PostgreSQL data does. Durable Functions later use the same Azurite store for their state, so the blobs must not be lost between runs.

## Step 5. Green: the Catalog Api service

Add the `catalog-api` service after the `azurite` block and before the `volumes:` line. It builds from the Dockerfile of lesson 3.1. The build context is the repository root, which is the folder of this file, so `context: .` is correct. The three settings are the same ones lesson 3.1 passed with `docker run -e`. Inside compose, the database and the blob endpoint use service names, not `localhost`.

The `depends_on` block waits for the PostgreSQL health check from step 3. It waits only for the Azurite container to start, because Azurite has no health check here.

`docker-compose.yml`

Add this block after the `azurite` block. Nothing is replaced.

```yaml
  catalog-api:
    build:
      context: .
      dockerfile: src/Services/Catalog/BrickShare.Catalog.Api/Dockerfile
    image: brickshare-catalog-api:local
    environment:
      ConnectionStrings__catalog: "Host=postgres;Database=catalog;Username=postgres"
      Rebrickable__ApiKey: placeholder-for-lesson-3-2
      Storage__BlobServiceUri: "http://azurite:10000/devstoreaccount1"
    ports:
      - "8080:8080"
    depends_on:
      postgres:
        condition: service_healthy
      azurite:
        condition: service_started
```

Run from the repository root:

```powershell
docker compose up -d --build
docker compose ps
```

Expected: green. The build reuses the layers from lesson 3.1 where it can, so it is quick if you built that image before. `docker compose ps` lists three services: `postgres` (`healthy`), `azurite` (`Up`), and `catalog-api` (`Up`).

Failure guide: if `catalog-api` exits at once, run `docker compose logs catalog-api`. The message names the missing or misspelled setting. The three settings in this block match the three checks in `Program.cs`. If the build fails with a restore or analyzer error, the same error appears in the local build. Fix it in the code, not in the compose file.

## Step 6. Green: the Catalog Api answers its liveness check

Run from the repository root:

```powershell
Invoke-WebRequest -UseBasicParsing -Uri http://localhost:8080/health/live | Select-Object StatusCode
```

Expected: green. `StatusCode` is `200`. The liveness check runs no database, Rebrickable, or Blob Storage call, so this check passes even though the database has no tables yet. Later lessons add the migrations and the checks that reach the database.

## Step 7. Stop the stack

Stop the containers and remove the network. The `postgres-data` and `azurite-data` volumes stay.

```powershell
docker compose down
```

Expected: green. The output lists the three containers and the network as removed. Run `docker compose up -d` again to start them with the same database data.

Failure guide: `docker compose down -v` also deletes the `postgres-data` and `azurite-data` volumes. Use it only when you want an empty database and no blobs.

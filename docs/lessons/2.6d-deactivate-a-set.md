# Lesson 2.6d. Deactivate a set: `Deactivate`, `DELETE /catalog/sets/{id}`, shared `ProblemDetails`

Features: [F01](../features/01-catalog-management.md)
Previous: [2.6c](2.6c-update-a-set.md) · Next: 2.6e Test isolation: Respawn resets, one shared PostgreSQL container for the Catalog tests

## Summary

We add `LegoSet.Deactivate`, the endpoint `DELETE /catalog/sets/{id}`, and a shared helper for the `404` `ProblemDetails`. Deactivating keeps the row and sets `IsActive` to `false`. The update and the deactivate handlers return the same `404` from `SetProblems`. At the end the set endpoints are complete: create, update, and deactivate.

## The problem

[Catalog management](../features/01-catalog-management.md#sets) says: "Deleting a set is a soft delete (deactivate)." A hard delete would remove the row. Other parts of the system refer to a set by its Catalog id, because "APIs, events, and other services use only these ids." A removed row would leave those references without a set. So `DELETE` sets a flag, and the row stays.

The [endpoint table](../features/01-catalog-management.md#endpoints) lists `DELETE /catalog/sets/{id}` with the policy `AdminOnly` and the purpose "Deactivate set (soft delete)". The feature doc has no rule for a second `DELETE` on a set that is already inactive. HTTP defines `DELETE` as idempotent (RFC 9110): the same request twice leaves the server in the same state. So the second call succeeds with `204` and changes nothing.

The concepts we introduce:

- **Soft delete.** `Deactivate` changes one flag. The setter stays private, so only the aggregate changes `IsActive`.
- **Idempotent delete.** A second call on an inactive set returns `204`. It does not fail.
- **Shared problem result.** The `404` body lives in one method, `SetProblems.NotFound`. The update and the deactivate handlers both call it.

This lesson publishes no event. The architecture lists `SetCreated` and `SetUpdated` only, so a deactivation event is not defined yet.

## Step 5. Green: the deactivate slice and the route

The handler loads the set, calls `Deactivate`, and saves. A missing set returns `404` as `ProblemDetails`. The return type lists the two outcomes, so the compiler checks both. The `404` body is written inline here, and step 6 moves it to a shared place.

`src/Services/Catalog/BrickShare.Catalog.Api/Features/Sets/Deactivate/DeactivateSet.cs` (new file)

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

using BrickShare.Catalog.Api.Infrastructure.Persistence;

using Microsoft.AspNetCore.Builder;
using Microsoft.AspNetCore.Http;
using Microsoft.AspNetCore.Http.HttpResults;
using Microsoft.AspNetCore.Routing;

namespace BrickShare.Catalog.Api.Features.Sets.Deactivate;

public static class DeactivateSet
{
    public static void MapDeactivateSet(this RouteGroupBuilder sets) =>
        sets.MapDelete("/{id:guid}", Handle);

    private static async Task<Results<NoContent, ProblemHttpResult>> Handle(
        Guid id, CatalogDbContext dbContext, CancellationToken cancellationToken)
    {
        var legoSet = await dbContext.LegoSets.FindAsync([id], cancellationToken);

        if (legoSet is null)
        {
            return TypedResults.Problem(
                title: "Set not found",
                detail: $"No set with id {id} exists.",
                statusCode: StatusCodes.Status404NotFound);
        }

        legoSet.Deactivate();
        await dbContext.SaveChangesAsync(cancellationToken);

        return TypedResults.NoContent();
    }
}
```

The group maps the third route. The `RequireAuthorization` call on the group already applies `AdminOnly`, so the new route needs no policy of its own.

## Result

The set endpoints are complete. Under the `AdminOnly` policy:

- `POST /catalog/sets` creates a set and returns `201`.
- `PUT /catalog/sets/{id}` replaces the details and returns `200`.
- `DELETE /catalog/sets/{id}` deactivates the set and returns `204`. The row stays in the database, and a second call also returns `204`.

An unknown id returns `404` as `ProblemDetails` for both `PUT` and `DELETE`. A bad request returns `400` as `ProblemDetails` for `POST` and `PUT`.

Not in this lesson: a deactivation event, and a rule that blocks an update of an inactive set. The feature docs have no rule for either. The architecture lists no event for deactivation.

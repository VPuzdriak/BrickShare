# Lesson 4.2. External ID tenant: customer user flow with e-mail OTP, Google, and Facebook

Features: [F03](../features/03-customer-accounts.md)
Previous: [4.1](4.1-workforce-tenant-app-registration.md) · Next: 4.3 `BrickShare.Auth`: `Staff` and `Customer` schemes, policy scheme by issuer, role claim mapping

## Summary

We create a Microsoft Entra External ID tenant for customers, in the Azure portal. The tenant holds the `BrickShare API` app registration with the scope `api.access`, and it issues version 2 tokens. A customer signs up or signs in with an e-mail one-time passcode, Google, or Facebook through one user flow. At the end the configuration matches the checklist in the Result section, and no repository file has changed except the progress file. Lesson 4.3 reads the issuer and the client id of this tenant.

## The problem

Customers have no identity yet. The Catalog Service accepts tokens only from `dotnet user-jwts` (lesson 2.5). [Customer accounts](../features/03-customer-accounts.md) needs real sign-in:

- "Customers sign in with e-mail one-time passcode, Google, or Facebook through Microsoft Entra External ID."
- "The user id is always the `oid` claim. Customer-facing endpoints never take a customer id from the route. They read it from the token."

[Architecture 5.1](../Architecture.md#51-tenants-and-app-registrations) names the objects in the External ID tenant: the `BrickShare API` app registration with the scope `api.access`, and the user flow with e-mail one-time passcode, Google, and Facebook. The customer client app comes later, in lesson 4.4. Development and Test share this tenant.

The concepts we introduce:

- **External ID tenant.** A customer tenant is separate from the workforce tenant of lesson 4.1. Customers never see the staff tenant, and staff never see the customer tenant. The tenant has its own issuer and its own discovery document.
- **Identity provider.** A source of sign-in. E-mail one-time passcode is built in. Google and Facebook are federated: the user signs in at Google or Facebook, and Entra ID trusts the answer. Each federated provider needs an app in its own developer console.
- **User flow.** The sign-up and sign-in journey. It lists the identity providers that users can pick, and the attributes it collects. The flow is linked to the API, so tokens for the API come from this flow.
- **Token version 2 and the issuer.** [Architecture 5.2](../Architecture.md#52-token-validation-in-aspnet-core) says the API requests version 2 tokens. The issuer of a token must match the `Customer` scheme in lesson 4.3. Step 5 reads the issuer from the tenant itself, so the value is not guessed.
- **No app roles here.** The `Customer` scheme adds the role `Customer` when a token is validated (lesson 4.3). Customers get no app role in the tenant, so this lesson creates no roles.

Scope decisions:

- **Azure portal, done once by hand.** [Architecture 9.1](../Architecture.md#91-infrastructure-as-code-with-terraform) puts Azure resources in Terraform. The customer tenant is the same exception as the workforce app in lesson 4.1. Lesson 13.7 imports these objects with the `azuread` provider, so this lesson records their ids.
- **Client secrets stay in the portal.** The Google and Facebook client secrets go only into the Entra form. They are not written in notes or in the repository. [Architecture 5.4](../Architecture.md#54-service-identities) keeps secrets in Key Vault. Key Vault comes with module 13, and this lesson does not move the secrets there.
- **One customer tenant for Development and Test.** The architecture shares tenants between these environments. Production gets its own tenant later.
- **No client app yet.** Nothing in this lesson signs in through our own app. The check uses the user flow page in the portal.

No feature rule can become a unit test before the API checks tokens. This lesson writes no production code and no test. Its checks are portal views and one public discovery document, and each one ends with red or green.

## Step 1. Check the starting state and sign in to the portal

Run from the repository root:

```powershell
git status
git branch --show-current
```

Expected: `git status` shows no changes. The branch is `lesson-4.2`.

Open the Microsoft Entra admin center at `https://entra.microsoft.com`. Sign in with the account that you used in lesson 4.1. To create an external tenant, the account needs the Tenant Creator role or the Global Administrator role. Creating the tenant from the Azure subscription route also needs the Contributor role on a subscription. See [Quickstart: Create a tenant](https://learn.microsoft.com/entra/external-id/customers/quickstart-tenant-setup) if the portal asks for another role.

Mark lesson 4.2 as `[~]` in `docs/Progress.md`, and set "Current lesson" to 4.2. Add a dated line to the log.

## Step 2. Red: the customer tenant does not exist yet

Open Identity, then Overview, then Manage tenants.

Expected: red. The list shows only the workforce tenant from lesson 4.1. If a tenant named `BrickShare Customers` already exists, an earlier attempt created it. Use that tenant and check the settings in the next steps. Do not create a second one.

## Step 3. Create the external tenant

On Manage tenants, select Create, then select External, then Continue. Fill in the basics:

- Tenant name: `BrickShare Customers`
- Domain name: a short name, lowercase, with letters and digits only. A hyphen is not accepted. Choose one that no other tenant uses, for example `bricksharecustomers`, with a number at the end if the name is taken.
- Subscription: the Azure subscription that the account can use. The account needs at least the Contributor role on it. If the account has no subscription, choose the free trial option instead, if the portal offers it.
- Resource group: create a new one, for example `rg-brickshare-customers`, or pick an existing group in the same subscription. The resource group is a container in Azure. It holds no BrickShare code and no Terraform state in this lesson.

Leave the other fields at their defaults unless the portal asks for a required value. Select Create. Tenant creation can take up to 30 minutes. Progress shows in the Notifications pane.

Expected: green when Manage tenants lists `BrickShare Customers`, with the tenant type External. Write the domain name in your notes. Lesson 4.3 and the discovery check in step 5 use it.

## Step 4. Switch to the customer tenant and record its ids

Open the account menu, select Switch directory, then select `BrickShare Customers`. Open Identity, then Overview.

Copy two values into your notes:

- Tenant ID. This is the GUID on the Overview page.
- Primary domain. It has the form `<domain name>.onmicrosoft.com`.

Expected: green. Overview shows the tenant name `BrickShare Customers`, the Tenant ID, and a primary domain that ends with `.onmicrosoft.com`. Do not save the values in a repository file. They are not secrets, and lesson 4.3 reads them from configuration.

## Step 5. Record the issuer from the discovery document

Open a new browser tab and go to this address. Replace `<domain name>` with the first part of the primary domain, and `<tenant id>` with the Tenant ID:

```text
https://<domain name>.ciamlogin.com/<tenant id>/v2.0/.well-known/openid-configuration
```

The host uses the domain name, not the tenant id. The Run user flow page in step 12 shows the same pattern, `https://<domain name>.ciamlogin.com/<tenant id>/v2.0/.well-known/openid-configuration`.

Expected: green. The page shows a JSON document. Find the `issuer` value and copy it exactly as it is written. It ends with `/v2.0`, which means the tenant issues version 2 tokens. Lesson 4.3 sets this value as the valid issuer of the `Customer` scheme.

If the page shows an error after a few minutes, the tenant is still provisioning. Wait and try again. Do not guess the issuer.

## Step 6. Check the e-mail one-time passcode provider

In the customer tenant, open External Identities, then All identity providers.

Find Email one-time passcode in the list. Check that it is enabled. If it is not, open it, enable it, and save.

Expected: green. Email one-time passcode is listed as enabled. This is the first sign-in option for the user flow in step 11.

## Step 7. Add Google as an identity provider

In the Google Cloud console, create an OAuth client for a web application. Configure the OAuth consent screen for external users first, if Google asks for it.

Copy the redirect URI from the Google identity provider form in Entra. The form shows it before you save. Paste it as the authorized redirect URI of the Google OAuth client.

Copy the Client ID and the Client secret from Google. In the Entra admin center, go to External Identities, then All identity providers. Add the Google identity provider, paste the Client ID and Client secret, and save.

Do not write the client secret in notes, and do not commit it. It stays in the Entra form.

Expected: green. All identity providers lists Google with the status configured. Google sign-in is now an option for user flows.

## Step 8. Add Facebook as an identity provider

In Meta for Developers, create an app with the Facebook Login product. While the app is in development mode, only its admins, developers, and testers can sign in. Add your own Facebook account as a tester or admin. Otherwise the sign-in fails for you.

Add the redirect URI from the Facebook identity provider form in Entra as a valid OAuth redirect URI of the Facebook Login product.

In Entra, go to External Identities, then All identity providers. Add the Facebook identity provider. Paste the App ID and the App secret from Meta, then save.

The Microsoft Learn article on Facebook sign-in is labeled preview. If the portal does not accept the Facebook provider in this tenant, do not mark the lesson done. Record the message in the log, and keep the lesson at `[~]`.

Expected: green. All identity providers lists Facebook with the status configured.

## Step 9. Register the BrickShare API in the customer tenant

Open App registrations, then New registration. Fill in the form:

- Name: `BrickShare API`
- Supported account types: Accounts in this organizational directory only (single tenant)
- Redirect URI: leave empty. The API has no sign-in page.

Select Register. On the Overview page, copy two values into your notes:

- Application (client) ID. Lesson 4.3 uses it as the audience of the tokens for the API.
- Object ID. Lesson 13.7 imports the app with it.

Open Expose an API. Select Set next to Application ID URI, accept the default `api://<client id>`, and save. Then select Add a scope. Use the same values as lesson 4.1, step 4:

- Scope name: `api.access`
- Who can consent: Admins and users
- Admin consent display name: `Use the BrickShare API`
- Admin consent description: `Lets the app call the BrickShare API as the signed-in user.`
- User consent display name: `Use the BrickShare API`
- User consent description: `Lets the app call the BrickShare API as you.`
- State: Enabled

Select Add scope.

Open Manifest. Find the `"api"` object, then the line `"requestedAccessTokenVersion": null` inside it. Change `null` to `2`, then select Save. This is the same change as lesson 4.1, step 6. Architecture 5.2 requires version 2 tokens.

Do not add app roles to this app. Customers get the role `Customer` in code, in lesson 4.3.

Expected: green. Overview shows the name `BrickShare API`, single tenant, and the two ids. Expose an API lists the URI `api://<client id>` and one enabled scope, `api.access`. The manifest shows `"requestedAccessTokenVersion": 2` under `"api"`.

## Step 10. Create the customer user flow

Open User flows, then New user flow. Choose the sign-up and sign-in type. Fill in the form:

- Name: `customer-sign-up-sign-in`
- Identity providers: Email one-time passcode, Google, and Facebook. Select all three.
- User attributes to collect at sign-up: Email Address and Display Name.

Select Create.

Expected: green. User flows lists `customer-sign-up-sign-in`, and its identity providers show Email one-time passcode, Google, and Facebook.

## Step 11. Link the user flow to the BrickShare API

Open the user flow `customer-sign-up-sign-in`. Open Applications, then Add application. Choose `BrickShare API` and select it.

This link makes the user flow issue tokens for the API. Without it, the flow signs users in but gives no token for our app.

Expected: green. The Applications page of the user flow lists `BrickShare API`.

## Step 12. Green: check the first sign-up

Run user flow needs a reply URL on the application. The BrickShare API has no sign-in page, so add a redirect URI for this test only:

- Open App registrations, then BrickShare API, then Authentication.
- Select Add a platform, then Web. Enter the redirect URI `https://localhost` and select Configure.

Open the user flow `customer-sign-up-sign-in` and select Run user flow. Choose `BrickShare API` as the application. In Reply URL, select `https://localhost`.

The sign-in page shows three options: e-mail, Google, and Facebook. Sign up with an e-mail address that you can read. Enter the one-time code that arrives by e-mail. Complete the profile page if the flow asks for one. After sign-in, the browser tries to open `https://localhost` and shows an error page. That error is expected. The sign-up is complete.

Then open Users, then All users. Your new test user is listed.

Then remove the temporary redirect URI. Open BrickShare API, then Authentication, and delete the `https://localhost` entry from the Web platform. Save.

Expected: green. The sign-up completes, the test user is in All users, and the Web platform of BrickShare API has no redirect URI. Do not paste the token into a public decoding website. It contains the e-mail address.

The token check against the API comes later. Lesson 4.3 adds the `Customer` scheme, and lesson 4.4 adds the sign-in client.

## Result

The customer tenant `BrickShare Customers` exists. It holds the `BrickShare API` app registration. The API exposes the scope `api.access` and issues version 2 tokens. One user flow lets customers sign up and sign in with an e-mail one-time passcode, Google, or Facebook. The flow is linked to the API. The first test customer is in the tenant.

The checklist, in the portal:

- External ID tenant `BrickShare Customers`, with its Tenant ID, domain, and `issuer` recorded.
- Email one-time passcode enabled, Google and Facebook configured.
- App registration `BrickShare API`, single tenant, with its client id and object id recorded.
- Application ID URI `api://<client id>`, with the scope `api.access` enabled.
- Manifest `api.requestedAccessTokenVersion` is `2`.
- User flow `customer-sign-up-sign-in` with three identity providers, linked to `BrickShare API`.
- One test customer in All users.

The repository and the code stay as they were. Lesson 4.3 adds the `Customer` scheme to `BrickShare.Auth`. It reads the `issuer` and the client id from configuration, and it adds the role `Customer` when a token is validated. Lesson 4.4 adds the sign-in client. The development issuer and `dotnet user-jwts` keep working unchanged until then.

Files added or changed:

- `docs/Progress.md` (lesson 4.2 marked `[~]`, then `[x]`, plus log lines)
- No repository code files change. The Entra objects live in the customer tenant.

# Lesson 2.3. EF Core with PostgreSQL: `DbContext`, mappings, migrations, UUID v7 ids

Features: [F01](../features/01-catalog-management.md)
Previous: [2.2](2.2-catalog-domain-and-legoset.md) · Next: 2.4 Integration tests with `WebApplicationFactory` and Testcontainers

## Summary

We add EF Core with the Npgsql provider to the Catalog Api project. A `CatalogDbContext` maps the `LegoSet` aggregate from lesson 2.2 to the `lego_sets` table. Value objects become plain columns, and money is stored as minor units plus a currency code. The set id is set by the application, never by the database. We generate the first migration with the CLI, and the migration script shows the table that the database will get.

## The problem

The Catalog Service has a domain model from lesson 2.2 and an Api project from lesson 2.1, but nothing stores a set. Without persistence:

- A `LegoSet` exists only in memory. Restarting the Api loses every set. [Architecture.md section 3.2](../Architecture.md#32-catalog-service) gives the Catalog Service the data store PostgreSQL with EF Core and Npgsql, and database `catalog`.
- The domain uses value objects, and PostgreSQL has no type for them. EF Core must convert `LegoSetNumber` to text and `MinRentalDays` to an integer, and it must store `Money` as two columns.
- Ids must come from the application. [Architecture.md section 3.2](../Architecture.md#32-catalog-service) says Catalog owns its identifiers: `LegoSet.Id` is a UUID v7 value generated by Catalog with `Guid.CreateVersion7()`. If EF Core let the database generate the id, the id would not match the value the domain holds.
- The schema must be versioned in code. Migrations record each schema change, so every environment gets the same tables.

The feature rules that drive this lesson:

- "Catalog gives every set and instance its own id. APIs, events, and other services use only these ids." ([Catalog management](../features/01-catalog-management.md#sets)). The table key is the set id from the aggregate, and the box number is not the key.
- "The LEGO set number is digits only" and it is "searchable, not unique" ([Catalog management](../features/01-catalog-management.md#sets)). The column stores text, and no unique index is added on it. Several sets can share one box number, for example different editions.
- The money rule: "Money is stored in minor units (`long` cents) with an ISO currency code" ([Architecture.md section 1.3](../Architecture.md#13-scope-and-assumptions)). A `Money` value becomes a `bigint` amount and a currency code column.

The concepts we introduce:

- **`DbContext`.** The entry point to the database. It holds the `DbSet` for each aggregate and builds the EF Core model once.
- **Entity type configuration.** One class per aggregate (`IEntityTypeConfiguration<LegoSet>`) holds its mapping. The `DbContext` picks it up from the assembly, so the context stays short.
- **Value conversion.** `HasConversion` maps a value object to one scalar column and back. The conversion calls the value object's constructor, so the rules from lesson 2.2 still run when EF Core reads a row.
- **Complex type.** `ComplexProperty` maps a value object with several fields to several columns in the same table. `Money` uses it.
- **Application-generated keys.** `ValueGeneratedNever` tells EF Core that the id is always set before the insert.
- **Migrations.** `dotnet ef` reads the model and writes the code that changes the schema. The generated files are checked in.

## Step 3. Green: the `DbContext` and the `LegoSet` mapping

The context and its mapping come in one step. EF Core builds the whole model when the context is first used. If one property of `LegoSet` has no mapping, the model fails to build. So all the properties are mapped now.

The context exposes one `DbSet` and applies every entity type configuration in its assembly. Create the two files with the CLI. The `dotnet new class` command needs the target folder to exist inside the project, so create the folder first. Run from the repository root:

```powershell
New-Item -ItemType Directory -Force src/Services/Catalog/BrickShare.Catalog.Api/Infrastructure/Persistence | Out-Null
dotnet new class -n CatalogDbContext -o src/Services/Catalog/BrickShare.Catalog.Api/Infrastructure/Persistence
dotnet new class -n LegoSetConfiguration -o src/Services/Catalog/BrickShare.Catalog.Api/Infrastructure/Persistence
```

`src/Services/Catalog/BrickShare.Catalog.Api/Infrastructure/Persistence/CatalogDbContext.cs` (replace the template class with this content)

```csharp
using BrickShare.Catalog.Domain;

using Microsoft.EntityFrameworkCore;

namespace BrickShare.Catalog.Api.Infrastructure.Persistence;

public sealed class CatalogDbContext(DbContextOptions<CatalogDbContext> options) : DbContext(options)
{
    public DbSet<LegoSet> LegoSets => Set<LegoSet>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.ApplyConfigurationsFromAssembly(typeof(CatalogDbContext).Assembly);
    }
}
```

The `LegoSetConfiguration` class holds the mapping of the aggregate. Each value object has a conversion or a complex type. The `Id` never comes from the database, so the column has no default. The domain events are not stored, so they are ignored.

`src/Services/Catalog/BrickShare.Catalog.Api/Infrastructure/Persistence/LegoSetConfiguration.cs` (replace the template class with this content)

```csharp
using BrickShare.Catalog.Domain;
using BrickShare.SharedKernel;

using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Metadata.Builders;

namespace BrickShare.Catalog.Api.Infrastructure.Persistence;

public sealed class LegoSetConfiguration : IEntityTypeConfiguration<LegoSet>
{
    public void Configure(EntityTypeBuilder<LegoSet> builder)
    {
        builder.ToTable("lego_sets");

        builder.HasKey(legoSet => legoSet.Id);

        builder.Property(legoSet => legoSet.Id)
            .ValueGeneratedNever()
            .HasColumnName("id");

        builder.Property(legoSet => legoSet.LegoSetNumber)
            .HasConversion(number => number.Value, value => new LegoSetNumber(value))
            .HasColumnName("lego_set_number");

        builder.Property(legoSet => legoSet.MinRentalDays)
            .HasConversion(days => days.Days, value => new MinRentalDays(value))
            .HasColumnName("min_rental_days");

        builder.ComplexProperty(legoSet => legoSet.DailyPrice, money => ConfigureMoney(money, "daily_price"));
        builder.ComplexProperty(legoSet => legoSet.Deposit, money => ConfigureMoney(money, "deposit"));
        builder.ComplexProperty(legoSet => legoSet.ReplacementValue, money => ConfigureMoney(money, "replacement_value"));
        builder.ComplexProperty(legoSet => legoSet.LateFeePerDay, money => ConfigureMoney(money, "late_fee_per_day"));

        builder.Ignore(legoSet => legoSet.DomainEvents);
    }

    private static void ConfigureMoney(ComplexPropertyBuilder<Money> money, string columnPrefix)
    {
        money.Property(value => value.Amount)
            .HasColumnName($"{columnPrefix}_amount");

        money.Property(value => value.Currency)
            .HasColumnName($"{columnPrefix}_currency")
            .HasMaxLength(3);
    }
}
```

`ConfigureMoney` maps each `Money` to two columns in the same table. The amount is a `bigint` of minor units, and the currency is a three-letter ISO code. The `Money` constructor checks the currency when EF Core reads a row.

EF Core creates a `LegoSet` with a constructor. It cannot bind the four `Money` parameters of the public constructor, because `Money` is mapped as a complex type. EF Core also needs a way to build the object when it reads a row, so the aggregate gets a private parameterless constructor. It is never called from domain code. The real values come from the mapped properties.

The class changes from a primary constructor to a regular constructor, so the private constructor can sit next to the public one. Replace the whole file.

`src/Services/Catalog/BrickShare.Catalog.Domain/LegoSet.cs` (replace the file with this content)

```csharp
using System;

using BrickShare.SharedKernel;

namespace BrickShare.Catalog.Domain;

public sealed class LegoSet : AggregateRoot<Guid>
{
    // Used by EF Core to materialize a stored set. EF Core cannot bind the Money parameters to the public constructor.
    private LegoSet()
        : this(Guid.Empty, null!, null!, null!, null!, null!, null!)
    {
    }

    public LegoSet(
        Guid id,
        LegoSetNumber legoSetNumber,
        MinRentalDays minRentalDays,
        Money dailyPrice,
        Money deposit,
        Money replacementValue,
        Money lateFeePerDay)
        : base(id)
    {
        LegoSetNumber = legoSetNumber;
        MinRentalDays = minRentalDays;
        DailyPrice = dailyPrice;
        Deposit = deposit;
        ReplacementValue = replacementValue;
        LateFeePerDay = lateFeePerDay;
    }

    public LegoSetNumber LegoSetNumber { get; }

    public MinRentalDays MinRentalDays { get; }

    public Money DailyPrice { get; }

    public Money Deposit { get; }

    public Money ReplacementValue { get; }

    public Money LateFeePerDay { get; }
}
```

Before: the file from lesson 2.1, with `AddOpenApi` and `AddHealthChecks` only.

After:

```csharp
using System;

using BrickShare.Catalog.Api.Infrastructure.Persistence;

using Microsoft.AspNetCore.Builder;
using Microsoft.AspNetCore.Diagnostics.HealthChecks;
using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.Configuration;
using Microsoft.Extensions.DependencyInjection;

using Scalar.AspNetCore;

var builder = WebApplication.CreateBuilder(args);

var catalogConnection = builder.Configuration.GetConnectionString("catalog")
    ?? throw new InvalidOperationException("The connection string 'catalog' is missing.");

builder.Services.AddOpenApi();
builder.Services.AddHealthChecks();
builder.Services.AddDbContext<CatalogDbContext>(options => options.UseNpgsql(catalogConnection));

var app = builder.Build();

app.MapOpenApi();
app.MapScalarApiReference();

app.MapHealthChecks("/health/live", new HealthCheckOptions { Predicate = _ => false })
    .AllowAnonymous();

await app.RunAsync();
```

`GetConnectionString` returns a nullable string, and `UseNpgsql` expects a non-null one. The `throw` makes the missing setting fail at startup with a clear message. The liveness check does not touch the database, so `/health/live` still answers without PostgreSQL. Migrations do not run at startup in this lesson. Lesson 2.4 applies them in a test host with a real PostgreSQL container.

## Step 5. Generate the first migration

The migration is code that the CLI writes from the model. We do not type it by hand. The migration goes into `Infrastructure/Persistence/Migrations`, next to the context and its mapping. The `dotnet ef` tool reads the model, so no database is needed.

Run from the repository root:

```powershell
dotnet ef migrations add InitialCreate --project src/Services/Catalog/BrickShare.Catalog.Api --startup-project src/Services/Catalog/BrickShare.Catalog.Api --output-dir Infrastructure/Persistence/Migrations
```

Expected: the command reports that it created the migration. It writes three files under `src/Services/Catalog/BrickShare.Catalog.Api/Infrastructure/Persistence/Migrations/`: a migration file named with a timestamp and `_InitialCreate`, its `.Designer.cs` file, and `CatalogDbContextModelSnapshot.cs`.

The generated files do not follow the repository code style, and the build treats style findings as errors. Format them now. Run from the repository root:

```powershell
dotnet format
dotnet build BrickShare.slnx
```

Expected: green, with no warnings. `dotnet format` fixes the style of the generated migration files.

Next, print the SQL that the migration runs. The script is only printed. Nothing is run against a database.

```powershell
dotnet ef migrations script --project src/Services/Catalog/BrickShare.Catalog.Api --startup-project src/Services/Catalog/BrickShare.Catalog.Api
```

Expected: the script creates the table `lego_sets` with these columns and types:

- `id uuid NOT NULL`
- `lego_set_number text NOT NULL`
- `min_rental_days integer NOT NULL`
- `daily_price_amount bigint NOT NULL` and `daily_price_currency character varying(3) NOT NULL`
- the same pair for `deposit`, `replacement_value`, and `late_fee_per_day`
- `CONSTRAINT "PK_lego_sets" PRIMARY KEY (id)`

The script has no index on `lego_set_number`, because the set number is not unique. It has no column for `DomainEvents`.

If the migration script does not show these columns, the mapping in step 3 is wrong. Fix the mapping, generate the migration again, and check the script.

## Result

The Catalog Service maps `LegoSet` to the `lego_sets` table. The `DbContext` is registered with the Npgsql provider. The set id is set by the application and is a `uuid` primary key with no database default. `LegoSetNumber` and `MinRentalDays` are stored as plain columns through conversions, so the rules from lesson 2.2 run again when EF Core reads a row. Each `Money` is two columns: minor units and a currency code. The first migration, `InitialCreate`, is checked in.

No table or column exists yet for the descriptive fields, such as the name, the pieces, and the description. Lesson 2.6 adds them with the create and update endpoints. Themes come with lesson 2.7.

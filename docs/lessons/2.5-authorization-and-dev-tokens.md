# Lesson 2.5. Authorization policies, development tokens with `dotnet user-jwts`, test tokens in the test project

Features: [F01](../features/01-catalog-management.md)
Previous: [2.4](2.4-integration-tests-with-testcontainers.md) · Next: 2.6 Create, update, and deactivate sets: validation filters, `ProblemDetails`

## Summary

We add the `BrickShare.Auth` project with two policies, `AdminOnly` and `EmployeeOrAdmin`, and a development JWT issuer. Developers get tokens from `dotnet user-jwts`. The integration tests make their own tokens with a helper in the test project, so they need no user secrets. A small probe endpoint per policy gives the tests something to call. At the end six integration tests are green: an admin is allowed, an employee is refused on admin routes, and a request without a token gets `401`.

## The problem

The Catalog Service has a database (lesson 2.3) and integration tests (lesson 2.4), but every endpoint is open. Without authorization:

- Anyone who can reach the Api can change the catalog. [Catalog management](../features/01-catalog-management.md#endpoints) gives every write endpoint the policy `AdminOnly`, and the scanned-code lookup the policy `EmployeeOrAdmin`. Without these policies, the table is only text.
- The feature doc also says "every lookup needs a signed-in staff account" ([Catalog management](../features/01-catalog-management.md#inventory-code-and-qr-label)). The sign-in must be checked on the server, not in the staff client.
- [Architecture.md section 5.2](../Architecture.md#52-token-validation-in-aspnet-core) defines the policies as role rules, so they do not depend on who issued the token. Module 4 replaces the issuer, and the endpoints stay the same.
- Real sign-in (Entra ID) comes in course module 4. Until then, developers need tokens that look like real ones, and [Architecture.md section 5.3](../Architecture.md#53-development-issuer-until-the-identity-module) says they come from `dotnet user-jwts`.
- The tests must not call `dotnet user-jwts`. The test host has no user secrets, and the tests must run the same before and after module 4. [Architecture.md section 7.2](../Architecture.md#72-testing-strategy-and-tdd) gives each test project its own token helper.

The concepts we introduce:

- **Authentication and authorization.** Authentication answers "who is calling?" It is the JWT bearer handler. Authorization answers "may this caller do this?" It is a policy. A request without a valid token gets `401 Unauthorized`. A valid token without the required role gets `403 Forbidden`.
- **Role-based policies.** A policy names a rule (`RequireRole("Admin")`). An endpoint group states its policy once with `RequireAuthorization`, so every endpoint in the group has it.
- **Development issuer.** The JWT bearer scheme is registered only in the `Development` environment, and only when `Authentication:UseDevelopmentIssuer` is `true`. Outside Development no scheme exists, so every protected call fails. That is the fail-closed default.
- **Test tokens.** The test project signs its own tokens with a fixed test key, and the factory sets the same key for the test host. The tests exercise the same validation path as a developer token.

The `TestTokens` helper writes a signed token with two claims: `role` for the policy, and `oid` for the user id. The helper is a test helper, so it is not part of the Api. The factory will use the same key in step 7.

`tests/Services/Catalog/BrickShare.Catalog.Api.Tests/TestTokens.cs`

```csharp
using System;
using System.IdentityModel.Tokens.Jwt;
using System.Security.Claims;
using System.Text;

using Microsoft.IdentityModel.Tokens;

namespace BrickShare.Catalog.Api.Tests;

public static class TestTokens
{
    public const string Issuer = "https://brickshare.test";
    public const string Audience = "brickshare-catalog-tests";

    public static SymmetricSecurityKey SigningKey { get; } =
        new(Encoding.UTF8.GetBytes("catalog-tests-signing-key-with-at-least-32-bytes"));

    public static string Create(string role)
    {
        var credentials = new SigningCredentials(SigningKey, SecurityAlgorithms.HmacSha256);

        var token = new JwtSecurityToken(
            issuer: Issuer,
            audience: Audience,
            claims:
            [
                new Claim("oid", Guid.CreateVersion7().ToString()),
                new Claim("role", role)
            ],
            expires: DateTime.UtcNow.AddMinutes(10),
            signingCredentials: credentials);

        return new JwtSecurityTokenHandler().WriteToken(token);
    }
}
```

The tests cover the rules from [Architecture.md section 5.2](../Architecture.md#52-token-validation-in-aspnet-core): `AdminOnly` needs role `Admin`, `EmployeeOrAdmin` needs `Employee` or `Admin`, and a request without a token is not allowed.

`tests/Services/Catalog/BrickShare.Catalog.Api.Tests/AccessProbeTests.cs`

```csharp
using System.Net;
using System.Net.Http;
using System.Net.Http.Headers;
using System.Threading.Tasks;

using AwesomeAssertions;

using Xunit;

namespace BrickShare.Catalog.Api.Tests;

public class AccessProbeTests(CatalogApiFactory factory) : IClassFixture<CatalogApiFactory>
{
    [Fact]
    public async Task Admin_token_is_allowed_on_admin_probe()
    {
        var status = await GetStatusAsync("/catalog/probe/admin", TestTokens.Create("Admin"));

        status.Should().Be(HttpStatusCode.OK);
    }

    [Fact]
    public async Task Employee_token_is_forbidden_on_admin_probe()
    {
        var status = await GetStatusAsync("/catalog/probe/admin", TestTokens.Create("Employee"));

        status.Should().Be(HttpStatusCode.Forbidden);
    }

    [Fact]
    public async Task Missing_token_is_unauthorized_on_admin_probe()
    {
        var status = await GetStatusAsync("/catalog/probe/admin");

        status.Should().Be(HttpStatusCode.Unauthorized);
    }

    [Fact]
    public async Task Admin_token_is_allowed_on_staff_probe()
    {
        var status = await GetStatusAsync("/catalog/probe/staff", TestTokens.Create("Admin"));

        status.Should().Be(HttpStatusCode.OK);
    }

    [Fact]
    public async Task Employee_token_is_allowed_on_staff_probe()
    {
        var status = await GetStatusAsync("/catalog/probe/staff", TestTokens.Create("Employee"));

        status.Should().Be(HttpStatusCode.OK);
    }

    [Fact]
    public async Task Customer_token_is_forbidden_on_staff_probe()
    {
        var status = await GetStatusAsync("/catalog/probe/staff", TestTokens.Create("Customer"));

        status.Should().Be(HttpStatusCode.Forbidden);
    }

    private async Task<HttpStatusCode> GetStatusAsync(string path, string? token = null)
    {
        using var client = factory.CreateClient();
        using var request = new HttpRequestMessage(HttpMethod.Get, path);

        if (token is not null)
        {
            request.Headers.Authorization = new AuthenticationHeaderValue("Bearer", token);
        }

        using var response = await client.SendAsync(request, TestContext.Current.CancellationToken);

        return response.StatusCode;
    }
}
```

## Step 4. Green: the policies and the two extension methods

Now the authorization rules exist in code. The policy names are constants, so the endpoints and the policy definitions use the same strings. The `AdminOnly` policy requires the role `Admin`. The `EmployeeOrAdmin` policy accepts `Employee` or `Admin`, which is the rule from [Architecture.md section 5.2](../Architecture.md#52-token-validation-in-aspnet-core). The policies read the `role` claim, and the JWT bearer handler maps it to the standard role claim, so `RequireRole` works with it.

The authentication method registers the JWT bearer scheme only when two conditions hold: the environment is `Development`, and `Authentication:UseDevelopmentIssuer` is `true`. The scheme takes no settings in code. `AddJwtBearer()` reads the signing key and the issuer settings from the configuration. The `dotnet user-jwts` tool writes them to user secrets, and the test factory sets them in step 7.

Create the three files with the CLI, then replace their content. The `dotnet new class` command writes a class in the project folder.

```csharp
using Microsoft.Extensions.DependencyInjection;

namespace BrickShare.Auth;

public static class AuthorizationExtensions
{
    public static IServiceCollection AddBrickShareAuthorization(this IServiceCollection services)
    {
        services.AddAuthorizationBuilder()
            .AddPolicy(Policies.AdminOnly, policy => policy.RequireRole("Admin"))
            .AddPolicy(Policies.EmployeeOrAdmin, policy => policy.RequireRole("Employee", "Admin"));

        return services;
    }
}
```

`src/BuildingBlocks/BrickShare.Auth/AuthenticationExtensions.cs` (replace the template class with this content)

```csharp
using Microsoft.AspNetCore.Authentication.JwtBearer;
using Microsoft.Extensions.Configuration;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;

namespace BrickShare.Auth;

public static class AuthenticationExtensions
{
    public static IServiceCollection AddBrickShareAuthentication(
        this IServiceCollection services,
        IConfiguration configuration,
        IHostEnvironment environment)
    {
        var authentication = services.AddAuthentication();

        if (environment.IsDevelopment() && configuration.GetValue<bool>("Authentication:UseDevelopmentIssuer"))
        {
            authentication.AddJwtBearer();
        }

        return services;
    }
}
```

`AddAuthentication()` always runs, so the authentication services exist in every environment. Only the development scheme is conditional. Outside Development, a protected endpoint has no scheme to read a token with, so the call fails and no one gets in.

## Step 5. Wire the authentication and authorization into the Api

The development setting goes into `appsettings.Development.json`. Outside Development the setting has no effect, because the scheme check also requires the `Development` environment.

`src/Services/Catalog/BrickShare.Catalog.Api/Program.cs` (replace the file with this content; the probe route is added in step 6)

```csharp
using System;

using BrickShare.Auth;
using BrickShare.Catalog.Api.Infrastructure.Persistence;

using Microsoft.AspNetCore.Builder;
using Microsoft.AspNetCore.Diagnostics.HealthChecks;
using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.Configuration;
using Microsoft.Extensions.DependencyInjection;

using Scalar.AspNetCore;

var builder = WebApplication.CreateBuilder(args);

var catalogConnection = builder.Configuration.GetConnectionString("catalog")
    ?? throw new InvalidOperationException("The connection string 'catalog' is missing.");

builder.Services.AddOpenApi();
builder.Services.AddHealthChecks();
builder.Services.AddDbContext<CatalogDbContext>(options => options.UseNpgsql(catalogConnection));
builder.Services.AddBrickShareAuthentication(builder.Configuration, builder.Environment);
builder.Services.AddBrickShareAuthorization();

var app = builder.Build();

app.UseAuthentication();
app.UseAuthorization();

app.MapOpenApi();
app.MapScalarApiReference();

app.MapHealthChecks("/health/live", new HealthCheckOptions { Predicate = _ => false })
    .AllowAnonymous();

await app.RunAsync();
```

## Step 6. Add the probe endpoints

The probe slice lives in `Features/Access/Probe/`, as the project rules require for a vertical slice. Each probe is a route group with one policy. The group states the policy once, so the endpoint cannot be added without it. The handler returns `TypedResults.Ok()`, with no body, because the tests only check the status code.

`src/Services/Catalog/BrickShare.Catalog.Api/Features/Access/Probe/AccessProbe.cs`

```csharp
using BrickShare.Auth;

using Microsoft.AspNetCore.Builder;
using Microsoft.AspNetCore.Http;
using Microsoft.AspNetCore.Routing;

namespace BrickShare.Catalog.Api.Features.Access.Probe;

public static class AccessProbe
{
    public static void MapAccessProbe(this IEndpointRouteBuilder app)
    {
        var probe = app.MapGroup("/catalog/probe");

        probe.MapGroup("/admin")
            .RequireAuthorization(Policies.AdminOnly)
            .MapGet("/", () => TypedResults.Ok());

        probe.MapGroup("/staff")
            .RequireAuthorization(Policies.EmployeeOrAdmin)
            .MapGet("/", () => TypedResults.Ok());
    }
}
```

## Step 7. Green: the test host signs and checks tokens

The factory gives the test host the settings it needs. It sets the environment to `Development` and turns on the development issuer. It also replaces the signing key and the issuer and audience checks with the test values from `TestTokens`. `PostConfigure` runs after the default JWT bearer configuration, so the test values win.

The factory file keeps everything from lesson 2.4 and adds the test-host configuration. The `ConfigureWebHost` method is the only part that changes.

`tests/Services/Catalog/BrickShare.Catalog.Api.Tests/CatalogApiFactory.cs` (replace the file with this content)

```csharp
using System.Threading.Tasks;

using BrickShare.Catalog.Api.Infrastructure.Persistence;

using Microsoft.AspNetCore.Authentication.JwtBearer;
using Microsoft.AspNetCore.Hosting;
using Microsoft.AspNetCore.Mvc.Testing;
using Microsoft.AspNetCore.TestHost;
using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;

using Testcontainers.PostgreSql;

using Xunit;

namespace BrickShare.Catalog.Api.Tests;

public sealed class CatalogApiFactory : WebApplicationFactory<CatalogApi>, IAsyncLifetime
{
    private readonly PostgreSqlContainer _postgres = new PostgreSqlBuilder("postgres:18").Build();

    public async ValueTask InitializeAsync()
    {
        await _postgres.StartAsync();

        await using var scope = Services.CreateAsyncScope();
        var dbContext = scope.ServiceProvider.GetRequiredService<CatalogDbContext>();
        await dbContext.Database.MigrateAsync();
    }

    public override async ValueTask DisposeAsync()
    {
        await base.DisposeAsync();
        await _postgres.DisposeAsync();
    }

    protected override void ConfigureWebHost(IWebHostBuilder builder)
    {
        builder.UseEnvironment(Environments.Development);
        builder.UseSetting("ConnectionStrings:catalog", _postgres.GetConnectionString());
        builder.UseSetting("Authentication:UseDevelopmentIssuer", "true");

        builder.ConfigureTestServices(services =>
            services.PostConfigure<JwtBearerOptions>(JwtBearerDefaults.AuthenticationScheme, options =>
            {
                options.TokenValidationParameters.ValidIssuer = TestTokens.Issuer;
                options.TokenValidationParameters.ValidAudience = TestTokens.Audience;
                options.TokenValidationParameters.IssuerSigningKey = TestTokens.SigningKey;
            }));
    }
}
```

The test host now uses the same validation path as a developer token: the scheme is registered, the token is checked for signature, issuer, audience, and lifetime, and then the policy reads the role.

## Step 8. Manual check with `dotnet user-jwts`

The tests do not need this step. It shows the developer flow: a token from the local issuer, sent to the running Api. The user secrets store the signing key that the tool creates, so the project needs a user secrets id first. `dotnet user-secrets init` adds the `UserSecretsId` property to the Api project file.

The first `dotnet user-jwts create` also adds an `Authentication:Schemes:Bearer` section to `appsettings.Development.json`. It holds `ValidIssuer` (`dotnet-user-jwts`) and the `ValidAudiences` from `launchSettings.json`. The signing key stays in the user secrets. Keep this section. The JWT bearer scheme reads it, so the Api accepts the tokens.

Run from the repository root:

```powershell
dotnet user-secrets init --project src/Services/Catalog/BrickShare.Catalog.Api
dotnet run --project src/Services/Catalog/BrickShare.Catalog.Api --launch-profile http
```

The `http` profile runs in `Development` and listens on `http://localhost:5029`. Leave it running. In a second terminal, from the repository root, create one token for an admin and one for an employee. With `--output token`, the command prints only the token. Then call the probes:


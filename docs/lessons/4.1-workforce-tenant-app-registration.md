# Lesson 4.1. Workforce tenant: BrickShare API app registration, scope, app roles

Features: [F04](../features/04-staff-management.md)
Previous: [3.3](3.3-configuration-and-override.md) · Next: 4.2 External ID tenant: customer user flow with e-mail OTP, Google, and Facebook

## Summary

We register the BrickShare API in the workforce Entra ID tenant, in the Azure portal. The app exposes the scope `api.access` and the app roles `Admin` and `Employee`, and it issues version 2 tokens. Only users with a role can get a token for the API. We assign `Admin` to our own account. At the end the configuration matches the checklist in the Result section, and no repository file has changed. Lesson 13.7 imports these objects into Terraform.

## The problem

Staff have no identity yet. The Catalog Service accepts tokens only from `dotnet user-jwts` (lesson 2.5). [Staff management](../features/04-staff-management.md) needs real sign-in:

- "Staff sign in with Microsoft Entra ID (workforce tenant)."
- "`Admin` can also do all `Employee` tasks."
- "Role changes take effect at the user's next sign-in."

[Architecture 5.1](../Architecture.md#51-tenants-and-app-registrations) names the objects in the workforce tenant: the `BrickShare API` app registration with the scope `api.access` and the app roles `Admin` and `Employee`. Development and Test share this tenant.

The concepts we introduce:

- **App registration and enterprise application.** The app registration defines the API. Its service principal, shown in the portal as the enterprise application, is the copy of that app inside the tenant. Role assignments and the "assignment required" switch live on the enterprise application.
- **Scope.** A client asks for `api.access` to get a token for the API. The scope appears in the token as `scp`.
- **App roles.** `Admin` and `Employee` appear in the `roles` claim of the token. [Architecture 5.2](../Architecture.md#52-token-validation-in-aspnet-core) maps that claim for the `Staff` scheme in lesson 4.3. The role policies from lesson 2.5 keep working unchanged.
- **Token version 2.** The API sets the token version to `2`. Version 2 tokens have the issuer `https://login.microsoftonline.com/<tenant id>/v2.0`, which lesson 4.3 validates. Version 1 tokens have a different issuer.
- **Assignment required.** Only users with a role assignment get a token for the API. A user without a role never reaches the API, so the policies never see a role-less caller.

Scope decisions:

- **Azure portal, done once by hand.** [Architecture 9.1](../Architecture.md#91-infrastructure-as-code-with-terraform) puts Azure resources in Terraform. The workforce app is the one exception, because Terraform comes in module 13. Lesson 13.7 imports the objects with the `azuread` provider, so this lesson records their ids (step 3).
- **No pre-authorized clients.** Nothing calls the API in this lesson, so no client needs the scope yet.
- **Only the `Admin` role is assigned.** Assigning roles to other staff is the job of the Customer Service (lesson 5.5), through Microsoft Graph.
- **The token check waits for a sign-in.** A `roles` claim exists only in a token that a real user gets from a client. The first lesson with a sign-in client checks it end to end. The checks in this lesson read the portal configuration.

No feature rule can become a unit test before the API checks tokens. This lesson writes no production code and no test. Its checks are portal views, and each one ends with red or green.

## Step 1. Check the starting state and sign in to the portal

Run from the repository root:

```powershell
git status
git branch --show-current
```

Expected: `git status` shows no changes. The branch is `lesson-4.1`.

Open the Microsoft Entra admin center at `https://entra.microsoft.com`. Sign in with an account that has the Application Administrator role in the workforce tenant. A tenant owner has that role. If the portal opens another tenant, switch directory from the account menu.

Open Entra ID, then Overview. Check that the primary domain is your workforce tenant and the account is a member, not a guest. Copy the Tenant ID and keep it in your notes. Do not save it in a repository file.

Mark lesson 4.1 as `[~]` in `docs/Progress.md`, and set "Current lesson" to 4.1. Add a dated line to the log.

## Step 2. Red: the BrickShare API app does not exist yet

Open Entra ID, then App registrations. Search for `BrickShare API`.

Expected: red. The search finds nothing. If an app with that name already exists, an earlier attempt created it. Open that app and check the configuration in step 9 instead of creating a second app.

## Step 3. Register the app and record its ids

Select New registration, then fill in the form:

- Name: `BrickShare API`
- Supported account types: Accounts in this organizational directory only (single tenant)
- Redirect URI: leave empty. The API has no sign-in page.

Select Register. On the Overview page, copy two values into your notes:

- Application (client) ID. Lesson 4.3 uses it as the audience of the `Staff` scheme.
- Object ID. Lesson 13.7 imports the app with it.

Expected: green. The Overview page shows the name `BrickShare API` and the two ids.

## Step 4. Set the Application ID URI and add the scope `api.access`

Open Expose an API. Select Set next to Application ID URI, accept the default `api://<client id>`, and save.

Select Add a scope and fill in the form:

- Scope name: `api.access`
- Who can consent: Admins and users
- Admin consent display name: `Use the BrickShare API`
- Admin consent description: `Lets the app call the BrickShare API as the signed-in user.`
- User consent display name: `Use the BrickShare API`
- User consent description: `Lets the app call the BrickShare API as you.`
- State: Enabled

Select Add scope.

Expected: green. Expose an API lists the Application ID URI `api://<client id>` and one enabled scope, `api.access`. No client is listed under Authorized client applications.

## Step 5. Add the app roles `Admin` and `Employee`

Open App roles. Select Create app role, then fill in the form for the first role:

| Field | Admin | Employee |
|-------|-------|----------|
| Display name | Admin | Employee |
| Allowed member types | Users/Groups | Users/Groups |
| Value | `Admin` | `Employee` |
| Description | Manages the catalog, staff, and bans. Does all Employee tasks. | Gives out, takes back, and inspects sets. |
| Do you want to enable this app role? | Checked | Checked |

Select Apply after each role.

Expected: green. App roles lists `Admin` and `Employee`, both enabled, with the allowed member type Users/Groups.

## Step 6. Set the token version to 2

Open Manifest. This is the Microsoft Graph app manifest, which the portal shows by default. Find the `"api"` object, then the line `"requestedAccessTokenVersion": null` inside it. Change `null` to `2`. Select Save.

Do not use the field `accessTokenAcceptedVersion`. It belongs to the AAD Graph manifest, which is being retired. The Microsoft Graph field is `api.requestedAccessTokenVersion`, and it sets the same token version. Version 2 makes the token issuer `https://login.microsoftonline.com/<tenant id>/v2.0`. Lesson 4.3 validates that issuer. Only change this one value. A JSON error stops the save, and the message shows the line.

Expected: green. The manifest shows `"requestedAccessTokenVersion": 2` under `"api"`, and the save finishes without an error.

## Step 7. Make the enterprise application require an assignment

The portal created the enterprise application with the app registration. Open Enterprise applications, search for `BrickShare API`, and open it. Open Properties.

Set Assignment required? to Yes, and save.

Expected: green. Properties shows Assignment required? as Yes. A user without a role now gets no token for the API.

## Step 8. Assign the `Admin` role to your own account

Staff get their roles from Microsoft Graph in lesson 5.5. For this check, we assign `Admin` to the account that signed in during step 1.

Open the enterprise application `BrickShare API`, then Users and groups. Select Add user/group, then None selected under Users. Choose your own account and select it. Under Select a role, choose `Admin`, then Select, then Assign.

Expected: green. Users and groups lists one row: your account, with the role `Admin`.

## Step 9. Green: check the configuration

Open each page and compare it with the table. Every row must match.

| Where in the portal | What to see |
|---------------------|-------------|
| App registrations, BrickShare API, Overview | One app, single tenant, two ids recorded in step 3 |
| Expose an API | Application ID URI `api://<client id>`, scope `api.access` enabled |
| App roles | `Admin` and `Employee`, enabled, Users/Groups |
| Manifest | `"requestedAccessTokenVersion": 2` under `"api"` |
| Enterprise applications, BrickShare API, Properties | Assignment required? Yes |
| Enterprise applications, BrickShare API, Users and groups | Your account with the role `Admin` |

Expected: green. All six rows match.

If a row is different, fix it on its page and check again. The checks are for the configuration only. The token check comes with the first lesson that signs a user in.

## Step 10. Mark the lesson done

Mark lesson 4.1 as `[x]` in `docs/Progress.md`, and set "Current lesson" to 4.2. Add a dated line to the log.

Keep the two ids from step 3 and the tenant id from step 1 for lesson 4.3 and lesson 13.7. They are not secrets.

## Result

The workforce tenant holds the `BrickShare API` app registration. It exposes the scope `api.access`, and it has the app roles `Admin` and `Employee`. It issues version 2 tokens. Only users with a role assignment get a token. Your account holds `Admin`.

The checklist, in the portal:

- App registration `BrickShare API`, single tenant, with its client id and object id recorded.
- Application ID URI `api://<client id>`, with the scope `api.access` enabled.
- App roles `Admin` and `Employee`, enabled.
- Manifest `api.requestedAccessTokenVersion` is `2`.
- Enterprise application `BrickShare API`, Assignment required? is Yes.
- Your account is assigned the role `Admin`.

The repository and the code stay as they were. Lesson 4.2 adds the External ID tenant for customers. Lesson 4.3 adds the `Staff` scheme to `BrickShare.Auth` and reads the tenant id and client id from configuration. Lesson 13.7 imports these objects into Terraform. The development issuer and `dotnet user-jwts` keep working unchanged until then.

Files added or changed:

- No repository files change. The Entra objects live in the workforce tenant.

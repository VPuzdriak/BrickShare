# Lesson 3.1. Multi-stage Dockerfile: chiseled runtime image, non-root user

Previous: [2.16](2.16-theme-facets-in-memory-cache.md) · Next: 3.2 docker compose: PostgreSQL, Azurite, Catalog Service

## Summary

We add a `Dockerfile` for the Catalog Api. It has two stages. The first stage uses the .NET SDK image to restore and publish the app. The second stage copies the published output onto the chiseled ASP.NET image and runs it as a non-root user. At the end the image builds, starts, answers `GET /health/live` with 200, and its app process runs as UID 1654.

## The problem

Until now the Catalog Api runs only with `dotnet run` on a developer machine. Nothing can start it as a container, and the next lesson (docker compose) needs an image to run. [Architecture 7.5](../Architecture.md#75-containers) sets the rule:

> Container Apps services use a multi-stage `Dockerfile` per service (`sdk` build stage, `aspnet` chiseled runtime image, non-root user).

Why each part matters for BrickShare:

- **The runtime image must not contain the SDK.** The SDK adds compilers, NuGet caches, and build tools that a running service never uses. Each extra package is attack surface and extra size. A multi-stage build keeps them in the first stage and throws that stage away.
- **Chiseled images.** The `aspnet:10.0-noble-chiseled` image contains only the .NET runtime and the libraries it needs. It has no shell and no package manager. An attacker who reaches the process has fewer tools to use.
- **Non-root user.** The process runs as UID 1654 (the `app` user in the image), not as root. If the process is compromised, it cannot change system files in the container.
- **Build context is the repository root.** The build reads `Directory.Build.props`, `Directory.Packages.props`, `global.json`, and `.editorconfig`, which all live at the root. It also needs the BuildingBlocks and Catalog Domain projects that the Api references. So the Docker build context is the repository root, and the `Dockerfile` sits in the Api folder. [Architecture 7.5](../Architecture.md#75-containers) does not name the file location or the build context. This lesson chooses both (see the Result section).

Concepts this lesson introduces:

- **Multi-stage build.** A `FROM` line starts a new stage. `COPY --from=build` moves files from the build stage into the final image. Only the last stage becomes the image.
- **Layer caching.** Docker reuses a layer when its inputs have not changed. Copying the project files and running `dotnet restore` before copying the source means a source change does not download every NuGet package again.
- **Build context and `.dockerignore`.** Docker sends the whole build context to the daemon. `.dockerignore` keeps host build output out of it. A `bin` or `obj` folder from Windows or macOS would break the Linux build.

No feature doc sets a business rule for this lesson, so there is no unit test to write first. The checks are build and run steps. Each one ends with red or green, as the other lessons do.

Startup settings for this lesson: `Program.cs` throws at startup if `ConnectionStrings:catalog`, `Rebrickable:ApiKey`, or `Storage:BlobServiceUri` is missing. The container gets these as `docker run` arguments with placeholder values. The live check runs no database, Rebrickable, or Blob Storage call. Lesson 3.3 moves these settings into environment variables and compose files.

## Step 2. Add `.dockerignore` at the repository root

The Docker CLI can't generate this file, so write it by hand. It keeps build output, IDE folders, Git data, and test code out of the build context. The build does not need them, and host `bin` and `obj` folders would break the Linux build.

`.dockerignore`

```text

**/obj
**/.idea
**/.vs
.git
```

## Step 4. Green: the SDK stage restores and publishes

The first version of the Dockerfile has only the build stage. It restores the NuGet packages, then publishes the Api. The restore runs before the source is copied, so the layer is reused when only source files change.

The second copy takes only the two folders the Api depends on: `src/BuildingBlocks/` and `src/Services/Catalog/`. The Gateway, the Functions, and the other services are not in the image, so a change in them does not invalidate the publish layer.

The copy of `.editorconfig` matters. `EnforceCodeStyleInBuild` reads the root `.editorconfig` during the build. Without it, the container build would apply different analyzer severities from a local build.

`src/Services/Catalog/BrickShare.Catalog.Api/Dockerfile`

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src

COPY global.json Directory.Build.props Directory.Packages.props .editorconfig ./
COPY src/BuildingBlocks/BrickShare.Auth/BrickShare.Auth.csproj src/BuildingBlocks/BrickShare.Auth/
COPY src/BuildingBlocks/BrickShare.SharedKernel/BrickShare.SharedKernel.csproj src/BuildingBlocks/BrickShare.SharedKernel/
COPY src/Services/Catalog/BrickShare.Catalog.Domain/BrickShare.Catalog.Domain.csproj src/Services/Catalog/BrickShare.Catalog.Domain/
COPY src/Services/Catalog/BrickShare.Catalog.Api/BrickShare.Catalog.Api.csproj src/Services/Catalog/BrickShare.Catalog.Api/
RUN dotnet restore src/Services/Catalog/BrickShare.Catalog.Api/BrickShare.Catalog.Api.csproj

COPY src/BuildingBlocks/ src/BuildingBlocks/
COPY src/Services/Catalog/ src/Services/Catalog/
RUN dotnet publish src/Services/Catalog/BrickShare.Catalog.Api/BrickShare.Catalog.Api.csproj -c Release -o /app/publish --no-restore
```

Run from the repository root:

```powershell
docker build -f src/Services/Catalog/BrickShare.Catalog.Api/Dockerfile -t brickshare-catalog-api:3.1 .
```

Expected: green. The build ends with `naming to ... brickshare-catalog-api:3.1` (or the equivalent `Built` line in your Docker version). The image is still the SDK image. Step 5 replaces it.

Failure guide: if restore fails with a missing project file, check the four `COPY` lines against the project references in `BrickShare.Catalog.Api.csproj` and `BrickShare.Catalog.Domain.csproj`. If the build fails with an analyzer warning, the same warning fails the local build. Fix it in the code, not in the Dockerfile.

## Step 5. Green: add the chiseled runtime stage as a non-root user

Add a second stage after the build stage. It copies only the published output into the chiseled ASP.NET image. The image already sets the UID for the `app` user in `APP_UID`, so `USER $APP_UID` makes the non-root user explicit. `ASPNETCORE_ENVIRONMENT` is not set, so the app runs in `Production`. The development token issuer from `appsettings.Development.json` is not registered in that environment, as [CLAUDE.md](../../CLAUDE.md) requires.

`src/Services/Catalog/BrickShare.Catalog.Api/Dockerfile`

Add these lines after the `RUN dotnet publish` line of the build stage. Nothing is replaced.

```dockerfile
FROM mcr.microsoft.com/dotnet/aspnet:10.0-noble-chiseled AS runtime
WORKDIR /app
COPY --from=build /app/publish .
USER $APP_UID
ENTRYPOINT ["dotnet", "BrickShare.Catalog.Api.dll"]
```

Run from the repository root:

```powershell
docker build -f src/Services/Catalog/BrickShare.Catalog.Api/Dockerfile -t brickshare-catalog-api:3.1 .
docker image inspect brickshare-catalog-api:3.1 --format '{{.Config.User}}'
```

Expected: the build is green. The `inspect` command prints `1654`, the UID of the non-root user. Before this step the same command printed nothing, because the SDK image runs as root.

Check the size too: `docker image ls brickshare-catalog-api:3.1` should show an image far smaller than the SDK image from step 4. The chiseled image has no shell, so `docker exec` into it does not work. Use `docker top` in step 6 instead.

## Step 6. Green: the container answers its liveness check as UID 1654

Start the container in the background with placeholder settings. `/health/live` runs no checks, so these values only satisfy the startup checks in `Program.cs`.

```powershell
docker run -d --name catalog-api-3-1 -p 8080:8080 `
  -e ConnectionStrings__catalog="Host=host.docker.internal;Database=catalog;Username=postgres" `
  -e Rebrickable__ApiKey=placeholder-for-lesson-3-1 `
  -e Storage__BlobServiceUri="http://host.docker.internal:10000/devstoreaccount1" `
  brickshare-catalog-api:3.1
```

Check the liveness endpoint and the user of the app process:

```powershell
Invoke-WebRequest -UseBasicParsing -Uri http://localhost:8080/health/live | Select-Object StatusCode
docker top catalog-api-3-1
```

Expected: green. `StatusCode` is `200`. In the `docker top` output, the row for the `dotnet BrickShare.Catalog.Api.dll` process shows `1654` in the `UID` column, not `root` or `0`.

Clean up when you are done:

```powershell
docker rm -f catalog-api-3-1
```

Failure guide: if the container exits at once, run `docker logs catalog-api-3-1`. The usual cause is a missing or misspelled setting. The message names it. If `docker top` shows `0`, the `USER` line did not take effect. Check that it is the last stage's line.

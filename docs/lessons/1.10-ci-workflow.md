# Lesson 1.10. CI workflow `ci.yml`: build, test, format check

Previous: [1.7](1.7-money-value-object.md) · Next: 1.11 GitHub repository setup

## Summary

We add one GitHub Actions workflow, `.github/workflows/ci.yml`. It runs on every pull request to `main`. It restores, builds, tests, and checks the format of the solution, with the same commands we run on our machine. At the end, a pull request shows a green `ci` check. We also prove that the check blocks a broken format, and then we restore the green state.

## The problem

Until now, every check in this course runs only on the author's machine. Lessons 1.2, 1.4, 1.5, and 1.7 each showed a command that must pass before a change is finished: the build with warnings as errors, the tests, and `dotnet format --verify-no-changes`. Nothing enforces them. A change with a warning, a failing test, or a wrong format can still reach `main`.

[Architecture.md section 10.2](../Architecture.md#102-workflows) defines `ci.yml`: it runs on every pull request, and it runs the build with warnings as errors, the tests, and the format check. [Architecture.md section 7.2](../Architecture.md#72-testing-strategy-and-tdd) says that CI runs all test levels on every pull request, and that a failing test blocks the merge. [CLAUDE.md](../../CLAUDE.md) asks for `dotnet format` before a change is finished. CI makes that rule automatic.

This lesson has no business rule from `docs/features/`. It is a quality gate for the whole repository.

The concepts:

- **Workflow.** A YAML file in `.github/workflows/` tells GitHub Actions what to run and when. We use one workflow, triggered by `pull_request`.
- **Job and check name.** Each job reports one check to the pull request. The job id `ci` gives the check the name `ci`. Lesson 1.11 requires this name in branch protection, so we keep it fixed now.
- **`global.json` in CI.** `actions/setup-dotnet` reads `global.json`, so CI uses the same SDK version (10.0.100) as the author's machine.
- **Same commands as locally.** The workflow runs the same commands that Step 2 runs on the author's machine. If they pass locally, they pass in CI.

## Step 2. Run the CI commands on your machine

This step is the baseline. The workflow will run these four commands in this order. We run them first, so a failure is found on our machine, not in CI.

Run from the repository root:

```powershell
dotnet restore BrickShare.slnx
dotnet format BrickShare.slnx --verify-no-changes --no-restore
dotnet build BrickShare.slnx --no-restore
dotnet test BrickShare.slnx --no-restore --no-build
```

Expected: green. Each command exits with code 0. The test run reports no failed tests, and the number of passed tests is the one that lesson 1.7 reported (14). The format check prints no changes.

If a command fails, fix it before you go on. The workflow would fail on the same command.

`--no-restore` on the build, test, and format commands is safe here, because the first command already restored the solution. CI does the same, so the restore runs once and its time is visible in the logs.

## Step 3. Write the workflow file

We write the file by hand. The `dotnet` CLI has no template for a GitHub workflow.

`.github/workflows/ci.yml`

```yaml
name: CI

on:
  pull_request:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

jobs:
  ci:
    runs-on: ubuntu-latest

    steps:
      - name: Check out the code
        uses: actions/checkout@v5

      - name: Set up .NET from global.json
        uses: actions/setup-dotnet@v5
        with:
          global-json-file: global.json

      - name: Restore
        run: dotnet restore BrickShare.slnx

      - name: Check format
        run: dotnet format BrickShare.slnx --verify-no-changes --no-restore

      - name: Build
        run: dotnet build BrickShare.slnx --no-restore

      - name: Test
        run: dotnet test BrickShare.slnx --no-restore --no-build
```

The trigger is `pull_request` for `main` only. Pushes to other branches do not start the workflow, so a branch is checked when its pull request opens or changes.

`workflow_dispatch` adds a manual run from the Actions tab, or with `gh workflow run ci.yml`. It runs the same four steps on the selected branch. The author uses it to check a branch without opening a pull request.

`permissions: contents: read` gives the job only the access it needs to read the code. The workflow does not write to the repository.

The job id is `ci`. The format check runs before the build and the tests. It is the fastest step, and it needs no compile. The step names describe each command, so a failed step shows its purpose in the log.

The flag for the format check is `--verify-no-changes`. It reports a change instead of writing it, as lesson 1.4 showed.

`dotnet build` does not pass `-warnaserror`. `Directory.Build.props` already sets `TreatWarningsAsErrors` for every project, from lesson 1.2.

The `actions/checkout` and `actions/setup-dotnet` versions are the current major versions when this lesson is written. Check the major version on the GitHub Marketplace before you commit.

Expected: the file exists at `.github/workflows/ci.yml`. Nothing runs yet. The workflow starts when the branch has a pull request.

## Step 4. Push the branch and open a pull request

We commit the workflow, push the branch, and open a pull request into `main`. The first run of `ci` should be green. This is the first real check, and it runs on GitHub, not on our machine.

Run from the repository root:

```powershell
git add .github/workflows/ci.yml docs/Progress.md
git commit -m "Add CI workflow"
git push -u origin lesson-1.10
gh pr create --base main --head lesson-1.10 --title "Lesson 1.10: CI workflow" --body "Adds the ci workflow: restore, build, test, and format check on pull requests."
```

Expected: the push succeeds. The pull request opens, and the Checks tab shows a `ci` check. It runs the four steps and ends green. If `gh` is not signed in, open the pull request in the browser instead.

## Step 5. Red: break the format on purpose

A check that never fails proves nothing. We break the format on purpose, so we can see the format step block the pull request.

We change the indentation of one line in `Money.cs` from 8 spaces to 6. The build and the tests still pass, and only the format check fails.

`src/BuildingBlocks/BrickShare.SharedKernel/Money.cs` (change one line in the constructor)

Before:

```csharp
        Amount = amount;
```

After (6 spaces before `Amount`):

```csharp
      Amount = amount;
```

Commit and push the change. Run from the repository root:

```powershell
git add src/BuildingBlocks/BrickShare.SharedKernel/Money.cs
git commit -m "Break format on purpose to check the CI gate"
git push
```

Expected: red. The `ci` check fails at the step `Check format`. The `Restore` step is green. The `Build` and `Test` steps do not run, because GitHub skips the steps after a failed one. The log says that `dotnet format` needs a change in `Money.cs`. This is the right reason: the gate stops on the format before it compiles.

## Step 6. Green: restore the format

We revert the broken commit. A revert keeps the history, and the squash merge in lesson 1.11 drops both commits from `main`.

Run from the repository root:

```powershell
git revert --no-edit HEAD
git push
```

Expected: green. The new revert commit restores the line to 8 spaces. The `ci` check runs again and all four steps pass.

Check the file on disk:

```powershell
Select-String -Path src/BuildingBlocks/BrickShare.SharedKernel/Money.cs -Pattern "^        Amount = amount;"
```

Expected: one line of output, with 8 spaces before `Amount`.

## Result

Every pull request to `main` runs the `ci` check. The check restores the solution, verifies the format, builds it with warnings as errors, and runs the tests. Step 5 showed a failing format blocking the check. Step 6 showed the green state again.

The test command, as the workflow runs it:

```powershell
dotnet test BrickShare.slnx --no-restore --no-build
```

Expected: green, with no failed tests.

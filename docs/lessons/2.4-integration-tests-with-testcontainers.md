# Lesson 2.4. Integration tests with `WebApplicationFactory` and Testcontainers

Features: [F01](../features/01-catalog-management.md)
Previous: [2.3](2.3-ef-core-with-postgresql.md) · Next: 2.5 Authorization policies, development tokens with `dotnet user-jwts`, test tokens in the test project

## Summary

We add the `BrickShare.Catalog.Api.Tests` project. A factory starts the Catalog Api in memory and points it at a real PostgreSQL 18 container from Testcontainers. The tests call the liveness endpoint over HTTP, and they save a `LegoSet` and read it back through `CatalogDbContext`. At the end three integration tests are green, and the migration from lesson 2.3 runs in the test database.

## The problem

Lesson 2.3 maps `LegoSet` to a table, but no test runs that mapping. Without integration tests:

- Nothing proves that the migration creates `lego_sets`, or that a saved set comes back with the same values. A wrong mapping stays hidden until a running service fails.
- The liveness endpoint from lesson 2.1 runs only when someone starts the app by hand. A test that calls it through HTTP catches a broken startup, for example a missing connection string.
- The domain tests from lesson 2.2 use no database. They cannot find a column type or a conversion that EF Core gets wrong.

[Architecture.md section 7.2](../Architecture.md#72-testing-strategy-and-tdd) assigns these checks to integration tests: `WebApplicationFactory` and Testcontainers, from the HTTP endpoint to a real database. An in-memory database provider would hide the mapping problems that matter here, so the tests use PostgreSQL itself.

The feature rules that drive the tests:

- "The LEGO set number is digits only" and it is "searchable, not unique" ([Catalog management](../features/01-catalog-management.md#sets)). A test saves two sets with the same number.
- "Catalog gives every set and instance its own id" ([Catalog management](../features/01-catalog-management.md#sets)). A test saves a set with its id and reads it back with the same id.

The concepts we introduce:

- **`WebApplicationFactory<TEntryPoint>`.** It starts the Api in memory for each test class and gives the test an `HttpClient`. The test host is the real host, with the real middleware and routes.
- **Testcontainers.** The `PostgreSqlContainer` starts a PostgreSQL container for the test class and stops it at the end. Tests need Docker, but no shared database.
- **Class fixture.** `IClassFixture<T>` creates one factory per test class. `IAsyncLifetime` starts the container before the first test and disposes it after the last one.
- **Test-side migration.** The test host applies the checked-in migration with `Database.MigrateAsync()`, the same schema that every environment gets.

## Step 3. Red: the liveness check answers over HTTP

We start with the outside view. A test calls `GET /health/live` on the real Catalog Api and expects `200 OK`. The test needs a factory that starts the Api with a PostgreSQL container. The factory sets the connection string `catalog` for the test host, so the Api uses the container and not the local settings file.

The factory is a class of the test project. It needs a public type from the Api project to point at the Api. We use a marker type, `CatalogApi`, and it does not exist yet. The marker is needed for the test project to compile, so this compile error is the right reason for red. The marker does not expose `Program`: the factory finds the entry point through the assembly of the marker type.


`tests/Services/Catalog/BrickShare.Catalog.Api.Tests/CatalogApiFactory.cs` (replace the template file with this content)

```csharp
using System.Threading.Tasks;

using Microsoft.AspNetCore.Hosting;
using Microsoft.AspNetCore.Mvc.Testing;

using Testcontainers.PostgreSql;

using Xunit;

namespace BrickShare.Catalog.Api.Tests;

public sealed class CatalogApiFactory : WebApplicationFactory<CatalogApi>, IAsyncLifetime
{
    private readonly PostgreSqlContainer _postgres = new PostgreSqlBuilder("postgres:18").Build();

    public async ValueTask InitializeAsync()
    {
        await _postgres.StartAsync();
    }

    public override async ValueTask DisposeAsync()
    {
        await base.DisposeAsync();
        await _postgres.DisposeAsync();
    }

    protected override void ConfigureWebHost(IWebHostBuilder builder)
    {
        builder.UseSetting("ConnectionStrings:catalog", _postgres.GetConnectionString());
    }
}
```

## Step 4. Green: add the marker type to the Api project

`WebApplicationFactory<TEntryPoint>` takes a class from the Api assembly and uses that assembly's entry point to build the test host. The class can be any public class in the Api project. We add an empty marker class, so the test project can refer to the Api without `Program` becoming public. `Program.cs` does not change. The type is a class. The factory's type parameter must be a class, so an interface would not compile here.

The marker lives in the Api project root and uses the Api namespace.

Run from the repository root:

```powershell
dotnet new class -n CatalogApi -o src/Services/Catalog/BrickShare.Catalog.Api
```

Replace the template content of the file with the code below.

`src/Services/Catalog/BrickShare.Catalog.Api/CatalogApi.cs` (replace the template file with this content)

```csharp
namespace BrickShare.Catalog.Api;

// The class is empty on purpose. It only marks this assembly for WebApplicationFactory<T>,
// which needs a class type and finds the entry point through its assembly.
#pragma warning disable S2094 // Empty marker class: an interface does not satisfy the factory's class constraint.
public sealed class CatalogApi;
#pragma warning restore S2094
```

SonarAnalyzer reports rule `S2094` for an empty class, and warnings are errors. The class must stay empty, so we suppress the rule for this one declaration. The comment gives the reason, as the project rules require.

## Step 5. Red: a saved set comes back from PostgreSQL

Next we test the write and read path of the mapping from lesson 2.3. The test saves a `LegoSet` through `CatalogDbContext` in one scope, reads it in a second scope, and compares every field. Each scope gets its own context, so the read does not return the object the test still holds in memory.

The helper methods `SaveAsync` and `LoadAsync` each open a scope and a context. The helpers keep the two tests short.

Run from the repository root:

```powershell
dotnet new class -n LegoSetPersistenceTests -o tests/Services/Catalog/BrickShare.Catalog.Api.Tests
```

Replace the template content of the file with the code below.

`tests/Services/Catalog/BrickShare.Catalog.Api.Tests/LegoSetPersistenceTests.cs` (replace the template file with this content)

```csharp
using System;
using System.Linq;
using System.Threading.Tasks;

using AwesomeAssertions;

using BrickShare.Catalog.Api.Infrastructure.Persistence;
using BrickShare.Catalog.Domain;
using BrickShare.SharedKernel;

using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.DependencyInjection;

using Xunit;

namespace BrickShare.Catalog.Api.Tests;

public class LegoSetPersistenceTests(CatalogApiFactory factory) : IClassFixture<CatalogApiFactory>
{
    [Fact]
    public async Task Saved_set_is_read_back_with_the_same_values()
    {
        var legoSet = CreateSet("10294");
        await SaveAsync(legoSet);

        var stored = (await LoadAsync(legoSet.Id)).Single();

        stored.Id.Should().Be(legoSet.Id);
        stored.LegoSetNumber.Should().Be(new LegoSetNumber("10294"));
        stored.MinRentalDays.Should().Be(new MinRentalDays(3));
        stored.DailyPrice.Should().Be(new Money(1500, "EUR"));
        stored.Deposit.Should().Be(new Money(15000, "EUR"));
        stored.ReplacementValue.Should().Be(new Money(30000, "EUR"));
        stored.LateFeePerDay.Should().Be(new Money(500, "EUR"));
    }

    private async Task SaveAsync(params LegoSet[] legoSets)
    {
        await using var scope = factory.Services.CreateAsyncScope();
        var dbContext = scope.ServiceProvider.GetRequiredService<CatalogDbContext>();

        dbContext.LegoSets.AddRange(legoSets);
        await dbContext.SaveChangesAsync(TestContext.Current.CancellationToken);
    }

    private async Task<LegoSet[]> LoadAsync(params Guid[] ids)
    {
        await using var scope = factory.Services.CreateAsyncScope();
        var dbContext = scope.ServiceProvider.GetRequiredService<CatalogDbContext>();

        return await dbContext.LegoSets
            .Where(legoSet => ids.Contains(legoSet.Id))
            .ToArrayAsync(TestContext.Current.CancellationToken);
    }

    private static LegoSet CreateSet(string legoSetNumber) =>
        new(
            Guid.CreateVersion7(),
            new LegoSetNumber(legoSetNumber),
            new MinRentalDays(3),
            new Money(1500, "EUR"),
            new Money(15000, "EUR"),
            new Money(30000, "EUR"),
            new Money(500, "EUR"));
}
```

Run from the repository root, with Docker running:

```powershell
dotnet test --solution BrickShare.slnx
```

Expected: red. `Saved_set_is_read_back_with_the_same_values` fails, and the message contains `42P01: relation "lego_sets" does not exist`. The container starts and the schema is empty, because no migration runs yet. `Liveness_check_returns_ok` stays green.

## Step 6. Green: apply the migration in the test host

The test host must create the schema before the first test saves a set. We run the checked-in migration from lesson 2.3 in `InitializeAsync`, after the container starts. The migration lives in the Api project, and `MigrateAsync` applies every migration that the database does not have yet. This is the same schema that the other environments get.

The fixture uses `Services`, which starts the host. The container is already running at this point, so the host reads the container connection string.

`tests/Services/Catalog/BrickShare.Catalog.Api.Tests/CatalogApiFactory.cs` (replace the file with this content)

```csharp
using System.Threading.Tasks;

using BrickShare.Catalog.Api.Infrastructure.Persistence;

using Microsoft.AspNetCore.Hosting;
using Microsoft.AspNetCore.Mvc.Testing;
using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.DependencyInjection;

using Testcontainers.PostgreSql;

using Xunit;

namespace BrickShare.Catalog.Api.Tests;

public sealed class CatalogApiFactory : WebApplicationFactory<CatalogApi>, IAsyncLifetime
{
    private readonly PostgreSqlContainer _postgres = new PostgreSqlBuilder("postgres:18").Build();

    public async ValueTask InitializeAsync()
    {
        await _postgres.StartAsync();

        await using var scope = Services.CreateAsyncScope();
        var dbContext = scope.ServiceProvider.GetRequiredService<CatalogDbContext>();
        await dbContext.Database.MigrateAsync();
    }

    public override async ValueTask DisposeAsync()
    {
        await base.DisposeAsync();
        await _postgres.DisposeAsync();
    }

    protected override void ConfigureWebHost(IWebHostBuilder builder)
    {
        builder.UseSetting("ConnectionStrings:catalog", _postgres.GetConnectionString());
    }
}
```

Run from the repository root, with Docker running:

```powershell
dotnet test --solution BrickShare.slnx
```

Expected: green. `Saved_set_is_read_back_with_the_same_values` passes. The saved id, the number, the rental days, and each `Money` value come back equal to what was saved. This confirms the conversions from lesson 2.3 in a real database.

## Step 7. Guard: two sets can share one set number

The feature doc says the set number is searchable but not unique. Lesson 2.3 added no unique index, so this test passes at once. It is a guard, not a driver of new code: if someone later adds a unique index on the set number, this test fails.

The test saves two sets with the same number, then reads both back. The filter uses the ids, because the rule is about the number, not about the query. Add the test method after `Saved_set_is_read_back_with_the_same_values` in `LegoSetPersistenceTests.cs`. Its helpers and usings are already in the file.

`tests/Services/Catalog/BrickShare.Catalog.Api.Tests/LegoSetPersistenceTests.cs` (changed: add this method after the first test, before `SaveAsync`)

```csharp
    [Fact]
    public async Task Two_sets_can_share_one_lego_set_number()
    {
        var first = CreateSet("10294");
        var second = CreateSet("10294");
        await SaveAsync(first, second);

        var stored = await LoadAsync(first.Id, second.Id);

        stored.Should().HaveCount(2);
    }
```

Run from the repository root, with Docker running:

```powershell
dotnet test --solution BrickShare.slnx
```

Expected: green. All three Catalog Api tests pass: `Liveness_check_returns_ok`, `Saved_set_is_read_back_with_the_same_values`, and `Two_sets_can_share_one_lego_set_number`. This test passed on its first run, and that is expected here. The mapping from lesson 2.3 already has no unique index.

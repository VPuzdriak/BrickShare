# Lesson 3.3. Configuration through environment variables and `docker-compose.override.yml`

Previous: [3.2](3.2-docker-compose-postgres-azurite-catalog.md) · Next: 4.1 Workforce tenant: BrickShare API app registration, scope, app roles `Admin` and `Employee`

## Summary

We split `docker-compose.yml` into two files. The base file keeps the shape of the stack: images, build, volumes, health checks, and start order. The new `docker-compose.override.yml` holds the local settings: published ports and the connection settings for the emulators. The Rebrickable key comes from a `.env` file that Git ignores, and compose refuses to start without it. At the end, the same stack starts as in lesson 3.2, and no placeholder or secret sits in a committed file.

## The problem

Lesson 3.2 left two shortcuts in `docker-compose.yml`:

- The Rebrickable key is a placeholder. The Catalog starts with it, but every set lookup fails. A real key cannot go in the file, because the file is in Git.
- The ports and the emulator connection settings sit in the base file. Every developer, every CI job, and every future environment gets the same local values.

[Architecture 8](../Architecture.md#8-local-development) sets the rules:

> Connection strings for emulators come from `docker-compose.override.yml` environment variables.

and

> The Rebrickable API key comes from .NET user secrets locally.

A container cannot read the user secrets of the host. This lesson therefore gives compose the key through a `.env` file. `dotnet run` on your machine still uses user secrets, as in lesson 2.8g.

Concepts this lesson introduces:

- **Environment variables override configuration files.** .NET reads a `:` in a setting name as `__` in an environment variable name. `ConnectionStrings__catalog` sets `ConnectionStrings:catalog`. The container runs in the default `Production` environment, so `appsettings.Development.json` is not loaded there. The three Catalog settings must come from the environment.
- **Base file and override file.** `docker compose up` reads `docker-compose.yml`, then `docker-compose.override.yml` if it exists, and merges them. Maps such as `environment` merge by key. Lists such as `ports` are appended, so each port belongs in one file only.
- **Required variables.** `${REBRICKABLE_API_KEY:?message}` reads the variable from the shell or from `.env`, in the folder that holds `docker-compose.yml`. The `:?` form stops compose with the message when the variable is missing or empty. Without it, the Catalog starts with an empty key. An empty string is not `null`, so the check in `RebrickableRegistration.cs` passes.

Scope decisions:

- No init script yet. The `catalog` database comes from `POSTGRES_DB`, and the Catalog migrations create its tables. The other service databases do not exist until their services do. Each service lesson adds its own database, so the init script arrives with the first of them. The course plan title for this lesson still names init scripts. Update that title when the plan is revised.
- [Architecture 8](../Architecture.md#8-local-development) lists `pg_trgm` and `unaccent` for the init script. This lesson does not touch extensions. The `pg_trgm` extension already comes from the migration in lesson 2.15.

## Step 3. Refactor: move the local settings to the override file

Ports and emulator connection settings are local choices. We move them out of the base file into `docker-compose.override.yml`, which compose reads without a flag. The behavior stays the same, except that the Catalog port now binds to `127.0.0.1` like the other two. Only this machine reaches it.

`docker-compose.yml` (replace the whole file with this content)

```yaml
services:
  postgres:
    image: postgres:18
    environment:
      POSTGRES_DB: catalog
      POSTGRES_HOST_AUTH_METHOD: trust
    volumes:
      - postgres-data:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d catalog"]
      interval: 5s
      timeout: 3s
      retries: 10

  azurite:
    image: mcr.microsoft.com/azure-storage/azurite
    command: azurite-blob --blobHost 0.0.0.0 --location /data
    volumes:
      - azurite-data:/data

  catalog-api:
    build:
      context: .
      dockerfile: src/Services/Catalog/BrickShare.Catalog.Api/Dockerfile
    image: brickshare-catalog-api:local
    depends_on:
      postgres:
        condition: service_healthy
      azurite:
        condition: service_started

volumes:
  postgres-data:
  azurite-data:
```

The `ports` and `environment` blocks of the Catalog service are gone from the base file. The three ports and the three settings move to the new override file.

`docker-compose.override.yml` (new)

```yaml
services:
  postgres:
    ports:
      - "127.0.0.1:5432:5432"

  azurite:
    ports:
      - "127.0.0.1:10000:10000"

  catalog-api:
    ports:
      - "127.0.0.1:8080:8080"
    environment:
      ConnectionStrings__catalog: "Host=postgres;Database=catalog;Username=postgres"
      Rebrickable__ApiKey: placeholder-key
      Storage__BlobServiceUri: "http://azurite:10000/devstoreaccount1"
```

The `Rebrickable__ApiKey` line keeps the placeholder for now. Use `placeholder-key` as its value. Step 4 replaces it.

Run from the repository root:

```powershell
docker compose config --quiet
docker compose config | Select-String -Pattern 'published'
```

Expected: green. The file validates. The `Select-String` lines show three published ports: `"10000"`, `"8080"`, and `"5432"`. Compose lists the services alphabetically. The ports now come from the override file.

## Step 4. Green: the key must come from the environment

We replace the placeholder with a required variable. Compose reads the value from the environment when it renders the file.

Replace this line in `docker-compose.override.yml`, under `catalog-api`, `environment`. Before:

`docker-compose.override.yml` (before)

```yaml
      Rebrickable__ApiKey: placeholder-key
```

After:

`docker-compose.override.yml` (after)

```yaml
      Rebrickable__ApiKey: ${REBRICKABLE_API_KEY:?Set REBRICKABLE_API_KEY in the .env file}
```

Run from the repository root. `.env` does not exist yet.

```powershell
docker compose config --quiet
$LASTEXITCODE
```

Expected: green. Compose stops with `required variable REBRICKABLE_API_KEY is missing a value: Set REBRICKABLE_API_KEY in the .env file`, and `$LASTEXITCODE` is `1`. The stack now refuses to start without the key.

## Step 5. Green: put the key in `.env`

Compose reads a `.env` file from the folder that holds `docker-compose.yml` and fills in the variables from it. Git ignores the file, because the repository's `.gitignore` lists `.env` in its dotenv section.

Create your own Rebrickable key as in lesson 2.8g, step 1. Create `.env` in the repository root with one line. Replace the placeholder text with your key. Do not paste the key into a chat, a commit, or a shared file.

`.env` (new, local only, never committed)

```dotenv
REBRICKABLE_API_KEY=paste-your-rebrickable-key-here
```

Run from the repository root:

```powershell
git check-ignore -v .env
docker compose config --quiet
$LASTEXITCODE
```

Expected: green. `git check-ignore` prints one line that names `.gitignore` and `.env`, so Git does not stage the file. `docker compose config --quiet` validates the file, and `$LASTEXITCODE` is `0`.

Do not run `docker compose config` without `--quiet` here. The output prints the rendered key.

## Step 6. Green: the Catalog container gets its settings from the environment

We start the whole stack and check the container. Run from the repository root:

```powershell
docker compose up -d --build
docker compose ps
Invoke-WebRequest -UseBasicParsing -Uri http://localhost:8080/health/live | Select-Object StatusCode
docker inspect (docker compose ps -q catalog-api) --format '{{range .Config.Env}}{{println .}}{{end}}' | Select-String -Pattern '^(ConnectionStrings__catalog|Storage__BlobServiceUri)='
docker inspect (docker compose ps -q catalog-api) --format '{{range .Config.Env}}{{println .}}{{end}}' | Select-String -Pattern '^Rebrickable__ApiKey=' -Quiet
```

Expected: green. `docker compose ps` lists `postgres` (`healthy`), `azurite` (`Up`), and `catalog-api` (`Up`). `StatusCode` is `200`. The second-to-last command prints two lines: the connection string and the blob service URI. The last command prints `True`.

Keep the `-Quiet` switch. Without it, the command prints the key.

Failure guide: if `docker compose up` stops with `required variable REBRICKABLE_API_KEY is missing a value`, compose does not find the key. Check that `.env` is in the repository root and that the line has no typo and no space before the name. If `catalog-api` starts and then exits, run `docker compose logs catalog-api`.

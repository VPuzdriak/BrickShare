# Lesson 4.3. `BrickShare.Auth`: `Staff` and `Customer` schemes, policy scheme by issuer, role claim mapping

Features: [F03](../features/03-customer-accounts.md), [F04](../features/04-staff-management.md)
Previous: [4.2](4.2-external-id-customer-tenant.md) · Next: 4.4 Scalar with real sign-in

## Summary

We teach `BrickShare.Auth` to accept tokens from both Entra tenants. A policy scheme reads the issuer of each token and forwards the request to the `Staff` scheme or the `Customer` scheme. The `Customer` scheme adds the role `Customer` when a token is valid, and a new `CustomerOnly` probe proves it. The development issuer from lesson 2.5 goes with its test tokens and settings, so the Catalog Service has one way to check tokens. First, every test moves to Entra-shaped tokens. At the end all tests are green, and a token from `dotnet user-jwts` gets `401`.

## The problem

The Catalog Service accepts only tokens from the development issuer (lesson 2.5). Lessons 4.1 and 4.2 created the two tenants, but no code reads their tokens yet. The feature docs and the architecture set the rules:

- "Staff sign in with Microsoft Entra ID (workforce tenant)." ([F04](../features/04-staff-management.md))
- "Customers sign in with e-mail one-time passcode, Google, or Facebook through Microsoft Entra External ID." ([F03](../features/03-customer-accounts.md))
- "The user id is always the `oid` claim." ([F03](../features/03-customer-accounts.md))
- The `Staff` scheme accepts the issuer `https://login.microsoftonline.com/<tenant id>/v2.0` and the audience of the workforce BrickShare API. Its role claims come from `roles`. ([Architecture 5.2](../Architecture.md#52-token-validation-in-aspnet-core))
- The `Customer` scheme uses the authority of the External ID tenant. It adds the role `Customer` when a token is validated. ([Architecture 5.2](../Architecture.md#52-token-validation-in-aspnet-core))
- A policy scheme selects the handler from the token `iss` claim. The policies stay role-based, so they do not depend on the issuer. ([Architecture 5.2](../Architecture.md#52-token-validation-in-aspnet-core))

The concepts we introduce:

- **Policy scheme.** A scheme that chooses another scheme for each request. We set `ForwardDefaultSelector` to pick the handler. The handlers do the real work.
- **Reading is not validating.** The selector reads the `iss` claim without checking the signature. It only chooses a handler. The chosen handler checks the signature, the issuer, the audience, and the lifetime. A forged `iss` goes to the wrong handler and fails there.
- **Role claim mapping.** Entra puts the app roles in the `roles` claim. `RequireRole` reads the claim type set on the identity. Each Entra scheme sets `RoleClaimType` to `roles`, so the policies from lesson 2.5 keep working.
- **A role added in code.** Customers get no app role in the External ID tenant (lesson 4.2). The `Customer` scheme adds the role `Customer` when the token is valid.
- **Fail closed.** A token that the selector does not recognize goes to a handler that rejects it. The caller gets `401`.

Scope decisions:

- **JwtBearer, not Microsoft.Identity.Web.** The package `Microsoft.AspNetCore.Authentication.JwtBearer` is already in `BrickShare.Auth`. The validation and claim settings in this lesson are JwtBearer options. No new package is added.
- **Tenant values in `appsettings.json`.** The tenant ids, the issuers, and the client ids are not secrets. They go in `appsettings.json` with the other non-secret settings. No user secrets are used for them.
- **Fake tenants in tests.** No test calls Entra. The test host uses fake issuers and a test key, as the Rebrickable tests use a fake key and a fake provider (lesson 2.8c).
- **No real sign-in yet.** The first real Entra token comes with the sign-in client in lesson 4.4. This lesson checks the schemes with test tokens.
- **Tests move first.** Step 3 changes every test to Entra-shaped tokens while the development scheme still exists. The tests then fail, and the next steps make them pass.
- **The development issuer goes in step 4.** The new code has no development branch. Step 8 removes what is left of it: the test helper, the test host setting, and the settings and secrets of `dotnet user-jwts`.
- **`CustomerOnly` checks the role only.** The ban rule (`CustomerOnly` in [Architecture 5.2](../Architecture.md#52-token-validation-in-aspnet-core)) comes with the bans in lessons 5.3 and 5.4.

```csharp
using System.IdentityModel.Tokens.Jwt;
using System.Security.Claims;
using System.Text;

using Microsoft.IdentityModel.Tokens;

namespace BrickShare.Catalog.Api.Tests;

public static class EntraTestTokens
{
    public const string StaffIssuer = "https://login.microsoftonline.com/00000000-0000-0000-0000-0000000000a1/v2.0";
    public const string CustomerIssuer = "https://brickshare.ciamlogin.com/00000000-0000-0000-0000-0000000000c1/v2.0";
    public const string ClientId = "00000000-0000-0000-0000-0000000000b1";

    public static SymmetricSecurityKey SigningKey { get; } =
        new(Encoding.UTF8.GetBytes("entra-tests-signing-key-with-at-least-32-bytes"));

    public static string Staff(string role) =>
        Create(StaffIssuer, ClientId, new Claim("roles", role));

    public static string Customer() =>
        Create(CustomerIssuer, ClientId);

    public static string Create(string issuer, string audience, params Claim[] claims)
    {
        var credentials = new SigningCredentials(SigningKey, SecurityAlgorithms.HmacSha256);

        var token = new JwtSecurityToken(
            issuer: issuer,
            audience: audience,
            claims: [new Claim("oid", Guid.CreateVersion7().ToString()), .. claims],
            expires: DateTime.UtcNow.AddMinutes(10),
            signingCredentials: credentials);

        return new JwtSecurityTokenHandler().WriteToken(token);
    }
}
```

## Step 5. Green: the `Customer` scheme and the policy scheme

Now there are two schemes, so the default becomes the policy scheme `Token`. The policy scheme reads the issuer from the `Authorization` header. If the issuer is the customer authority, the request goes to the `Customer` scheme. Every other request goes to the `Staff` scheme, which refuses every issuer except the workforce one.

The `Customer` scheme takes the External ID authority and the client id of the customer tenant. Its validation parameters are the same as the `Staff` scheme. It has one event: when the token is valid, the scheme adds the role `Customer` to the identity. The role claim type is `roles`, the same as the `Staff` scheme, so `RequireRole` sees the new role.

`src/BuildingBlocks/BrickShare.Auth/AuthenticationExtensions.cs` (replace the file with this content)

```csharp
using System.IdentityModel.Tokens.Jwt;
using System.Security.Claims;

using Microsoft.AspNetCore.Authentication;
using Microsoft.AspNetCore.Authentication.JwtBearer;
using Microsoft.Extensions.Configuration;
using Microsoft.Extensions.DependencyInjection;

namespace BrickShare.Auth;

public static class AuthenticationExtensions
{
    public static IServiceCollection AddBrickShareAuthentication(
        this IServiceCollection services,
        IConfiguration configuration)
    {
        var customerAuthority = configuration["Authentication:Customer:Authority"];

        services.AddAuthentication(Schemes.Token)
            .AddPolicyScheme(Schemes.Token, "Staff or customer token", options =>
            {
                options.ForwardDefaultSelector = context =>
                    SelectScheme(context.Request.Headers.Authorization.ToString(), customerAuthority);
            })
            .AddJwtBearer(Schemes.Staff, options =>
            {
                options.Authority = configuration["Authentication:Staff:Authority"];
                options.Audience = configuration["Authentication:Staff:Audience"];
                options.MapInboundClaims = false;
                options.TokenValidationParameters.RoleClaimType = "roles";
            })
            .AddJwtBearer(Schemes.Customer, options =>
            {
                options.Authority = customerAuthority;
                options.Audience = configuration["Authentication:Customer:Audience"];
                options.MapInboundClaims = false;
                options.TokenValidationParameters.RoleClaimType = "roles";
                options.Events = new JwtBearerEvents { OnTokenValidated = AddCustomerRole };
            });

        return services;
    }

    private static string SelectScheme(string authorization, string? customerAuthority)
    {
        const string bearerPrefix = "Bearer ";

        if (!authorization.StartsWith(bearerPrefix, StringComparison.OrdinalIgnoreCase))
        {
            return Schemes.Staff;
        }

        var token = authorization[bearerPrefix.Length..];
        var tokenReader = new JwtSecurityTokenHandler();

        if (!tokenReader.CanReadToken(token))
        {
            return Schemes.Staff;
        }

        var issuer = tokenReader.ReadJwtToken(token).Issuer;

        if (issuer is not null && issuer == customerAuthority)
        {
            return Schemes.Customer;
        }

        return Schemes.Staff;
    }

    private static Task AddCustomerRole(TokenValidatedContext context)
    {
        var identity = (ClaimsIdentity)context.Principal!.Identity!;
        identity.AddClaim(new Claim(identity.RoleClaimType, "Customer"));

        return Task.CompletedTask;
    }
}
```

The null check on `issuer` matters. A token with no `iss` claim gives `null`. Without the check, `null` would equal an authority that is not configured, and the token would reach the wrong scheme.

## Step 7. Refactor: separate reading the issuer from choosing the scheme

The selector now does two jobs. It reads the header and the token, and it chooses the scheme. We split them, so each method has one job. The name `ReadUnverifiedIssuer` says that the read is not validation. The handler validates the token later. The token reader becomes one shared instance, so each request does not create a new handler.


Replace `SelectScheme` with this method, and add `ReadUnverifiedIssuer` after it:

```csharp
    private static string SelectScheme(string authorization, string? customerAuthority)
    {
        var issuer = ReadUnverifiedIssuer(authorization);

        if (issuer is not null && issuer == customerAuthority)
        {
            return Schemes.Customer;
        }

        return Schemes.Staff;
    }

    private static string? ReadUnverifiedIssuer(string authorization)
    {
        if (!authorization.StartsWith(BearerPrefix, StringComparison.OrdinalIgnoreCase))
        {
            return null;
        }

        var token = authorization[BearerPrefix.Length..];

        return TokenReader.CanReadToken(token) ? TokenReader.ReadJwtToken(token).Issuer : null;
    }
```

## Result

`BrickShare.Auth` accepts tokens from the workforce tenant and from the customer tenant. A policy scheme reads the issuer. Tokens from the customer tenant go to the `Customer` scheme. Every other token goes to the `Staff` scheme, which accepts only the workforce issuer. Any other token gets `401`.

The `Staff` scheme checks the workforce issuer and the BrickShare API audience. It reads the roles from `roles`. The `Customer` scheme checks the customer issuer and audience. When its token is valid, it adds the role `Customer`. The policy `CustomerOnly` requires that role.

The development issuer is gone. The `Bearer` scheme, the `UseDevelopmentIssuer` setting, the `dotnet user-jwts` signing key, and the `TestTokens` helper are removed. Every test uses an Entra-shaped test token.

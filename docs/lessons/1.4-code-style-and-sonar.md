# Lesson 1.4. Code style: `.editorconfig`, SonarAnalyzer, `dotnet format`

Previous: [1.3](1.3-central-package-management.md) · Next: 1.5 Test projects with xUnit v3 and AwesomeAssertions

## Summary

We add one root `.editorconfig` that sets the code style for the whole repository. We turn on `AnalysisLevel` and `EnforceCodeStyleInBuild` in `Directory.Build.props`, so style rules run during the build. We add SonarAnalyzer as a `GlobalPackageReference` in `Directory.Packages.props`, so every project gets the same bug and smell checks. A probe project shows each rule fail and then pass. We delete the probe at the end. The first test packages (xUnit v3 and AwesomeAssertions) arrive in lesson 1.5.

## The problem

Right now, the repository has shared build settings and central package versions, but no code style rules and no code analysis. Without them:

- Each author indents, names, and wraps code in a different way. The course code looks like many projects, not one.
- A style problem is found only by a reviewer, if at all. Nothing in the build or in CI checks it.
- Common bugs compile without a warning. A `double` compared with `==` is one example. Students then copy this pattern into the course code.
- A formatter that is not run leaves diffs that hide the real change in a pull request.

For BrickShare, [CLAUDE.md](../../CLAUDE.md) says that code style comes from the root `.editorconfig`, that warnings are fixed and not suppressed, and that `dotnet format` runs before a change is finished. [Architecture.md section 7](../Architecture.md#7-solution-structure) places `.editorconfig` at the root, and [section 7.3](../Architecture.md#73-directorybuildprops) and [section 7.4](../Architecture.md#74-directorypackagesprops) show the build and package settings. CI runs `dotnet format --verify-no-changes` and the build with Sonar rules in [section 10.2](../Architecture.md#102-workflows). Lesson 1.10 adds that CI step. This lesson has no business rule from `docs/features/`.

The concepts:

- **`.editorconfig`** is a text file that editors and `dotnet format` read. It sets indentation, line endings, and the severity of code style rules. A file at the root applies to every file below it.
- **Analyzers** are rules that run during the build. SonarAnalyzer adds rules for bugs, code smells, and security issues. `AnalysisLevel` turns on the standard Roslyn analyzers. `EnforceCodeStyleInBuild` makes the `.editorconfig` style rules run during the build too.
- **`dotnet format`** rewrites files so they match `.editorconfig`. With `--verify-no-changes` it does not write anything. It fails when a change is needed, so CI can use it as a check.

The probe in this lesson has no business meaning. It is a small class with a `double` comparison. The probe is the failing check for each step, the same way lessons 1.2 and 1.3 used probes. We delete it at the end.

## Step 2. Generate the root .editorconfig with the .NET CLI

We do not write `.editorconfig` by hand. The .NET SDK has a template that writes a default file with the rules the .NET team recommends. We run it at the repository root. The file it writes is about 390 lines long. Most of it is the template default, so this lesson shows only the keys that we change.

Run from the repository root:

```powershell
dotnet new editorconfig
```

Expected: the CLI prints `The template "EditorConfig file" was created successfully.` and creates `.editorconfig` at the root.

The template default does not match the course. We change the `[*]` section and one line in `[*.cs]`:

- In the `[*]` section, add these four lines after `indent_style = space`:

  ```ini
  charset = utf-8
  end_of_line = lf
  insert_final_newline = true
  trim_trailing_whitespace = true
  ```

- In the `[*.cs]` section, delete the line `insert_final_newline = false`. Without it, the `[*]` value applies to C# files too.
- In the `[*.cs]` section, change `csharp_style_namespace_declarations = file_scoped:suggestion` to `csharp_style_namespace_declarations = file_scoped:warning`. A block namespace then fails the build, not only an editor hint.
- Leave `indent_size = 4` for `[*.cs]` and `indent_size = 2` for the MSBuild XML sections as the template sets them.

The keys that matter for this course are:

- `root = true` stops the editor from looking for more `.editorconfig` files above the repository. The template sets it.
- `indent_size = 4` for `*.cs` is the size that `dotnet format` enforces for C#.
- `csharp_style_namespace_declarations = file_scoped:warning` makes a block namespace a warning. `file_scoped` is the form used in every probe and course file.
- `csharp_new_line_before_open_brace = all` puts each opening brace on its own line. The template sets it.

The rules are not checked yet. The build does not read `.editorconfig` style rules until step 5. `dotnet format` reads the indentation and line endings now.

## Step 3. Create a probe with the wrong indentation and see the check fail

We make a probe project in a `probe/` folder at the repository root. It contains one class with a `double` comparison. We indent the class with two spaces, which the `.editorconfig` forbids for C#. We delete the probe in step 8.

`probe/StyleProbe/StyleProbe.csproj`

```xml
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>Library</OutputType>
  </PropertyGroup>

</Project>
```

`probe/StyleProbe/Probe.cs`

```csharp
namespace StyleProbe;

public static class Probe
{
  public static bool AreEqual(double first, double second)
  {
    return first == second;
  }
}
```

Run from the repository root:

```powershell
dotnet format --verify-no-changes probe/StyleProbe
```

Expected: red. The command exits with a non-zero code. It reports that `Probe.cs` needs a change. The change is the indentation: two spaces where `.editorconfig` asks for four. The `==` line is not a problem for this check yet. SonarAnalyzer comes in step 6.

## Step 4. Fix the format with dotnet format

We let the formatter make the change. We do not edit the indentation by hand. The formatter writes the four-space indentation into `Probe.cs`. The file otherwise stays the same.

Run from the repository root:

```powershell
dotnet format probe/StyleProbe
dotnet format --verify-no-changes probe/StyleProbe
```

Expected: the first command writes the change and exits with code 0. The second command reports no changes and exits with code 0. This is green. Open `probe/StyleProbe/Probe.cs` to check that the method body now uses four spaces.

## Step 5. Turn on analyzers and code style in the build

We add two settings to `Directory.Build.props`. `AnalysisLevel` turns on the standard .NET analyzers. We set it to `10.0-recommended`: the .NET 10 rule set, with the recommended severity bucket. `EnforceCodeStyleInBuild` makes the `.editorconfig` style rules part of the build. With `TreatWarningsAsErrors` from lesson 1.2, a style warning now fails the build.

Why a number and not `latest-recommended`: `latest` means "the newest analyzer set that the installed SDK knows". The rule set then changes each time the SDK is upgraded, so a build can start to fail with no code change. A version number such as `10.0` pins the rule set to .NET 10. The suffix `-recommended` keeps the severity bucket. On the SDK used for this course, `latest-recommended` resolves to `9.0`, and `10.0-recommended` resolves to `10.0`. You can check this yourself:

```powershell
dotnet msbuild probe/StyleProbe/StyleProbe.csproj -getProperty:EffectiveAnalysisLevel -p:AnalysisLevel=latest-recommended
dotnet msbuild probe/StyleProbe/StyleProbe.csproj -getProperty:EffectiveAnalysisLevel -p:AnalysisLevel=10.0-recommended
```

Expected: the first command prints `9.0`, and the second prints `10.0`. The probe must exist, which it does after step 3. Lesson 1.4 uses the pinned value from here on.

`Directory.Build.props`

```xml
<Project>

  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <Nullable>enable</Nullable>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
    <AnalysisLevel>10.0-recommended</AnalysisLevel>
    <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
  </PropertyGroup>

</Project>
```

This replaces the `PropertyGroup` from lesson 1.2. The first three lines are unchanged. The two new lines come after `TreatWarningsAsErrors`.

Run from the repository root:

```powershell
dotnet build probe/StyleProbe
```

Expected: green. The probe is already formatted from step 4, and it has no code that breaks the new analyzer or style rules yet. The `==` comparison is not flagged, because SonarAnalyzer is still missing.

## Step 6. Add SonarAnalyzer as a global package and see it fail

We add SonarAnalyzer to `Directory.Packages.props` with `GlobalPackageReference`. This item adds the package to every project in the solution, so no project file needs its own reference. The `Version` is allowed here because this file is the only place for versions, as lesson 1.3 requires.

Use the newest stable SonarAnalyzer.CSharp version from nuget.org. The version below is the newest one in the local NuGet cache when this lesson was written.

`Directory.Packages.props`

```xml
<Project>

  <PropertyGroup>
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
    <CentralPackageTransitivePinningEnabled>true</CentralPackageTransitivePinningEnabled>
  </PropertyGroup>

  <ItemGroup>
    <GlobalPackageReference Include="SonarAnalyzer.CSharp" Version="10.36.0.15337" />
  </ItemGroup>

</Project>
```

This adds the `ItemGroup` with the `GlobalPackageReference`. The file has no `PackageVersion` entries yet.

Run from the repository root:

```powershell
dotnet build probe/StyleProbe
```

Expected: red. The build fails with `error S1244: Floating point numbers should not be tested for equality`. The Sonar analyzer warns on the `==` comparison, and `TreatWarningsAsErrors` turns that warning into a build error. The rule works. The fix is in the code, not in a suppression.

## Step 7. Fix the probe without suppressing the rule

We change the comparison so it does not test two `double` values for equality. The method checks whether the difference is smaller than a small tolerance. The tolerance is a `const`, so the number has a name. We add `using System;` because `Math` needs it. Implicit usings are not enabled in this course.

The whole file is shown. It replaces the current `Probe.cs`. The `AreEqual` method keeps its name and signature. The body changes from `return first == second;` to a tolerance check.

`probe/StyleProbe/Probe.cs`

```csharp
using System;

namespace StyleProbe;

public static class Probe
{
    private const double Tolerance = 0.000001;

    public static bool AreEqual(double first, double second)
    {
        return Math.Abs(first - second) < Tolerance;
    }
}
```

A suppression such as `#pragma warning disable S1244` or `[SuppressMessage]` is not allowed. [CLAUDE.md](../../CLAUDE.md) requires a justification comment for any suppression, and this course has no case that needs one.

Run from the repository root:

```powershell
dotnet build probe/StyleProbe
```

Expected: green. The build succeeds with no warnings.

## Step 8. Remove the probe and commit the settings

The probe was only a check, so it must not reach the repository. We delete it, and then we check the working tree. We commit the three files that this lesson changed.

Run from the repository root:

```powershell
Remove-Item -Recurse -Force probe
git status --short
```

Expected: `git status --short` lists `.editorconfig` as a new file, and `Directory.Build.props` and `Directory.Packages.props` as modified. It shows no `probe/` folder. The `bin/` and `obj/` folders are ignored by `.gitignore`, and they are gone with the probe. `docs/Progress.md` may still show as modified. Leave it for the lesson workflow.

Run from the repository root:

```powershell
git add .editorconfig Directory.Build.props Directory.Packages.props
git commit -m "Add code style and SonarAnalyzer"
```

Expected: Git reports one commit with three files changed. `git status` then shows only the `docs/Progress.md` change, if it is still open.

## Result

What works now:

- The root `.editorconfig` sets the same encoding, line endings, and indentation for every file in the repository.
- `AnalysisLevel` and `EnforceCodeStyleInBuild` make the analyzer and style rules part of the build.
- SonarAnalyzer runs on every project through `GlobalPackageReference`. A Sonar warning fails the build, as step 6 showed.
- `dotnet format --verify-no-changes` reports a clean format for the probe. Step 3 showed the failure, and step 4 showed the fix.

There are no tests yet. The first red-green cycle with a unit test starts in lesson 1.5. The repository has no projects in `BrickShare.slnx` yet, so `dotnet format` and the build run on a project path, not on the solution. Lesson 1.10 runs both on the solution in CI.

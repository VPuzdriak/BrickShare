# Lesson 5.1. Customer Service projects, `Customer` aggregate, just-in-time provisioning

Features: [F03](../features/03-customer-accounts.md)
Previous: [4.4](4.4-scalar-with-real-sign-in.md) · Next: 5.2 Profile update, staff customer search

## Summary

We create the Customer Service. It has a Domain project with the `Customer` aggregate and an Api project with a PostgreSQL `DbContext`, a migration, and a liveness check. The endpoint `GET /customers/me` is restricted to the `CustomerOnly` policy. On the first call with a valid customer token, the endpoint creates the customer from the token claims. Later calls return the same customer. At the end the Domain tests and the Api tests are green.

## The problem

The repository has a Catalog Service and the shared authentication. It has no Customer Service. `BrickShare.Auth` already defines the `CustomerOnly` policy and the `Customer` token scheme (lesson 4.3), but no endpoint uses them. Customers have no profile, so the reservation work in module 6 has no customer to refer to.

The feature doc and the architecture set the rules for this lesson:

- "On the first call with a valid customer token, the service creates the `Customer` record (just-in-time provisioning from token claims) and publishes `CustomerRegistered`." ([F03](../features/03-customer-accounts.md))
- "The user id is always the `oid` claim. Customer-facing endpoints never take a customer id from the route. They read it from the token." ([F03](../features/03-customer-accounts.md), [Architecture 5.2](../Architecture.md#52-token-validation-in-aspnet-core))
- The `Customer` model has `Id` (External ID object id), `Email`, `DisplayName`, `Phone`, `CreatedAt`, and `Status`. ([Architecture 3.6](../Architecture.md#36-customer-service))
- The Customer Service uses PostgreSQL, database `customers`. ([Architecture 6](../Architecture.md#6-data-ownership))

The concepts we introduce:

- **Aggregate root.** `Customer` derives from `AggregateRoot<Guid>` from the shared kernel. Its id is the `oid` claim. Later lessons add the ban rules to it ([Architecture 7.1](../Architecture.md#71-domain-driven-design)).
- **Just-in-time provisioning.** The handler loads the customer by the `oid` claim. If no row exists, it creates the customer from the token claims and saves it. The handler does this in one transaction, and the aggregate holds the data.
- **Identity from the token.** The endpoint reads the id from the token only. The route has no customer id.
- **Route group policy.** The `/customers` group declares `CustomerOnly` on the group, as [CLAUDE.md](../../CLAUDE.md) requires.

Scope decisions for this lesson:

- **A GET creates the row.** The first call with a valid token creates the customer, as [F03](../features/03-customer-accounts.md) requires. The alternative, a separate `POST /customers`, adds a client step. Simultaneous first calls can fail with a duplicate key, because the handler has no conflict handling. Step 11 explains the reasons.
- **No `CustomerRegistered` event yet.** The feature rule names it, but the outbox and the mapping from domain events to integration events come in lessons 7.3 and 7.5. This lesson creates the customer, and it raises no event.
- **No `Phone` and no `Status`.** The profile update (lesson 5.2) and the bans (lesson 5.3) add them.
- **Namespaces use `BrickShare.Customers`, not `BrickShare.Customer`.** The aggregate is named `Customer`. Under a namespace `BrickShare.Customer.Api`, the name `Customer` resolves to the namespace `BrickShare.Customer` before it reaches the aggregate, and the compiler reports CS0118. The plural avoids the clash.
- **Development only for Scalar.** The Scalar UI is mapped in Development only, as [Architecture 11](../Architecture.md#11-cross-cutting-concerns) requires. The document has no sign-in scheme yet. Customer sign-in in Scalar is not in the course plan, so this lesson checks the endpoint with integration tests and with unauthenticated probes.
- **The migration runs at startup in Development.** [Architecture 8](../Architecture.md#8-local-development) says so for every service. The Catalog Service does not do it yet.

## Step 5. Green: the `Customer` aggregate

The aggregate is the smallest class that passes the test. It derives from `AggregateRoot<Guid>`, so the id comes from the base class. The constructor takes the values from the token and the creation time from the caller. The domain never reads the clock, as [Architecture 7.1](../Architecture.md#71-domain-driven-design) requires.

The private parameterless constructor is for EF Core. EF Core uses it to create an empty customer when it reads a row. It calls the public constructor with empty values, and EF Core then sets the stored values through the private setters. This is the same pattern as `LegoSet` in the Catalog Domain.

`src/Services/Customers/BrickShare.Customers.Domain/Customer.cs` (new file)

Create the file with the CLI, then replace the template content with the code below:

```powershell
dotnet new class -n Customer -o src/Services/Customers/BrickShare.Customers.Domain
```

```csharp
using System;

using BrickShare.SharedKernel;

namespace BrickShare.Customers.Domain;

public sealed class Customer : AggregateRoot<Guid>
{
    private Customer()
        : this(Guid.Empty, string.Empty, string.Empty, default)
    {
    }

    public Customer(Guid id, string email, string displayName, DateTimeOffset createdAt)
        : base(id)
    {
        Email = email;
        DisplayName = displayName;
        CreatedAt = createdAt;
    }

    public string Email { get; private set; }

    public string DisplayName { get; private set; }

    public DateTimeOffset CreatedAt { get; private set; }
}
```

Run from the repository root:

```powershell

```

`src/Services/Customers/BrickShare.Customers.Api/Infrastructure/Persistence/CustomerDbContext.cs` (replace the template class with this content)

```csharp
using BrickShare.Customers.Domain;

using Microsoft.EntityFrameworkCore;

namespace BrickShare.Customers.Api.Infrastructure.Persistence;

public sealed class CustomerDbContext(DbContextOptions<CustomerDbContext> options) : DbContext(options)
{
    public DbSet<Customer> Customers => Set<Customer>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.ApplyConfigurationsFromAssembly(typeof(CustomerDbContext).Assembly);
    }
}
```

`src/Services/Customers/BrickShare.Customers.Api/Infrastructure/Persistence/CustomerConfiguration.cs` (replace the template class with this content)

```csharp
using BrickShare.Customers.Domain;

using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Metadata.Builders;

namespace BrickShare.Customers.Api.Infrastructure.Persistence;

public sealed class CustomerConfiguration : IEntityTypeConfiguration<Customer>
{
    public void Configure(EntityTypeBuilder<Customer> builder)
    {
        builder.ToTable("customers");

        builder.HasKey(customer => customer.Id);

        builder.Property(customer => customer.Id)
            .ValueGeneratedNever()
            .HasColumnName("id");

        builder.Property(customer => customer.Email)
            .HasColumnName("email");

        builder.Property(customer => customer.DisplayName)
            .HasColumnName("display_name");

        builder.Property(customer => customer.CreatedAt)
            .HasColumnName("created_at");

        builder.Ignore(customer => customer.DomainEvents);
    }
}
```

The id is never generated by the database, because the `oid` claim provides it. So `ValueGeneratedNever` is set.

public static class ClaimsPrincipalExtensions

    public static Guid CustomerId(this ClaimsPrincipal user) =>
        Guid.Parse(user.FindFirst("oid")?.Value ?? throw new InvalidOperationException("The token has no oid claim."));
}
```

The endpoint creates the customer on the first GET, and it is not a separate sign-up call. The reasons:

- The customer signs up in External ID, not in BrickShare. External ID issues the token, and the service sees the sign-up only through the token claims.
- The first authenticated call is the first moment the service can create the row. A separate `POST /customers` would add a client step that every sign-in must remember.
- The reservation work in module 6 needs a `Customer` row to refer to. The row exists as soon as the customer first uses the API.

The trade-off is that a GET writes to the database. Later calls return the same row, so repeated calls are safe. A first call that runs at the same time as another first call can fail with a duplicate key. The scope notes at the top of this lesson name this gap.

Next, the handler. It finds the customer by the id from the token. If no row exists, it creates the customer from the `email` and `name` claims, with the current time from `TimeProvider`, and saves it. Then it returns the profile. The handler does not change an existing customer. The profile update comes in lesson 5.2.

The handler uses the aggregate's constructor. The aggregate holds the data, and the handler only loads and saves it, as [Architecture 7.1](../Architecture.md#71-domain-driven-design) describes.

using System;
using System.Security.Claims;
using System.Threading;
using System.Threading.Tasks;

using BrickShare.Customers.Api.Infrastructure.Identity;
using BrickShare.Customers.Api.Infrastructure.Persistence;
using BrickShare.Customers.Domain;

using Microsoft.AspNetCore.Builder;
using Microsoft.AspNetCore.Http;
using Microsoft.AspNetCore.Http.HttpResults;
using Microsoft.AspNetCore.Routing;
using Microsoft.EntityFrameworkCore;

namespace BrickShare.Customers.Api.Features.Customers.GetProfile;

public static class GetProfile
{
    public static void MapGetProfile(this RouteGroupBuilder customers) =>
        customers.MapGet("/me", Handle);

    private static async Task<Ok<CustomerProfileResponse>> Handle(
        ClaimsPrincipal user,
        CustomerDbContext dbContext,
        TimeProvider timeProvider,
        CancellationToken cancellationToken)
    {
        var customerId = user.CustomerId();

        var customer = await dbContext.Customers.FirstOrDefaultAsync(
            candidate => candidate.Id == customerId, cancellationToken);

        if (customer is null)
        {
            customer = new Customer(
                customerId,
                user.FindFirst("email")?.Value ?? string.Empty,
                user.FindFirst("name")?.Value ?? string.Empty,
                timeProvider.GetUtcNow());

            dbContext.Customers.Add(customer);
            await dbContext.SaveChangesAsync(cancellationToken);
        }

        return TypedResults.Ok(new CustomerProfileResponse(
            customer.Id, customer.Email, customer.DisplayName, customer.CreatedAt));
    }
}
```

The `email` and `name` claims are standard OpenID Connect claims. The endpoint reads them without a check, because the profile update in lesson 5.2 lets the customer change them. A token without these claims creates a customer with an empty e-mail address and an empty name.

The route group is the last file. It declares `CustomerOnly` on the whole `/customers` group, so every endpoint of the group needs the customer role. The endpoint is registered in it.

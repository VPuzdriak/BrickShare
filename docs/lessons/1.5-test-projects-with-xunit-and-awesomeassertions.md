# Lesson 1.5. Test projects with xUnit v3 and AwesomeAssertions

Previous: [1.4](1.4-code-style-and-sonar.md) · Next: 1.6 Shared kernel: `Entity`, `AggregateRoot`, `ValueObject`, domain events, results

## Summary

We add the test packages, xUnit v3 and AwesomeAssertions, to `Directory.Packages.props`. We then run one full red-green-refactor cycle on a small probe class. Each test fails first, then passes after the smallest code change. We delete the probe at the end, and the package versions stay in the central file for lesson 1.6.

## The problem

Right now, the repository has build rules, code style, and analyzers, but no test. Without a test project and an assertion library:

- Nothing checks that a rule works. A business rule can change and no build fails.
- The course has no first red-green-refactor cycle. Students see the rules in [CLAUDE.md](../../CLAUDE.md), but they do not run them.
- Each test project could pick its own packages and versions. [Lesson 1.3](1.3-central-package-management.md) stops that for versions, but not for the choice of library.

For BrickShare, [CLAUDE.md](../../CLAUDE.md) sets the test stack: domain unit tests use xUnit v3 and AwesomeAssertions, with no mocks. Test names describe behavior, such as `Pickup_fails_when_deposit_is_not_secured`. [Architecture.md section 7.2](../Architecture.md#72-testing-strategy-and-tdd) describes the test levels and the TDD rule. Lesson 1.5 covers the unit test level only. This lesson has no business rule from `docs/features/`, so the probe rule is a teaching example.

The concepts:

- **xUnit v3** is the test framework. A method with `[Fact]` is one test. The test passes when it returns without an exception. The Microsoft Testing Platform lets `dotnet test` find and run the tests. The solution opts in through `global.json` (step 3).
- **AwesomeAssertions** is the assertion library. It adds `Should()` to values, so a test reads as a sentence: `result.Should().Be(10)`. A failed assertion reports the expected and the actual value.
- **Why AwesomeAssertions and not FluentAssertions.** FluentAssertions is the library with the same `Should()` syntax. Version 8 and later need a commercial license, so the course does not use it. AwesomeAssertions is a community fork of the last free line, FluentAssertions 7. It has the same syntax and an open source license, Apache-2.0. The course code and the examples that students find online use the same calls. [Architecture.md section 7.2](../Architecture.md#72-testing-strategy-and-tdd) records this decision.
- **Red-green-refactor** is the TDD cycle. Red: a test fails for the right reason. Green: the simplest code makes it pass. Refactor: the code gets cleaner, and the tests stay green.

## Step 2. Create the probe library

We make a probe in a `probe/` folder at the repository root. It has two projects: the class under test, and the test project. The probe has no business meaning. We delete the whole folder in step 9.

The library starts with no code. An empty class does not build: SonarAnalyzer rule S2094 reports it, and warnings are errors. The test in step 4 uses a class that does not exist yet, so it cannot compile. That gives the first red.

We create the project with the .NET CLI, then remove the parts the repository does not use. Run from the repository root:

```powershell
dotnet new classlib -n Probe -o probe/Probe
```

The template writes `probe/Probe/Probe.csproj` and an empty `Class1.cs`. SonarAnalyzer rejects the empty class, so we delete `probe/Probe/Class1.cs`. The project file also sets `TargetFramework`, `ImplicitUsings`, and `Nullable`. `Directory.Build.props` already sets the target framework and nullable, and the course uses explicit `using` lines. We delete the whole `PropertyGroup`.

`probe/Probe/Probe.csproj`, before:

```xml
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>

</Project>
```

`probe/Probe/Probe.csproj`, after:

```xml
<Project Sdk="Microsoft.NET.Sdk">

</Project>
```

Run from the repository root:

```powershell
dotnet build probe/Probe
```

Expected: green. The library builds with no warnings.

## Step 3. Create the test project and add the packages

The test project references the library. It has no `Version` on any package. The versions come from `Directory.Packages.props`, as lesson 1.3 requires.

We write the project file by hand. The repository's `global.json` pins the 10.0.100 SDK, and the xUnit template of that SDK has no `--xunit-version` option. Run `dotnet new xunit` in this repository and it writes xUnit v2 with the VSTest packages `Microsoft.NET.Test.Sdk` and `xunit.runner.visualstudio`. The course uses xUnit v3 on the Microsoft Testing Platform, so the template cannot produce this project.

`probe/Probe.Tests/Probe.Tests.csproj`

```xml
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <IsPackable>false</IsPackable>
    <IsTestProject>true</IsTestProject>
    <OutputType>Exe</OutputType>
  </PropertyGroup>

  <ItemGroup>
    <ProjectReference Include="../Probe/Probe.csproj" />
  </ItemGroup>

</Project>
```

xUnit v3 runs on the Microsoft Testing Platform. The .NET 10 SDK refuses the old VSTest runner, so the `OutputType` of `Exe` is required and the solution opts in to the platform in `global.json`. The `xunit.runner.visualstudio` adapter is for the VSTest runner, so the course does not use it. Architecture.md section 7.4 lists no runner package, which matches.

`global.json` already exists from lesson 1.1, so `dotnet new globaljson` does not apply. We add the platform opt-in by hand:

`global.json`

```json
{
  "sdk": {
    "version": "10.0.100",
    "rollForward": "latestFeature"
  },
  "test": {
    "runner": "Microsoft.Testing.Platform"
  }
}
```

Without this block, `dotnet test` stops with the error `Testing with VSTest target is no longer supported by Microsoft.Testing.Platform on .NET 10 SDK and later`.

Now we add the two packages with the .NET CLI. With central package management on, `dotnet add package` writes the version into `Directory.Packages.props` and leaves the `Version` out of the project file. We do not type a version by hand. The CLI uses the newest stable version on nuget.org.

Run from the repository root:

```powershell
dotnet add probe/Probe.Tests package xunit.v3
dotnet add probe/Probe.Tests package AwesomeAssertions
```

Expected: each command reports `PackageReference for package ... added`. Then open `Directory.Packages.props`. It now has two `PackageVersion` entries next to the `GlobalPackageReference` from lesson 1.4. Open `probe/Probe.Tests/Probe.Tests.csproj`. Its `PackageReference` items have no `Version` attribute.

The CLI also rewrites the layout of `Directory.Packages.props`. It changes the indent to two spaces, puts each element on its own line, removes the blank lines, and drops the final newline. The diff touches every line of the file. This is the CLI's output, so keep it.

Run from the repository root:

```powershell
dotnet build probe/Probe.Tests
```

Expected: green. The build restores the two packages. There are no tests yet, so the test runner finds nothing.

## Step 4. Red: write the first test for the greeting

We write the test before the code. The rule for the probe is simple. `Greeting.For` returns a greeting for a name. The first test checks a normal name. The test uses AwesomeAssertions to compare the result.

The test name describes the behavior: `For_greets_the_name`. Test names use underscores, as [CLAUDE.md](../../CLAUDE.md) shows, and the analyzer rule CA1707 rejects underscores. We scope that rule off for test projects in `.editorconfig`, and leave it on for production code. Append this section to the end of `.editorconfig`:

```ini
# Test projects: test names use underscores to describe behavior, such as Pickup_fails_when_deposit_is_not_secured
[**/*.Tests/**.cs]
dotnet_diagnostic.CA1707.severity = none
```

The test name describes the behavior: `For_greets_the_name`. The `[Fact]` attribute marks a test for xUnit. The `using` lines bring in xUnit and AwesomeAssertions. The file is file-scoped, as `.editorconfig` requires.

`probe/Probe.Tests/GreetingTests.cs`

```csharp
using AwesomeAssertions;
using Xunit;

namespace Probe.Tests;

public class GreetingTests
{
    [Fact]
    public void For_greets_the_name()
    {
        var greeting = Greeting.For("Ada");

        greeting.Should().Be("Hello, Ada!");
    }
}
```

Run from the repository root:

```powershell
dotnet test --project probe/Probe.Tests
```

Expected: red. The build fails with `CS0103: The name 'Greeting' does not exist in the current context`. This is the right reason. The class does not exist yet, so the test has no code to run.

The `.editorconfig` section from this step turns off `CA1707` for the test project. Without it, the build would also report `CA1707` on the test name. With it, the only error is `CS0103`.

## Step 5. Green: the simplest code for the first test

We add the simplest method that passes the first test. It returns the greeting for any name, with no special case. The method is an expression body, which keeps it to one line.

`probe/Probe/Greeting.cs`

```csharp
namespace Probe;

public static class Greeting
{
    public static string For(string name) => $"Hello, {name}!";
}
```

This creates `Greeting.cs` with the first version of the class.

Run from the repository root:

```powershell
dotnet test --project probe/Probe.Tests
```

Expected: green. `For_greets_the_name` passes, and the test run reports one passed test.

## Step 6. Red: write the test for a blank name

The second rule is about a blank name. A blank name must not produce `Hello,   !`. The greeting uses `stranger` instead. We add this test to `GreetingTests.cs`, after the first test, inside the same class.

`probe/Probe.Tests/GreetingTests.cs`

```csharp
using AwesomeAssertions;
using Xunit;

namespace Probe.Tests;

public class GreetingTests
{
    [Fact]
    public void For_greets_the_name()
    {
        var greeting = Greeting.For("Ada");

        greeting.Should().Be("Hello, Ada!");
    }

    [Fact]
    public void For_greets_a_stranger_when_the_name_is_blank()
    {
        var greeting = Greeting.For("   ");

        greeting.Should().Be("Hello, stranger!");
    }
}
```

The file now has the second test. The first test is unchanged.

Run from the repository root:

```powershell
dotnet test --project probe/Probe.Tests
```

Expected: red. `For_greets_a_stranger_when_the_name_is_blank` fails. AwesomeAssertions reports the expected text `Hello, stranger!` and the actual text `Hello,    !`. The first test still passes. The failure shows the value that the code returns, so it is easy to see what to fix.

## Step 7. Green: handle a blank name

We add the rule to the method. A name that is empty or only spaces becomes `stranger`. We use `string.IsNullOrWhiteSpace`, which covers both cases. The first test still passes, because `Ada` is not blank.

`probe/Probe/Greeting.cs`

```csharp
namespace Probe;

public static class Greeting
{
    public static string For(string name)
    {
        var who = string.IsNullOrWhiteSpace(name) ? "stranger" : name;
        return $"Hello, {who}!";
    }
}
```

This replaces the expression-body method from step 5.

Run from the repository root:

```powershell
dotnet test --project probe/Probe.Tests
```

Expected: green. Both tests pass, and the run reports two passed tests.

## Step 8. Refactor: name the fallback

The tests are green, so we can clean up the code without a change of behavior. The word `stranger` is a rule of its own, so we give it a name. The constant makes the fallback easy to find and change. The tests check the result, so a wrong rename fails at once.

`probe/Probe/Greeting.cs`

```csharp
namespace Probe;

public static class Greeting
{
    private const string Stranger = "stranger";

    public static string For(string name)
    {
        var who = string.IsNullOrWhiteSpace(name) ? Stranger : name;
        return $"Hello, {who}!";
    }
}
```

This adds the `Stranger` constant and uses it in place of the string literal. The method signature does not change.

Run from the repository root:

```powershell
dotnet test --project probe/Probe.Tests
dotnet format probe/Probe/Probe.csproj
dotnet format probe/Probe.Tests/Probe.Tests.csproj
dotnet format --verify-no-changes probe/Probe/Probe.csproj
dotnet format --verify-no-changes probe/Probe.Tests/Probe.Tests.csproj
```

Expected: green for the test run, with two passed tests. `dotnet format` takes a project or solution path, not a folder. The `--verify-no-changes` runs report no changes. The first two format runs add a blank line between the `using` groups, as `.editorconfig` requires. They also remove the final newline from `.cs` files, because `.editorconfig` sets `insert_final_newline = false` for `*.cs`.

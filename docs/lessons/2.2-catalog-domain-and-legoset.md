# Lesson 2.2. Catalog Domain project, `LegoSet` aggregate and value objects

Features: [F01](../features/01-catalog-management.md)

## Summary

We create the `BrickShare.Catalog.Domain` project and its test project. We add the `LegoSet` aggregate and two value objects, `LegoSetNumber` and `MinRentalDays`. The prices use the `Money` type from lesson 1.7. Each rule is written test-first. At the end the domain project builds without ASP.NET Core, EF Core, or any other infrastructure, and eight tests pass.

## The problem

The Catalog Service has an Api project from lesson 2.1, but no domain model. Without a domain model:

- Nothing stores the rules of a set. The rules would end up in endpoints or handlers, where they are hard to test and easy to break. [Architecture.md section 7.1](../Architecture.md#71-domain-driven-design) says business rules live in aggregates and value objects.
- A set number is just a string. Nothing stops an admin from saving `10294-1` as the LEGO set number. That value is the Rebrickable reference, which is a different thing. [Catalog management](../features/01-catalog-management.md) says the LEGO set number is "from the box (for example `10294`, searchable, not unique)" and that the Rebrickable reference (for example `10294-1`) is separate.
- Minimum rental days is a plain number with no rule behind it. The reservation rule "It must be at least `minRentalDays` of the set" ([06-reservation-and-payment.md](../features/06-reservation-and-payment.md)) needs a valid value in the first place.

The feature rules that drive this lesson:

- A set has a daily price, a deposit, a replacement value, and a late fee per day. The shop stores all of them as money.
- `LateFeePerDay` is the amount charged for each day a set is kept after its due date. The fee is per set, so a set with a higher `LateFeePerDay` costs more for each late day. The return step calculates the total as `overdueDays * lateFeePerDay`, where `overdueDays` is `max(0, ReturnedAt.Date - DueDate)` ([09-return-and-inspection.md](../features/09-return-and-inspection.md)). This lesson only stores the per-day amount. It does not calculate the fee. The fee is a `Money` value, so a late fee of EUR 5.00 is stored as `500`.
- "`ReplacementValue` is the cost to buy the set again. The admin sets `Deposit` per set. A guideline is 30–50% of `ReplacementValue`." The guideline is advice for the admin. The domain does not enforce it.
- Reservations copy the prices and the minimum days from Catalog at booking time. Catalog owns the source values, so the aggregate must hold them.

The concepts we introduce:

- **Aggregate root.** `LegoSet` is the consistency boundary for a set. It holds its values and protects its invariants. It is a class that inherits `AggregateRoot<Guid>` from the shared kernel (lesson 1.6).
- **Value object.** `LegoSetNumber` and `MinRentalDays` have no identity. Two values with the same content are equal. Each one checks its rule in the constructor, so an invalid value cannot exist. A `record` gives the equality, as in `Money` (lesson 1.7).
- **No clock and no random ids in the domain.** The aggregate receives its id from the caller. The handler in lesson 2.6 creates it with `Guid.CreateVersion7()`. This keeps the domain free of `DateTime.UtcNow` and of hidden time sources, as [CLAUDE.md](../../CLAUDE.md) requires.
- **Uniqueness is storage, not domain.** The feature doc says the set number is "not unique". The domain has nothing to check for that. The database and the endpoints handle it in later lessons.

## Step 7. Green: check the digits in the constructor

We check the value first. `ArgumentException.ThrowIfNullOrEmpty` rejects the empty value. `char.IsAsciiDigit` checks every character, so `-` and letters fail. The `Linq` method `All` does the loop.

`src/Services/Catalog/BrickShare.Catalog.Domain/LegoSetNumber.cs` (replace the file with this content)

```csharp
using System;
using System.Linq;

namespace BrickShare.Catalog.Domain;

public sealed record LegoSetNumber
{
    public LegoSetNumber(string value)
    {
        ArgumentException.ThrowIfNullOrEmpty(value);

        if (!value.All(char.IsAsciiDigit))
        {
            throw new ArgumentException("A LEGO set number contains digits only.", nameof(value));
        }

        Value = value;
    }

    public string Value { get; }
}
```

The change adds the two `using` lines and the two checks. Everything else in the file stays the same.

Its constructor takes the id and the values, and it stores them. The value objects check their own rules, so the aggregate has no checks of its own yet.

We create the file with the CLI. Run from the repository root:

```powershell
dotnet new class -n LegoSet -o src/Services/Catalog/BrickShare.Catalog.Domain
```

`src/Services/Catalog/BrickShare.Catalog.Domain/LegoSet.cs` (replace the template class with this content)

```csharp
using System;

using BrickShare.SharedKernel;

namespace BrickShare.Catalog.Domain;

public sealed class LegoSet(
    Guid id,
    LegoSetNumber legoSetNumber,
    MinRentalDays minRentalDays,
    Money dailyPrice,
    Money deposit,
    Money replacementValue,
    Money lateFeePerDay) : AggregateRoot<Guid>(id)
{
    public LegoSetNumber LegoSetNumber { get; } = legoSetNumber;

    public MinRentalDays MinRentalDays { get; } = minRentalDays;

    public Money DailyPrice { get; } = dailyPrice;

    public Money Deposit { get; } = deposit;

    public Money ReplacementValue { get; } = replacementValue;

    public Money LateFeePerDay { get; } = lateFeePerDay;
}
```

The properties have no setters. A `LegoSet` changes only through its methods, and lesson 2.6 adds the first method, which is an update. The primary constructor keeps the class short, and it matches the style of `Entity<TId>` in the shared kernel.

```powershell

```

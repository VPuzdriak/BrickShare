# Lesson 2.13. Set images: SAS upload URLs with Azurite

Features: [F01](../features/01-catalog-management.md#images)
Previous: [2.12](2.12-qr-labels-and-lookup-by-code.md) · Next: 2.14 Browse sets: filters, sorting, paging, set details

## Summary

An admin requests an upload URL for a new image of a set. `POST /catalog/sets/{id}/images/upload-url` stores a `SetImage` with status `Uploaded` and returns a short-lived user delegation SAS URL for the blob `set-images/originals/{setId}/{imageId}`. The admin uploads the file straight to Blob Storage, so the file never passes through the Catalog Service. At the end the Api tests for the upload URL are green. The automated tests use a fake storage port. The Azurite check is a manual step at the end.

## The problem

Catalog has sets and instances, but it cannot take a photo of a set yet. [Catalog management](../features/01-catalog-management.md#images) describes the image flow:

> 1. Admin requests an upload URL. Catalog returns a short-lived user delegation SAS URL for `set-images/originals/{setId}/{imageId}`. The image status is `Uploaded`.
> 2. Admin uploads the file directly to Blob Storage.
> 3. Media Functions create a web version ... and a thumbnail ...

Steps 3 and 4 belong to lessons 8.3 and later. This lesson covers step 1 only. The endpoint comes from the endpoint table:

| Method | Route | Policy | Purpose |
|--------|-------|--------|---------|
| POST | `/catalog/sets/{id}/images/upload-url` | `AdminOnly` | Get a short-lived user delegation SAS URL for direct upload to `set-images/originals/` |

The architecture adds two rules. [Architecture 3.2](../Architecture.md#32-catalog-service) names the `SetImage` fields, and [Architecture 11](../Architecture.md#11-cross-cutting-concerns) requires that SAS URLs are short-lived and scoped to one blob.

The concepts we introduce:

- **`SetImage` is its own aggregate.** It refers to its set by `SetId`, as `SetInstance` does. One request changes one aggregate, so the image is saved without touching `LegoSet`.
- **A port for blob storage.** The domain depends on `ISetImageStorage`. The Api project implements it with `Azure.Storage.Blobs`. Tests use a fake, as the Rebrickable lookup does. The domain never sees an Azure type.
- **User delegation SAS.** The URL is signed with a key that Entra ID issues to the managed identity. No account key is used, which matches [CLAUDE.md](../../CLAUDE.md): no keys in the code or in configuration.
- **Time through `TimeProvider`.** The expiry time comes from the injected clock, so the tests can fix it.

This lesson does not do the following:

- It does not process the upload. Media Functions do that in lesson 8.3.
- It does not add an endpoint to read or list images. The response of this endpoint is enough for now.
- It does not add the `Ready` status. Only `Uploaded` exists until Media Functions publish `SetImageProcessed`.

## Step 3. Green: the `SetImage` aggregate

`SetImage` follows the pattern of `SetInstance`: a constructor sets the state, and the setters are private. The blob name is part of the domain, because the rule for it is in the feature doc. The status constant is a static class, the same as `InstanceStatus`.

`src/Services/Catalog/BrickShare.Catalog.Domain/SetImage.cs` (new file, full content)

```csharp
using System;

using BrickShare.SharedKernel;

namespace BrickShare.Catalog.Domain;

public sealed class SetImage : AggregateRoot<Guid>
{
    public static readonly TimeSpan UploadUrlLifetime = TimeSpan.FromMinutes(15);

    // Used by EF Core to materialize a stored image.
    private SetImage()
        : this(Guid.Empty, Guid.Empty)
    {
    }

    public SetImage(Guid id, Guid setId)
        : base(id)
    {
        SetId = setId;
        OriginalBlobName = $"originals/{setId}/{id}";
        Status = SetImageStatus.Uploaded;
    }

    public Guid SetId { get; private set; }

    public string OriginalBlobName { get; private set; }

    public string Status { get; private set; }
}
```

`UploadUrlLifetime` is the rule for "short-lived". The feature doc does not give a number, so this lesson picks 15 minutes. The blob name is relative to the container `set-images`, so the full blob path is `set-images/originals/{setId}/{imageId}`.

`src/Services/Catalog/BrickShare.Catalog.Api/Features/Sets/ImageUpload/CreateImageUploadUrl.cs` (new file, full content)

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

using BrickShare.Catalog.Api.Infrastructure.Persistence;
using BrickShare.Catalog.Domain;

using Microsoft.AspNetCore.Builder;
using Microsoft.AspNetCore.Http;
using Microsoft.AspNetCore.Http.HttpResults;
using Microsoft.AspNetCore.Routing;
using Microsoft.EntityFrameworkCore;

namespace BrickShare.Catalog.Api.Features.Sets.ImageUpload;

public static class CreateImageUploadUrl
{
    public static void MapCreateImageUploadUrl(this RouteGroupBuilder sets) =>
        sets.MapPost("/{id:guid}/images/upload-url", Handle);

    private static async Task<Results<Ok<ImageUploadUrlResponse>, ProblemHttpResult>> Handle(
        Guid id,
        CatalogDbContext dbContext,
        ISetImageStorage imageStorage,
        TimeProvider timeProvider,
        CancellationToken cancellationToken)
    {
        var setExists = await dbContext.LegoSets.AnyAsync(legoSet => legoSet.Id == id, cancellationToken);

        if (!setExists)
        {
            return SetProblems.NotFound(id);
        }

        var image = new SetImage(Guid.CreateVersion7(), id);
        var expiresAt = timeProvider.GetUtcNow() + SetImage.UploadUrlLifetime;
        var uploadUrl = await imageStorage.CreateUploadUrlAsync(image.OriginalBlobName, expiresAt, cancellationToken);

        dbContext.SetImages.Add(image);
        await dbContext.SaveChangesAsync(cancellationToken);

        return TypedResults.Ok(new ImageUploadUrlResponse(image.Id, uploadUrl, expiresAt));
    }
}

public sealed record ImageUploadUrlResponse(Guid ImageId, Uri UploadUrl, DateTimeOffset ExpiresAt);
```

The endpoint goes into the set group, which already requires `AdminOnly`. `SetEndpoints` gets the using and the mapping.

The adapter asks Blob Storage for a user delegation key. It uses the key to sign a SAS for one blob, with `create` and `write` permissions only. The start time comes from the injected `TimeProvider`, not from the system clock.

`src/Services/Catalog/BrickShare.Catalog.Api/Infrastructure/Storage/BlobSetImageStorage.cs` (new file, full content)

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

using Azure.Storage.Blobs;
using Azure.Storage.Sas;

using BrickShare.Catalog.Domain;

namespace BrickShare.Catalog.Api.Infrastructure.Storage;

public sealed class BlobSetImageStorage(BlobServiceClient serviceClient, TimeProvider timeProvider) : ISetImageStorage
{
    private const string ContainerName = "set-images";

    public async Task<Uri> CreateUploadUrlAsync(string blobName, DateTimeOffset expiresOn, CancellationToken cancellationToken)
    {
        var startsOn = timeProvider.GetUtcNow();
        var delegationKey = await serviceClient.GetUserDelegationKeyAsync(startsOn, expiresOn, cancellationToken);

        var sasBuilder = new BlobSasBuilder(BlobSasPermissions.Create | BlobSasPermissions.Write, expiresOn)
        {
            BlobContainerName = ContainerName,
            BlobName = blobName,
            Resource = "b",
            StartsOn = startsOn
        };

        var blobClient = serviceClient.GetBlobContainerClient(ContainerName).GetBlobClient(blobName);

        return blobClient.GenerateUserDelegationSasUri(sasBuilder, delegationKey.Value);
    }
}
```

The registration reads the service URI from configuration and uses `DefaultAzureCredential`. In Azure that is the managed identity. On a developer machine it is the Azure CLI login. No key is read from configuration.

{
    public static IServiceCollection AddSetImageStorage(this IServiceCollection services, IConfiguration configuration)
    {
        var serviceUri = configuration["Storage:BlobServiceUri"]
            ?? throw new InvalidOperationException("The setting 'Storage:BlobServiceUri' is missing.");

        services.AddSingleton(_ => new BlobServiceClient(new Uri(serviceUri), new DefaultAzureCredential()));
        services.AddSingleton<ISetImageStorage, BlobSetImageStorage>();

        return services;
    }
}

## Step 15. Manual check against Azurite (not a test)

This check needs a running Azurite, so it is not part of the green run. The automated tests do not call Azurite.

> **Known limit.** Azurite does not reliably accept user delegation SAS URLs. Its user delegation key support is not complete, and a URL signed with it can return `403 AuthenticationFailed` even when the code is correct. If the upload in this step fails with `403`, the cause is Azurite, not this code. Record it in the log and check the upload against a real development storage account when [lesson 13.4](../CoursePlan.md#13-azure-infrastructure-with-terraform) provides one.

Start Azurite. Run from any folder:

```powershell
docker run --rm -p 10000:10000 mcr.microsoft.com/azure-storage/azurite azurite-blob --blobHost 0.0.0.0
```

Create the container `set-images` once. Run from any folder:

```powershell
az storage container create --name set-images --connection-string "UseDevelopmentStorage=true"
```

Sign in with the Azure CLI, because `DefaultAzureCredential` uses that login locally. Run from any folder:

```powershell
az login
```

Start the Catalog Service in Development, then ask for an upload URL with an admin token from `dotnet user-jwts` ([Architecture 5.3](../Architecture.md#53-development-issuer-until-the-identity-module)). Send the image with a `PUT` request. Use `curl.exe`, because `curl` is an alias in Windows PowerShell. Run from the folder with the photo:

```powershell
curl.exe -X PUT -H "x-ms-blob-type: BlockBlob" --data-binary "@photo.jpg" "<uploadUrl from the response>"
```

Expected: the command returns HTTP `201 Created`, and the blob `originals/{setId}/{imageId}` appears in the `set-images` container. If the response is `403`, read the limit note above. Do not change the code to work around Azurite.

## Result

The Catalog Service issues upload URLs for set images.

- `POST /catalog/sets/{id}/images/upload-url` returns `200` with `imageId`, `uploadUrl`, and `expiresAt`. The URL is a user delegation SAS for one blob, `set-images/originals/{setId}/{imageId}`, with `create` and `write` permissions. It expires after 15 minutes.
- Each request stores a `SetImage` with status `Uploaded`. The row is saved only after the URL is issued.
- An unknown set returns `404` with `ProblemDetails`. An employee gets `403`.
- The Azure calls sit behind the port `ISetImageStorage`. The automated tests use a fake, so they never call Azure.

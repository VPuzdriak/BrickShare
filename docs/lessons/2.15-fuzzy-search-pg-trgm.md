# Lesson 2.15. Fuzzy search with `pg_trgm`

Features: [F02](../features/02-catalog-browsing-and-search.md)
Previous: [2.14](2.14-browse-sets-filters-sorting-paging.md) · Next: 2.16 Theme facets with in-memory caching

## Summary

`GET /catalog/sets?q=...` finds active sets whose names are close to the search text, so "falcon" finds "Millennium Falcon" and "Milenium Falcon" (one typo) still finds it. The PostgreSQL extension `pg_trgm` and a GIN trigram index do the matching in the database. With search text, results sort by match score. At the end the Api tests for search are green.

## The problem

Browsing works, but the `q` parameter from the endpoint table is ignored. Every search returns the whole catalog. [Catalog browsing and search](../features/02-catalog-browsing-and-search.md) sets the rules:

> **Fuzzy search on the set name** and the LEGO set number from the box. "milenium falcn" (two typos) finds "Millennium Falcon". A search term matches any part of the name, so "falcon" finds "Millennium Falcon".

> With search text, results sort by match score. With no search text, results sort by the chosen field (name, pieces, price, newest).

The [Catalog Service](../Architecture.md#32-catalog-service) names the tool: the `pg_trgm` extension with GIN trigram indexes for typo-tolerant name search.

Concepts this lesson introduces:

- **Trigrams.** `pg_trgm` splits text into three-character pieces. "falcon" becomes a set of pieces such as `fal`, `alc`, `con`. Two strings are similar when they share many pieces. Typos change only a few pieces, so a typo still leaves most of them.
- **Word similarity.** The `<%` operator asks whether the search text is similar to any part of the name. "falcon" is a full word inside "Millennium Falcon", so the score is high. A plain similarity score would compare the whole name and give a low score.
- **A GIN index for the operator.** A GIN index with the `gin_trgm_ops` operator class serves `<%` queries. The index stores the trigrams of each name.
- **Npgsql translates the operator.** `EF.Functions.TrigramsAreWordSimilar` produces `<%` in SQL, and `EF.Functions.TrigramsWordSimilarity` produces the score. The functions ship in the `Npgsql.EntityFrameworkCore.PostgreSQL` package, so the query stays in LINQ and needs no new package.
- **Search overrides sort.** The feature rule sets the order when search text is present. The `sort` parameter from lesson 2.14 still validates, but it has no effect when `q` is set.

Scope decisions made in this lesson:

- **Set name only.** The feature rule also covers the LEGO set number. Matching a number needs a string value for the `LegoSetNumber` value object, which EF does not translate in a query. This lesson leaves the number out. It is an open point for the author.
- **Default threshold.** The server default for `pg_trgm.word_similarity_threshold` is 0.6. The feature doc suggests 0.4 for short names. This lesson keeps 0.6. A query with two typos may find nothing.
- **Blank search is no search.** A `q` with only spaces behaves like a missing `q`.
- **No `unaccent`.** The feature doc also creates `unaccent`. No lesson in the course plan covers it yet, so this lesson skips it.

## Step 2. Add the extension and the trigram index

The search needs two things in the database: the `pg_trgm` extension, and a GIN index on the name for the `<%` operator. The tests run the migrations, so they need both. This step adds no behavior. It is the setup for the search tests in steps 3 to 5.

The extension is declared on the model. EF Core creates it in the migration. Replace the `OnModelCreating` method in `src/Services/Catalog/BrickShare.Catalog.Api/Infrastructure/Persistence/CatalogDbContext.cs` with this one. The only new line is the first one.

`src/Services/Catalog/BrickShare.Catalog.Api/Infrastructure/Persistence/CatalogDbContext.cs`

```csharp
    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.HasPostgresExtension("pg_trgm");
        modelBuilder.HasSequence<long>("inventory_code_seq");
        modelBuilder.ApplyConfigurationsFromAssembly(typeof(CatalogDbContext).Assembly);
    }
```

The index is declared on the set name. In `LegoSetConfiguration.cs`, add the index after the unique index on `RebrickableSetNum`. Find this block:

`src/Services/Catalog/BrickShare.Catalog.Api/Infrastructure/Persistence/LegoSetConfiguration.cs`

```csharp
        builder.HasIndex(legoSet => legoSet.RebrickableSetNum)
            .IsUnique();
```

Add these lines directly after it, with a blank line before them:

```csharp
        builder.HasIndex(legoSet => legoSet.Name)
            .HasMethod("gin")
            .HasOperators("gin_trgm_ops");
```

The name index is case-insensitive in `pg_trgm`. The trigram functions fold case, so the index does not need `lower(name)` as the feature doc shows.

The migration is generated by the CLI. Do not write it by hand. Run from the repository root:

```powershell
dotnet ef migrations add AddFuzzySearchIndexes --project src/Services/Catalog/BrickShare.Catalog.Api --startup-project src/Services/Catalog/BrickShare.Catalog.Api --output-dir Infrastructure/Persistence/Migrations
dotnet format
```

Expected: the command creates `<timestamp>_AddFuzzySearchIndexes.cs` and its `.Designer.cs` file, and it updates `CatalogDbContextModelSnapshot.cs`. The migration creates the extension and the GIN index. Do not edit the generated files. `dotnet format` fixes their namespace style. Without it the build fails with IDE0161.

The migration passes the index operator class as a constant array, and the build fails with CA1861 on it. The tool writes this code, so the rule is turned off for migration files. Add this section at the end of the root `.editorconfig`:

`.editorconfig`

```ini
# EF Core migrations are generated: the tool writes a constant array argument for index operator classes
[**/Migrations/*.cs]
dotnet_diagnostic.CA1861.severity = none
```

Run from the repository root:

```powershell

```

Expected: green. The existing tests now run on a database with `pg_trgm` and the new index. No behavior has changed yet.

namespace BrickShare.Catalog.Api.Features.Sets.Browse;

The handler adds the filter. In `BrowseSets.cs`, replace the line `var matches = dbContext.LegoSets.Where(legoSet => legoSet.IsActive);` with these lines. The theme, piece, and price blocks that follow stay as they are.

`src/Services/Catalog/BrickShare.Catalog.Api/Features/Sets/Browse/BrowseSets.cs`

```csharp
        var matches = dbContext.LegoSets.Where(legoSet => legoSet.IsActive);

        var search = request.Search;

        if (!string.IsNullOrWhiteSpace(search))
        {
            matches = matches.Where(legoSet => EF.Functions.TrigramsAreWordSimilar(search, legoSet.Name));
        }
```

`TrigramsAreWordSimilar` translates to `search <% name`. The default threshold is 0.6. A set whose name is not similar enough to the search text is removed here.

## Step 5. Green: with search text, sort by match score

When search text is present, the order is the match score, highest first. The score is the word similarity between the search text and the name. Ties go to the name, then the id, so paging stays stable.

Add the `Rank` method to `BrowseSets`, after the `Sort` method:

`src/Services/Catalog/BrickShare.Catalog.Api/Features/Sets/Browse/BrowseSets.cs`

```csharp
    private static IOrderedQueryable<LegoSet> Rank(IQueryable<LegoSet> sets, string search) =>
        sets.OrderByDescending(legoSet => EF.Functions.TrigramsWordSimilar(search, legoSet.Name))
            .ThenBy(legoSet => legoSet.Name)
            .ThenBy(legoSet => legoSet.Id);
```

The handler chooses the order. In `BrowseSets.cs`, replace these two lines:

```csharp
        var rows = await Sort(matches, request.Sort)
            .Skip((request.Page - 1) * request.PageSize)
```

with these lines:

```csharp
        var ordered = string.IsNullOrWhiteSpace(search)
            ? Sort(matches, request.Sort)
            : Rank(matches, search);

        var rows = await ordered
            .Skip((request.Page - 1) * request.PageSize)
```

`Sort` still handles the list without search text, so lesson 2.14 behaves as before.

## Result

What now works:

- `GET /catalog/sets?q=...` returns active sets whose names are similar to the search text. "falcon" finds "Millennium Falcon". One typo, such as "milenium falcon", still finds it.
- With search text, results sort by match score, highest first. The name and the id break ties. The `sort` parameter has no effect while `q` is set.
- Without search text, or with a blank search text, the list works as in lesson 2.14.
- The database has the `pg_trgm` extension and a GIN trigram index on the set name.

Not in this lesson: matching by LEGO set number, the 0.4 threshold for short names, and the `unaccent` extension. See the scope decisions above.

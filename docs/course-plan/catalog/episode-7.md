# Episode 7 — Terraform: recreate it declaratively

## Why this episode ends the way episode 6 ended

Episode 6's last line was: "before you let `terraform apply` create anything, you should be
able to recognise every single resource it's about to make." This episode is that recognition
test. Nothing here should be a surprise — it's the exact same three resources, the exact same
names' worth of decisions, just declared instead of clicked.

**One thing is different, and it's worth naming out loud on camera:** the Docker Hub image
reference and the container port are about to become **lines in a file**, not fields in a
wizard. The mistake that broke episode 6's deployment — the Container tab's Port field left at
its default `80`, invisible until a 230-second timeout surfaced it — is **structurally
impossible once it's written this way**. There's no field to forget, because the value is going
to be `WEBSITES_PORT = "8080"`, sitting in a diff that gets reviewed before `apply` runs, the
same way any other code change would be. This is the whole case for infrastructure as code,
made concrete instead of asserted: the class of bug from two episodes ago cannot recur, not
because anyone remembered to be careful, but because the shape of the tool doesn't allow it.

## The target shape

```
infra/
  main.tf
  .terraform.lock.hcl        # generated by init in Step 3, committed once it exists
```

**One file, on purpose.** A resource group, an App Service Plan and a Web App is three
resources. Splitting that across `providers.tf`, `backend.tf`, `variables.tf`, `main.tf`,
`outputs.tf`, and a module with its own three files — nine files for three resources — is
structure with nothing behind it yet: no second caller to justify a module, no second
environment to justify variables for things that are the same every time, no file so long it
needs splitting. That's the identical mistake episode 2 spent its whole first half refusing to
make with four C# projects on day one, just wearing HCL instead. One file, read top to bottom,
is the actual right size for what this episode deploys.

**This grows later, for concrete reasons, not on a schedule:** a second service that wants the
same App-Service-for-Containers shape is what earns a module — there's nothing to reuse with
one caller. `main.tf` genuinely getting hard to read once Postgres (episode 16), Storage
(episode 26) and Key Vault (episode 21) all land in it is what earns a split into multiple
files. Both are named here so that whoever adds the fourth resource to this file knows exactly
what signal they're watching for, rather than restructuring on a feeling.

## Step 1 — Bootstrap the state backend

Terraform stores its own knowledge of what exists — the state file — somewhere. For this
course, that's Azure Blob Storage. But the storage account holding that state has to exist
*before* `terraform init` can point at it, and Terraform can't create its own backend using
state it has nowhere yet to put. This is a real chicken-and-egg problem, not a rough edge to
smooth over, and the honest answer is: **something has to come first, imperatively.**

Run these once, by hand, before any HCL exists:

```bash
az group create --name rg-brickshare-tfstate --location westeurope

az storage account create \
  --name stbricksharetfstate \
  --resource-group rg-brickshare-tfstate \
  --location westeurope \
  --sku Standard_LRS \
  --min-tls-version TLS1_2 \
  --allow-blob-public-access false

az storage container create \
  --name tfstate \
  --account-name stbricksharetfstate \
  --auth-mode login

az role assignment create \
  --assignee "$(az ad signed-in-user show --query id -o tsv)" \
  --role "Storage Blob Data Contributor" \
  --scope "$(az storage account show --name stbricksharetfstate --resource-group rg-brickshare-tfstate --query id -o tsv)"
```

**Say this plainly, don't apologise for it:** "Everything from here on is code you review in a
diff before it runs. This isn't — it's four commands, run once, and the reason is structural:
Terraform can't put its own state file inside infrastructure that doesn't exist yet. One
deliberately imperative step in an otherwise declarative episode."

**Three decisions in this bootstrap worth explaining, not just running:**

- **The state resource group (`rg-brickshare-tfstate`) is separate from the resource group
  Terraform will manage (`rg-brickshare-dev`).** It has to outlive every `terraform destroy` run
  against the dev environment, including a mistake pointed at the wrong resource group. State
  for infrastructure you're actively learning to blow away and rebuild should not live inside
  the thing being blown away.
- **`--auth-mode login`, no storage account key generated at all.** The backend block written
  in Step 2 sets `use_azuread_auth = true`, so Terraform authenticates as the logged-in Azure
  identity via RBAC rather than a key that would need to be generated, stored somewhere, and
  rotated. This is the first place in actual infrastructure code that the "no secrets in
  configuration" stance from `docs/architecture/catalog.md` gets kept rather than just written
  down.
- **The fourth command is not optional, and it's easy to assume it isn't needed.** Creating a
  storage account and reading or writing the blobs inside it are two separate permission
  layers in Azure — control plane (manage the resource itself) and data plane (touch what's
  inside it). Creating the account, even as the account's own creator, grants **only** the
  first. `use_azuread_auth = true` needs the second, and nothing grants that automatically —
  not creating the account, not being Contributor on the resource group. `Storage Blob Data
  Contributor`, explicitly assigned, is what closes that gap. Skip this command and `terraform
  init` fails with:

  ```
  Failed to get existing workspaces: listing blobs: executing request: unexpected status 403
  (403 This request is not authorized to perform this operation using this permission.) with
  AuthorizationPermissionMismatch
  ```

  **Say, if this comes up:** "This isn't Terraform being difficult — it's Azure's two
  permission planes doing exactly what they're designed to do. Being able to create the account
  doesn't mean being able to read what's in it; those are deliberately separate, and the role
  assignment is what bridges them." RBAC assignments can take a minute or two to propagate — if
  this command has already run and the error still shows up immediately after, wait briefly and
  retry `terraform init` before assuming something else is wrong. If the role-assignment
  command itself fails with a 403, that's a different problem: assigning roles needs `Owner` or
  `User Access Administrator` on the subscription, which not every account has — on a personal
  or training subscription this is rarely the blocker, since the account is usually its own
  Owner.

**Two things worth knowing before running these, if this is being followed rather than just
watched:**

- **`stbricksharetfstate` is a storage account name, and those are globally unique across all
  of Azure** — not just one subscription. If it's taken, pick another name and use it
  consistently in Step 2; there's nothing else to change.
- Worth saving these four commands somewhere memorable — a gist, a wiki page, a comment at the
  top of `main.tf`. They only run once per environment, which is exactly the kind of thing
  that's forgotten by the second time it's needed.

## Step 2 — Write `infra/main.tf`

```bash
mkdir infra
cd infra
```

Everything below goes in **one file**. It's built up in labelled pieces here so each part gets
its own explanation, not because it's a preview of files still to come.

### The `terraform` block — version, provider, and backend together

```hcl
terraform {
  required_version = ">= 1.9"

  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 4.0"
    }
  }

  backend "azurerm" {
    resource_group_name  = "rg-brickshare-tfstate"
    storage_account_name = "stbricksharetfstate"
    container_name       = "tfstate"
    key                  = "catalog.tfstate"
    use_azuread_auth     = true
  }
}
```

`~> 4.0` allows patch and minor updates within the 4.x line but blocks a 5.0 major upgrade from
silently changing resource behaviour underneath the course. `.terraform.lock.hcl` — generated
by `init` in Step 3, committed once it exists — goes one step further and pins the *exact*
resolved provider version, so `terraform init` on a different machine installs precisely what
was tested here.

`key = "catalog.tfstate"` is deliberately per-service, not a generic `terraform.tfstate`. The
storage account and container from Step 1 are shared infrastructure; the state file inside it
is scoped to one service's resources, the same way `docs/architecture/catalog.md` scopes
ownership. A future rentals service gets its own key in this same account, not its own account.

### The provider block

```hcl
provider "azurerm" {
  features {}
}
```

**Say, when this goes on screen:** "No client ID, no client secret, nothing that looks like a
credential — and that's not an oversight. This provider authenticates as whoever is logged into
the Azure CLI. Same identity that just ran the bootstrap commands, same identity that's been
clicking through the portal since episode 6. One login, reused, rather than a second credential
invented for Terraform to hold."

### The one variable

```hcl
variable "docker_image" {
  description = "Docker Hub image reference for the catalog API, e.g. \"yourname/brickshare-catalog-api:episode-6\"."
  type        = string
}
```

The only value in this file that genuinely can't be a literal — it's personal to whoever's
building this, and Terraform should refuse to guess it. Nothing else in this file gets a
variable: one environment, one region, one set of names, all used exactly once. A variable for
a value that never varies is indirection with nothing behind it.

### The three resources

```hcl
resource "azurerm_resource_group" "main" {
  name     = "rg-brickshare-dev"
  location = "westeurope"
}

resource "azurerm_service_plan" "catalog" {
  name                = "plan-brickshare-catalog-dev"
  resource_group_name = azurerm_resource_group.main.name
  location            = azurerm_resource_group.main.location
  os_type             = "Linux"
  sku_name            = "B1"
}

resource "azurerm_linux_web_app" "catalog" {
  name                = "app-brickshare-catalog-dev"
  resource_group_name = azurerm_resource_group.main.name
  location            = azurerm_resource_group.main.location
  service_plan_id     = azurerm_service_plan.catalog.id

  site_config {
    application_stack {
      docker_image_name   = var.docker_image
      docker_registry_url = "https://index.docker.io"
    }
  }

  app_settings = {
    WEBSITES_PORT          = "8080"
    ASPNETCORE_ENVIRONMENT = "Production"
  }
}
```

**Say, on `WEBSITES_PORT` — this is the entire payoff of the episode:** "This one line is the
whole fix for the mistake episode 6 made twice — once in the Container tab's Port field,
defaulted to 80 and easy to miss, once again via the Configuration blade's Save button, easy to
click past. Here it's not a field on a form. It's a line in the only file that exists, sitting
in a diff that gets reviewed before `apply` ever runs. There's nothing to forget, because
there's no longer a blank to leave empty."

### The resource naming, end to end

| Resource | Name | Compare to episode 6 |
| --- | --- | --- |
| Resource group | `rg-brickshare-dev` | was `rg-brickshare-portal-demo` |
| App Service Plan | `plan-brickshare-catalog-dev` | was `plan-brickshare-demo` |
| Linux Web App | `app-brickshare-catalog-dev` | was `app-brickshare-catalog-demo` |

Same shape, real names this time — `-demo` said "throwaway" on purpose in episode 6; `-dev`
says "this one persists," because episode 9's pipeline needs a live target to deploy into.
Fixed, not randomised: predictable, sayable on camera, and stable across episodes that
reference it. The trade-off — Azure Web App names are unique across every subscription in the
world, not just this one — is small and already proven safe; episode 6 confirmed a near-
identical name was free in this tenant.

### The output

```hcl
output "web_app_url" {
  value = "https://${azurerm_linux_web_app.catalog.default_hostname}"
}
```

One output, because `terraform output web_app_url` is what Step 3 uses to verify the deployment
without copying a URL out of the Azure portal by hand.

### `.gitignore`

Before running anything, add a Terraform section to the repository's `.gitignore`:

```
## Terraform
.terraform/
*.tfstate
*.tfstate.*
crash.log
crash.*.log
.terraformrc
terraform.rc
```

`.terraform/` is the local provider plugin cache — regenerated by `init`, never committed.
`*.tfstate` matters less with a remote backend configured, but ignoring it is what stops a
local state file from ever being committed by accident if `terraform` runs before `init` picks
up the backend. **`.terraform.lock.hcl` is deliberately not in this list** — it's the one
generated file that gets committed, for the version-pinning reason above.

## Step 3 — Run it

```bash
terraform init
```

`init` reads the backend block, finds the bootstrap storage account from Step 1, and configures
remote state. It also downloads the `azurerm` provider and writes `.terraform.lock.hcl` —
**commit that file** once it appears.

```bash
terraform plan
```

With `docker_image` declared and no value supplied, Terraform stops and asks for it right in
the terminal — `var.docker_image / Enter a value:`. Type the Docker Hub reference from episode
6. For a value typed more than once, `-var="docker_image=..."` or exporting
`TF_VAR_docker_image` skips the prompt; neither is needed for a single run.

**This is the moment the whole episode has been building to.** `plan` prints exactly what
would change — three resources to add, nothing else — without touching Azure. **Say:** "This is
what the portal in episode 6 could never give us: the diff, before it happens. Read every line
of this before you'd ever type `apply` against something that mattered."

```bash
terraform apply
```

Confirm, watch it create the resource group, then the plan, then the web app. Once it finishes,
`terraform output web_app_url` prints the same shape of URL episode 6 produced by hand — hit
`/`, `/health/live`, `/health/ready` on it, same three responses as every episode since 3.

```bash
terraform plan
```

**Run it again, unchanged.** `No changes. Your infrastructure matches the configuration.` is
the episode's actual "Done when" — not the apply succeeding, but the *second* plan proving
nothing is left for Terraform to reconcile. State and reality agree.

## What this episode is not

No Postgres, no Storage, no Key Vault, no Application Insights — every one of those is in
`docs/architecture/catalog.md`'s infrastructure list, and every one of them arrives in the
episode that gives it a reason: Postgres in episode 16, Blob Storage in episode 26, Key Vault
the moment episode 21 introduces the Rebrickable API key, Application Insights in episode 29.
Building any of them now, before the feature that needs them exists, would be the exact
structure-ahead-of-need mistake episode 2 spent its whole first half refusing to make.

**And no container registry — but only for one more episode.** That list also includes one, and
unlike the rest its reason arrives immediately: episode 9's pipeline has to push an image
somewhere, and Docker Hub cannot accept that push without a stored token. So episode 8 replaces
the Docker Hub reference above with an ACR the app reads as its own managed identity. It stays
Docker Hub here because this episode's job is Terraform, and adding a fourth resource to the
episode that introduces the tool would blur both.

**No module, no multi-file split, yet.** The target-shape section above names the two things
that actually earn one — a second service reusing this shape, or this file genuinely getting
long — rather than splitting on a schedule or a feeling.

No `terraform destroy` at the end of this episode, unlike episode 6's portal teardown. This
infrastructure is meant to persist — episode 9's pipeline needs a live App Service to deploy
into, and "the loop closes" only means something if there's something on the other end of it.

## Verification

```bash
terraform fmt -check     # formatting
terraform init -backend=false       # provider only, no Azure calls
terraform validate       # HCL is internally consistent
```

The above three run with no Azure credentials and touch nothing in any subscription — useful
for CI later, and for checking this episode's code without yet having run the bootstrap step.

The episode's actual "Done when" needs the real backend and a real subscription: bootstrap
(Step 1), `init` (Step 3), `plan` (3 to add), `apply`, the three URLs responding, `plan` again
(no changes).

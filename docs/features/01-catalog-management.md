# Catalog management

Admins manage Lego sets, set images, and the physical instances the shop owns. Set specifications are looked up in the Rebrickable catalog by the LEGO set number, so the admin does not type them by hand. Uploaded images are processed automatically.

| Item | Value |
|------|-------|
| Actors | Admin |
| Services | Catalog, Media Functions, Rebrickable API |
| Architecture | [Catalog Service](../Architecture.md#32-catalog-service), [Media Functions](../Architecture.md#372-media-functions) |

## Rules

### Sets

- Catalog gives every set and instance its own id. APIs, events, and other services use only these ids. Rebrickable identifiers are external references and never leave Catalog.
- A set has: LEGO set number from the box (for example `10294`, searchable, not unique), optional Rebrickable reference (for example `10294-1`), name, theme, release year, pieces, minimum age, description, minimum rental days, daily price, deposit, replacement value, late fee per day, and attributes that vary between sets (minifigures, dimensions, tags).
- The LEGO set number is digits only. `10294-1` is not a LEGO set number: the `-1` suffix is part of the Rebrickable reference.
- Minimum rental days is set per set, not for the whole shop. It is any whole number greater than 0. The code sets no upper limit.
- `ReplacementValue` is the cost to buy the set again. The admin sets `Deposit` per set. A guideline is 30–50% of `ReplacementValue`, so expensive sets have a bigger deposit.
- Deleting a set is a soft delete (deactivate).

### Lookup in Rebrickable

Adding a set is a two-step process: look up, then submit.

1. The admin enters a set identifier, for example `10294` or `10294-1`. Without a variant suffix, Catalog tries `-1`.
2. Catalog calls the Rebrickable API and returns a **set draft**. Nothing is saved yet.
3. The admin reviews the draft, adds the shop data, and submits it with `POST /catalog/sets`.

| Field | Source |
|-------|--------|
| LEGO set number, Rebrickable reference, name, release year, piece count | Rebrickable set |
| Theme | Rebrickable theme. Catalog maps it to a local theme by Rebrickable theme id. The top-level parent theme becomes the catalog theme. Sub-themes are not stored. A missing local theme is created on submit |
| Minifigure count | Rebrickable set minifigures |
| Reference image URL, Rebrickable page URL | Rebrickable set |
| Minimum age, description, minimum rental days, daily price, deposit, replacement value, late fee | Admin. Rebrickable has no ages or prices |

- The admin can change every draft field before submitting.
- A set number unknown to Rebrickable returns `404`. The admin can still create the set manually without a lookup.
- If a set with the same Rebrickable reference already exists in the catalog, the lookup returns `409` with the id of the existing set. Different variants (`10294-1`, `10294-2`) are different sets.
- On submit, Catalog generates the set id and stores the Rebrickable reference, the Rebrickable theme id, and the time of the lookup, so the data can be refreshed later.
- **Refresh:** the admin can re-fetch Rebrickable data for an existing set. Only Rebrickable fields are updated. Shop data (prices, deposit, age) stays unchanged.
- **Image:** the draft shows the Rebrickable image as a reference only. The admin uploads the shop's own photos through the normal image flow. Copying Rebrickable images into the catalog is not done, because the image rights do not belong to Rebrickable or to the shop.

### Instances

- An instance is one physical copy of a set: inventory code, condition (`New`, `Good`, `Worn`), physical status (`Available`, `InMaintenance`, `Retired`, `Lost`), notes.
- Instance status in Catalog is the physical status. Whether an instance is rented is owned by the Reservation Service.
- An inspection result updates the instance condition and may set `InMaintenance` (see [Return and inspection](09-return-and-inspection.md)).
- A lost set sets the instance `Lost` (see [Overdue and lost sets](10-overdue-and-lost-sets.md)). A lost instance that comes back later goes back to `Available` after inspection.

### Inventory code and QR label

When an admin adds an instance, Catalog generates its inventory code and a printable label. The label is glued on the box. Staff scan it with a QR scanner to find the instance quickly when they hand the set to a customer or receive it back.

- The inventory code is generated by Catalog. It is unique, never reused, and never changes. The admin does not type it.
- **Readable after wear.** The code uses only characters that stay distinguishable when the label is scratched, faded, or partly torn:

  | Allowed (17) | `2 3 4 5 7 9 A E H K M N P T W X Y` |
  |---|---|
  | Excluded | `0 O Q D C G 6` (round shapes), `1 I L J` (vertical strokes), `8 B`, `S`, `Z`, `U V`, `F` (looks like a worn `E`), `R` (looks like a worn `P`) |

- Format: 5 code characters plus 1 check character, printed in two groups: `W9X-25W`. 17^5 gives 1,419,857 codes. If the shop ever needs more, the length grows to 6. Existing labels stay valid, because the parser accepts both lengths.
- The check character (Luhn mod N over the 17-character alphabet) catches a single wrong character or two swapped characters when a code is typed by hand. A wrong code is rejected before any lookup.
- Input is normalized: lowercase is accepted, and dashes and spaces are ignored.
- **Neighboring boxes look different.** Copies of the same set stand next to each other on the shelf, so consecutive numbers must not give similar codes. Before encoding, the number is scrambled. The codes stay unique but look unrelated: numbers 1, 2, 3 become `HW9-5N4`, `2NM-E94`, `KHX-MY3`.
- **Generation steps:**
  1. Take the next number `n` from the PostgreSQL sequence `inventory_code_seq` (one query for all instances when `quantity` > 1).
  2. Scramble: `m = (n × 738457) mod 17^5`. The multiplier shares no factor with 17^5, so every `n` gives a different `m`, and `n` can be recovered with the inverse 923080.
  3. Encode `m` in base 17 with the alphabet above, padded to 5 characters.
  4. Append the Luhn mod N check character.
  5. Print as `XXX-XXX`.
- A rolled-back transaction leaves a gap in the sequence. That is fine: codes do not need to be continuous, and numbers are never reused.
- **Physical durability:** labels are printed on polyester (not paper) with a thermal transfer printer. Direct thermal labels fade and are not used. The QR code uses error correction level H, so it still scans with up to 30% of it damaged. The code text uses a large monospaced font.
- The QR code contains **only the inventory code** as plain text, for example `W9X-25W`. No URL and no internal id.
- Staff use a 2D barcode scanner that works as a keyboard (USB or Bluetooth HID). The scanner types the code into the focused search field of the staff client and ends with Enter. The client then calls the lookup endpoint. No special scanner driver or integration is needed.
- Plain text keeps the QR code small and easy to scan, works in every environment, and never goes out of date. If a label cannot be scanned, staff type the code printed below the QR code.
- The code alone gives no access: every lookup needs a signed-in staff account.
- The label shows the QR code, the inventory code in large text, the set name, and the LEGO set number. It contains no customer data.
- Label format: SVG, 50 × 30 mm, ready for a label printer or a normal printer.
- Adding several instances returns all their labels in one printable sheet.
- A damaged label can be reprinted at any time. The content is always the same.
- Scanning resolves the code to the instance, its set, and its current physical status (see [Pick-up](08-pickup.md) and [Return and inspection](09-return-and-inspection.md) for how scans are used).

### Images

1. Admin requests an upload URL. Catalog returns a short-lived user delegation SAS URL for `set-images/originals/{setId}/{imageId}`. The image status is `Uploaded`.
2. Admin uploads the file directly to Blob Storage.
3. Media Functions create a web version (WebP, max 1600 px) in `set-images/web/` and a thumbnail (400 px) in `set-images/thumbs/`, then publish `SetImageProcessed`.
4. Catalog stores the web and thumbnail blob names and marks the image `Ready`.

## Endpoints

| Method | Route | Policy | Purpose |
|--------|-------|--------|---------|
| GET | `/catalog/sets/lookup/{setNumber}` | `AdminOnly` | Look up specs in Rebrickable and return a set draft (nothing is saved) |
| POST | `/catalog/sets` | `AdminOnly` | Create set from a submitted draft or from manual input |
| POST | `/catalog/sets/{id}/refresh-specs` | `AdminOnly` | Re-fetch Rebrickable data for an existing set |
| PUT | `/catalog/sets/{id}` | `AdminOnly` | Update set |
| DELETE | `/catalog/sets/{id}` | `AdminOnly` | Deactivate set (soft delete) |
| POST | `/catalog/sets/{id}/images/upload-url` | `AdminOnly` | Get a short-lived user delegation SAS URL for direct upload to `set-images/originals/` |
| POST | `/catalog/sets/{id}/instances` | `AdminOnly` | Add one or more instances (`quantity`), returns ids, inventory codes, and label URLs |
| GET | `/catalog/instances/{id}/label` | `AdminOnly` | Label for one instance (SVG), also for reprints |
| POST | `/catalog/instances/labels` | `AdminOnly` | Printable sheet with labels for several instances |
| GET | `/catalog/instances/by-code/{inventoryCode}` | `EmployeeOrAdmin` | Resolve a scanned code: instance, set, condition, physical status |
| PUT | `/catalog/instances/{id}` | `AdminOnly` | Change condition or status |
